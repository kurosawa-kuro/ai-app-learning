# 07 テスト戦略

[AGENTS.md](../AGENTS.md)に従い、教材の動作、本人の経験・習得、提供者の支援終了を別々に検証する。AIが完成させたことやテスト合格だけで学習成果を認定しない。

## 変更内容に応じた検証

| 対象 | 必要な確認 | 証明しないもの |
|---|---|---|
| 文書・リンク・命名 | ルート3文書との整合、参照先、改名による欠落・参照漏れ、差分 | アプリ動作・実環境受入・学習効果 |
| アプリの実装・設定 | 対象教材のREADME・AGENTS.mdにある実際のテスト・整形・静的検査 | 公開済み・実データで安全に動くこと |
| 画面・通信 | 必要な操作と期待結果。模擬通信と実通信を区別 | ローカル確認だけでの本番保証 |
| 公開・移行 | 対象のrunbookによる公開版・権限・保存・復旧の確認 | ビルド成功だけでの利用開始可否 |
| 学習者への提供 | 同じ環境・サンプルで予行し、本人の依頼・試行・判断を観測 | 全技術の習得・就職・資格合格 |

ルートの `make test` はTODO表示の雛形であり品質ゲートではない。検証コマンドは対象教材の実装から確認する。未実装のWeb・Java環境や設計段階の教材に、架空の起動・試験結果を記載しない。

文書変更では、相対リンクと正本との整合を確認したうえで実行する。

```powershell
git diff --check
```

改名した未追跡ファイルは通常のdiffだけでは検査されないため、移動前後の対応と内容も照合する。

## 初回成功の確認

[支援シート](templates/ai-pairing-session.md)で、本人の希望がAIへの依頼に反映されたこと、応答を使って課題を進めたこと、期待結果と比較したことを確認する。提供者が補助してよい。「AIが正しいと言った」だけでは結果確認としない。

全教材の修了、自力のコード記述、資格、別課題への応用は初回の合格条件に足さない。その先を選んだ場合は、GASの興味・理解・活用、Webの実利用、Java・SQLの自力修正、事務処理の正確さ・時間・再現性など、本人の目的で判断する。

## 支援終了と提供可能性の確認

課題と支援の枠が事前に決まり、依頼文・確認方法・戻し方が引き渡され、終了日と残件の扱いが記録されたかを確認する。準備時間・支援時間・質問対応量を振り返り、支援が無期限に延びない範囲へ調整する。未達のまま枠が終了した場合は、成功と区別して残す。

協力者は未定、教育支援の実証は未実施。[初回検証案](../src/app-learning/docs/06_first-pairing-pilot.md)の記載を実績と扱わない。

## 検証記録

対象教材・版、日付、環境、コマンドまたは操作、期待と結果、未実施事項・理由を残す。模擬試験、実環境受入、公開、本人の経験を区別する。過去のPASSを最新版へ流用しない。開発作業の証拠区分は[Evidence Policy](specs/evidence-policy.md)を参照する。
