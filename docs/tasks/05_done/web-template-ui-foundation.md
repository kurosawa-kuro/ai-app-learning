# Webテンプレートの共通UI・操作導線の改修記録

作成・実装日：2026-10-27。ユーザー提供のUI/UX評価に沿って共通UIを改修。管理画面の維持とゲーム画面の別レイアウトを両立させる。以下のContext・Planは着手時の記録であり、現在の仕様は[共通UI設計](../../../src/web-app-starter/template/docs/ui-foundation.md)を参照。

## Goal

admin-picoとPico CSSを活かし、投稿ノートとゲーム型教材の両方を支えられる共通UIを整える。画面幅・情報の優先順位・操作と状態表示のルールを揃え、各教材で同じ調整を繰り返す負担を減らす。

ログインは意図的に除外する。認証の追加を改善項目にしない。黒基調・緑のアクセント、Spring Boot・Thymeleaf、User 1：Post 多、画像の任意添付は維持する。

## Context：着手時のコードとの照合

対象：[template](../../../src/web-app-starter/template/README.md)。現行ファイルを読んで確認した内容であり、以前の一画面版を前提にしない。

| 現行箇所 | 確認した状態 | 改修の焦点 |
|---|---|---|
| templates/layout.html | 共有fragmentは存在する。ただしアプリ名、投稿・投稿者のリンク、currentAuthor、画像ON/OFF、モバイルタブが直書き | 共通シェルと投稿アプリの設定・状態を分離 |
| templates/posts/list.html | 一覧画面と絞込みが独立済み | ページ全体の最大幅、一覧の情報量と主操作を揃える |
| templates/posts/form.html | フォームのみ52rem上限。ヘッダーとフォーム幅の基準が異なる。投稿者selectと共通ヘッダーの選択表示が併存 | ヘッダーごと約800pxの幅へ。投稿者の操作を一か所に集約 |
| templates/posts/detail.html | 詳細画面は存在。本文と情報カードの2列。ブラウザーconfirmによる削除確認も存在 | 長文の行幅、情報の重複、削除の強調度、確認パターンの統一 |
| static/app.css | ページ幅・投稿固有・モバイルナビ・共通フォーカス等が同居 | 共通トークン、レイアウト、部品、投稿専用CSSへ分離 |
| PostController / PageContext | 検証失敗時の本文保持は一部実装済み。DB障害・サイズ超過ではredirectになる | 失敗の種類ごとの入力保持・復旧導線を揃える |

既存の画面分割、本文へスキップ、モバイルメニュー、フォームの一部入力保持、削除確認は活かす。「全部ない」と見なして作り直さない。

## Scope

今回の対象は共通UI、投稿アプリの画面・状態表示、ゲーム型への適合確認。DB再設計、認証、全GAS教材の移植、Renderへの公開、大幅なブランド変更は含めない。

提示された評価内の参考画像をそのまま模写するのではなく、評価本文の修正事項と既存admin-picoの部品に沿って設計する。

## Skeleton：責務の分離

ThymeleafのfragmentとCSSの役割で分ける。React等の追加は行わない。

| 部品 | 責務 | 持ち込まないもの |
|---|---|---|
| AppShell | アプリ名、テーマ、ヘッダー、任意のサイドバー、モバイルメニュー、メイン領域 | 投稿者モデル、投稿URL、画像設定、DBアクセス |
| Navigation | アプリ側から渡すラベル・URL・選択中項目を表示。PC/モバイルで同じ定義を利用 | 共通fragment内の投稿専用リンク |
| PageLayout | form / standard / detail / playの幅・余白・レスポンシブ | 各ページでのその場しのぎのmax-width |
| PageHeader | ページタイトル、短い説明、主操作、必要なら戻る導線 | 装飾の英語見出し、全ページ固定の投稿者表示 |
| Form | 項目名、必須/任意、補足、項目エラー、送信状態、操作列 | 個別の投稿保存ロジック |
| List | 絞込み、件数、一覧、空状態、モバイルでの情報順 | 投稿固有の列定義・データ取得 |
| Detail | 読む領域、補足情報、通常操作と削除領域の配置 | 投稿専用フィールドの固定 |
| Feedback / Confirm | 保存中・成功・失敗・空状態・削除確認、フォーカス制御 | 保存処理の成否を見ずに成功を表示する処理 |
| 投稿アプリ | 投稿・投稿者のナビ定義、入力項目、投稿者選択、画像機能の状態 | 共通シェルの複製 |

想定配置：templates/ui/に共通fragment、templates/posts/とusers/に業務画面、static/ui/に共通CSS・JS、static/features/posts/に投稿固有の調整。既存layout.htmlを移行の入口として使い、段階的に中身を抽出する。

admin-picoのテーマ・カード・フォーム・ナビ・ダイアログの部品を先に確認して使う。足りない責務だけを薄い共通fragmentで補う。共通CSSの元ファイル、Pico本体の固定版・ライセンスは引き継ぐ。

## Plan：修正順

### P0-1：画面幅と主操作を先に決める

幅はサイドバーを除く利用可能領域に対する上限。画面が広くなってもフォームや長文を無制限に引き伸ばさない。タイトル・説明・主操作・本文は同じページコンテナーに収める。

| 画面種別 | 上限の初期基準 | 配置 |
|---|---|---|
| form：新規投稿 | 800px | 中央寄せ、一列の入力。末尾にキャンセル・保存 |
| standard：投稿一覧・投稿者管理 | 1200px | タイトルと主操作 → 絞込み → 件数・一覧 |
| detail：投稿詳細 | 960px | 本文の行幅は最大約40em。補足は脇または下、削除は末尾 |
| play：ゲームの操作領域 | 960px | 中央の選択・決定・結果が主役。常設サイドバーは不要 |

- 共通トークンで上限を管理し、個別画面から数値を上書きしない。
- 内側の余白はPC 24px、狭い画面16pxを基準にする。
- 390 / 768 / 1280 / 1920pxの画面で確認する。上限は固定幅ではなく、狭い画面では利用可能幅まで縮む。
- 投稿一覧の主操作は「新規投稿」、フォームは「投稿を保存」。主操作の強調をページ内で競合させない。

### P0-2：共通シェルから投稿固有情報を外す

- layout.htmlに直書きされた投稿リンク・アプリ名・投稿者表示をアプリ側の設定/fragmentへ移す。
- 同じナビ定義からサイドバーとモバイル表示を作る。画面ごとに二重管理しない。
- AppShellはサイドバーあり/なしを選べる。ゲームに「投稿一覧」「投稿者管理」や管理画面用の大きな左ナビを表示しない。
- imagesEnabledの扱いは投稿フォーム・添付画像の表示へ寄せる。共通シェルへ機能フラグを直書きしない。
- シェル描画だけのために全教材へ投稿者DBへのアクセスを要求しない。PageContextの投稿者供給も投稿アプリの範囲に限定する。

### P0-3：投稿とゲームの画面骨格を並べて確認

スタイルの微調整前に、同じ共通UIで次の2種類を組み立てる。

- 投稿ノート：一覧 → 新規投稿 → 詳細。
- skill-janken-game相当：仲間・スキルの確認 → グー/チョキ/パーの選択 → 明示的な決定 → 結果。

skill-janken-gameは現在GAS版なので、Thymeleaf fragmentをそのまま共有できるとは扱わない。まずSpring側のUI検証用画面でゲームの配置・操作を再現し、共通CSS・部品の責務が適合するか確認する。ゲームデータや勝敗処理は検証用と明示し、GAS移植・実ゲームとの接続完了とは区別する。

### P1-1：投稿者選択を一か所へ集約

- 共通ヘッダーの「選択中の投稿者」チップを外す。ログインユーザーに見える表現をなくす。
- 新規投稿フォーム冒頭を「投稿者：山田 ［変更］」にする。変更操作をしたときだけ選択UIを開く。
- 未選択時は、その同じ場所で投稿者を選ぶ。0人なら「投稿者を追加」を示す。
- フォーム初期値は「この投稿者で新規投稿」の明示指定 → 前回選択の記憶 → DBのデフォルト → 未選択。決まった投稿先はフォームの下書きが保持し、送信時に実在確認する。
- 一覧の絞込みは表示条件であり、投稿先の状態とは分ける。絞込み操作で投稿先を黙って変更しない。
- 投稿先の変更・追加でタイトル・本文を失わせない。画面遷移を必要とする場合の戻り先と下書き復元を先に定義する。
- Cookie等で記憶する投稿者は便宜上の既定値であり、認証・所有者の証明にしない。

### P1-2：フォーム・詳細・状態表示を統一

| 場面 | 修正後の挙動 |
|---|---|
| 入力 | ラベルを上、補足を直下に置く。タイトルは必須、本文・画像は任意と表現を揃える |
| 入力エラー | 項目の近くに原因と直し方を表示。エラー概要から該当項目へ移動できる。入力値は維持 |
| 保存中 | 保存ボタンを「保存中…」にし二重クリックを抑制。aria-busy等で状態を伝える |
| 保存成功 | 保存先の詳細画面へ進み、保存完了を表示する |
| 通信・DB・Storage失敗 | 投稿フォームと入力を維持し、再試行を示す。画像の再選択が必要なら明記する |
| サイズ超過 | 送信前にもサイズを検査。サーバー側検査は継続する。リクエスト全体拒否時の下書き復元も検証する |
| 投稿0件 | 「まだ投稿がありません」＋「新規投稿」 |
| 絞込み0件 | 「条件に合う投稿がありません」＋「絞込みを解除」 |
| 投稿者0人 | 「投稿者を追加すると投稿できます」＋追加操作 |
| 削除 | 対象名と戻せないことを確認画面に表示。「キャンセル」を既定のフォーカスにする |
| 削除失敗 | 対象を残したまま理由と再試行を示す。成功していないのに一覧から消さない |

入力保持は通常のバリデーションだけでなく、DB例外・画像エラーでも確かめる。ファイル入力の自動復元はできないため、再選択と本文保持を別に扱う。フォーム状態保持のために無条件で本文を永続ブラウザーストレージへ保存しない。

詳細画面は「タイトル・投稿者・日時 → 本文・画像 → 次の操作」を基本にする。ヘッダーと情報カードに同じ投稿者・日時を重複表示しない。本文は全幅に伸ばさず、画像は縦横比を保つ。削除ボタンを主操作と同じ強さで常時競合させない。

### P2：可読性と視覚調整

- NEW POST / POST等の装飾英語を整理し、日本語のタイトル・操作説明を優先する。
- 本文16px、補足14pxを初期基準にし、重要な説明を小さな薄い文字だけで伝えない。
- 緑は主操作・現在位置、ピンクはエラー・削除等の注意に絞る。色だけで状態を区別しない。
- 長い投稿者名・タイトル、5000文字の本文、画像あり/なし、画像機能OFFでも崩れないよう確認する。
- スマートフォンの操作対象は約44px以上を基準とし、ダイアログ・ドロワーはフォーカス移動、閉じる操作、元の位置への復帰まで揃える。

## Notes

### 実装・検証結果（2026-10-27）

- AppShell / PageLayout / PageHeader / Form / List / Detail / Feedbackを共通fragmentへ分離。画面幅をform 800px、standard 1200px、detail/play 960pxへ集約。
- 投稿者はフォーム内の確認・変更・追加に集約。JSON送信で通信エラー時も入力を保持。項目エラー、保存中、空状態、対象名を示す削除ダイアログを実装。
- 管理画面・ユーザーのデフォルト指定・画像／AI許可設定を維持。ゲームUI体験は投稿DBモデルを要求しないコントローラーと、サイドバーなしの共通シェルを使う。
- Java 13件成功。Playwright 10件成功・2件は適用外または重複としてスキップ。実DB・Storage、失敗時の入力保持、設定共有、削除キャンセル、ドロワーのフォーカス、ゲーム操作を検証。
- 投稿・管理・ゲームを390 / 768 / 1280 / 1920pxで撮影・確認。機能管理は820pxも確認。ゲームカードの幅・ナビの余白を画像で確認し調整した。
- 表示部品名とHTMLタグ名の衝突、静的資産と投稿URLの衝突、ドロワー遷移前のフォーカス失敗を解消し、最終の全ブラウザーテストを通した。
- `git diff --check` と環境変数読込み検査も成功。今回のコードはローカル検証済み。Renderへは未反映、GASとの統合・AI接続は未実施。
- 通常POSTでリクエスト全体が拒否された場合の下書き復元、および通信断をまたぐサーバー側の冪等保証は対象外。JavaScript有効時は現在の入力を保持し、保存結果不明時は一覧確認を促す。

- 実装順は「幅と責務 → 投稿/ゲームの骨格 → 操作・状態 → 可読性 → 機能と視覚の検証」。先に色や装飾だけを調整しない。
- 実装時に確定した共通UIの規約はテンプレート仕様・READMEへ反映する。この計画書を実装済み仕様として扱わない。
- ローカルDockerがなくてもRenderデプロイは可能。リポジトリのDockerfileをRender側でビルドする方式を利用する。UI改修とは別作業として扱う。[Render公式](https://render.com/docs/docker)（2026-10-27確認）。
