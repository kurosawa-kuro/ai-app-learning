# 教育目的を逸脱した機能追加と公開検証の失敗

記録日：2026-10-27。これは提供者・受講者の要望不足ではなく、実装担当AIの設計判断と検証の失敗である。

## 本来の目的

一つの教材でAIに頼み、動かし、結果を確かめる経験を作る。全機能・全技術を学ぶことは必須ではない。提供者が制作・説明・検証・サポートを有限の範囲で提供できることが成立条件だった。

## やってしまったこと

「横展開前に不足をなくす」を、本番運用の網羅性を高めることと取り違えた。独自のバックアップ／復元、監査DB、永続AI要求台帳、定期削除、環境用Basic認証などを共通土台に積み上げた。必要性を教育目標から確認せず、過去に追加した課題をすべて実装すること自体を目標にしてしまった。

ユーザーが当初から認証不要と述べていたにもかかわらず、公開時の環境認証を別名義で追加した。個人ログインではないという分類は、ユーザーが望まない認証を追加してよい理由にはならない。

さらに、画面用データの自動注入が画像・非同期処理にも広がり、ユーザー選択に全投稿の件数集計を使い、必要のない画面へ投稿・AI用スクリプトも配信していた。

## 実害と確認できた事実

- 本番運用向けの説明・コード・検証項目が増え、教育内容の見通しと横展開時の変更範囲を悪化させた。
- Basic認証の結果を再利用せず、静的ファイル取得でもパスワード照合を繰り返していた。同じ環境で、修正前は複数画面が約10秒だった。
- Pico CSS本体がルートの `vendor/` 除外に巻き込まれ、Gitへ入っていなかった。Renderでは404／JSONになり、ボタン・入力欄などの基礎スタイルが適用されなかった。ローカルにあるだけで同梱済みと判断した。
- Renderの投稿0件の状態で測定し、約2秒への改善をデモの評価として報告した。実画像・複数ページを含む受入ではなかった。
- その後、12投稿・4画像を入れた確認では、デプロイ直後の一覧に約21秒を要した。稼働後の画像入り一覧は別計測で約3.2〜3.3秒だった。起動直後の遅さは残っていた。

上記は別々の問題である。監査や復旧コードすべてが各画面の10秒を直接発生させたという測定はしていない。コード量の過大化と、実行時の待ち時間の原因を混同しない。

## なぜ見逃したか

- 学習の成功より、実務的な完備性を優先した。
- 「実装する必要があるか」の再評価をせず、追加済みの課題表を実装命令として扱った。
- テスト成功・疎通成功・見出し表示を、配布物の完全性・使い心地・デモ品質と取り違えた。
- 空データ、ローカル資産、認証状態などの測定条件を報告の中心に置かなかった。

## 修正方針

1. 認証、独自復旧基盤、監査DB書込み、AI永続台帳・定期処理、環境表示を外す。
2. 投稿・画像・ユーザー選択・設定・CSV・最小AI連携へ絞る。AIの下書きはブラウザーセッションの直近1件だけ保持する。
3. 不要なDB照会と画面用資産の配信を減らす。画像・入力保護・参照チェックを維持する。
4. 過去の設計書・完了報告は履歴として区別し、廃止した機能を次の教材の必須要件へ戻さない。
5. 公開先に架空の投稿・画像を用意し、PC・スマホで機能・スタイル・速度を確認してから完了を報告する。

軽量化の実装・検証状況は[教育用の最小構成](educational-baseline.md)に記録する。この記録を書いたことだけでは改修完了としない。

## 再発防止を適用する場所

- [テンプレートのAGENTS.md](../AGENTS.md)：今後のコード変更へ適用する制約。
- [教育用の最小構成](educational-baseline.md)：残すもの・廃止するものの正本。
- tests/render-acceptance.cjs：公開先の全CSS・フォームスタイル・認証不要・CSRF。
- tests/render-visual.cjs：12投稿・画像・2ページ、PC／スマホ、横はみ出し・画面エラー。
- tests/render-performance.cjs：ページ別の経過時間とリソース取得時間。

追加提案を採用する基準は「実務ではあった方がよい」ではなく、「この教材のどの学習目標を、最小の実装で達成するか」である。

## 追加で見つかった画像保存の不具合

利用者からPOST /postsの502、その後403が続く報告を受けた。Renderの切替・旧プロセス終了のログは確認したが、502の個別原因は確定できていない。

フォーム保護トークンをサーバーセッションに保存していたため、再起動後の古いフォームからの送信は403になり、JavaScriptは同じ失効済みトークンを再送し続けた。英語のForbiddenだけを表示し、入力保持後の復旧導線を用意していなかった。

修正：CSRFトークンをHttpOnly・SameSite=LaxのCookie方式に変更し、サーバー再起動から独立させた。403時はGET /csrfでトークンだけ更新する。投稿は自動再送せず、本文・画像・同じ要求IDを残したまま本人がもう一度保存する。ページの再読み込みや入力の破棄を要求しない。

検証：再接続のPlaywrightで502→実際のCSRF失効403→再保存→画像表示・投稿1件を確認。Javaでセッション消失後のトークン有効性と、Cookieなしの拒否も確認。ログイン・監査・永続AI台帳は再導入していない。

再発防止：閲覧だけで公開完了にせず、公開先で画像付き保存まで確認する。利用中のデプロイはフォームの継続操作へ影響するものとして扱う。
