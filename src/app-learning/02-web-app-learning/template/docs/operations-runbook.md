# 状態確認・復旧・公開範囲の運用

2026-10-27。コマンドはテンプレートのディレクトリで実行する。

## 日常の修正と障害確認

- 投稿詳細の「投稿を編集」でタイトル・本文を変更する。画像は維持・差し替え・解除を選べる。保存前に別操作で投稿が変わっていた場合は上書きせず、再確認を求める。
- ユーザー管理の「名前を変更」で表示名を変更する。ユーザーID・アイコン・既存投稿・デフォルト指定を維持する。
- 「管理・設定 → 状態と復旧」で、環境名・接続先の識別名・実スキーマ、DB、Storage、画像許可を確認する。画像の許可とStorageの正常性は別々に表示する。
- 「保存済み画像を確認」は投稿・アイコンの参照先を取得し、正常・元画像なし・取得失敗を区別する。元画像が失われた場合は、元ファイルを再アップロードする。
- 「後片付けを再試行」は削除待ちの画像だけを処理する。参照中の画像は削除しない。繰り返してよい。
- 操作結果は `operation_events` に日時・固定の処理コード・結果・照会IDを記録する。HTTP結果の数字は応答ステータスであり、200だけで業務処理成功とは判定しない。投稿の保存・更新等は別の処理結果も残す。

ログや操作結果へ本文・画像・パスワード・キーを出さない。ブラウザーで選択したユーザーは、本人確認済みの実行者ではない。

## バックアップの範囲

「状態と復旧 → バックアップを保存」、または次のコマンドを使う。

```powershell
.\run-local.ps1 -Action backup
```

`.local/backups/backup-*.zip` に保存する。Web操作では同じファイルをダウンロードできる。`.local` はGit除外。

| 内容 | 扱い |
|---|---|
| ユーザー、投稿、アイコン、管理設定 | 全行を保存 |
| 操作記録、投稿・AIの受付記録、AI結果、削除待ち記録 | アーカイブへ保存。削除待ちは復元先で自動実行させず隔離する |
| 投稿・アイコンが参照する画像 | 実ファイルを保存し、SHA-256を記録。同じ画像の参照は重複保存しない |
| DBマイグレーションの版、取得日時 | manifestへ保存 |
| DB接続・Storageキー・環境アクセス用パスワード | 含めない。提供者が別の秘密情報管理で保持する |
| Storage内の未参照ファイル、他アプリ・他スキーマ | 対象外 |

DBの読取は一貫したスナップショットを使う。画像が取得できない場合は不完全なZIPを成功扱いせず、作成を中止する。バックアップ時には投稿・画像の編集を止め、DBと画像の変更が重ならないようにする。

運用基準は、利用日の終了時と更新・データ操作前に取得し、提供者がアプリと別の安全な保管先へコピーすること。直近7日分と週次4世代を目安に保管し、月1回および大きな更新前に復元確認を行う。これは実施する運用であり、定期実行や外部保管を自動設定済みという意味ではない。

復旧可能な時点はmanifestの取得日時である。バックアップ取得後に追加したデータはそのZIPからは復元できない。

## 独立した場所への復元

```powershell
.\run-local.ps1 -Action restore `
  -BackupFile .local/backups/backup-取得したファイル名.zip `
  -RestoreSchema app_template_restore_check_20261027
```

復元先は**未作成の `app_template_restore_*` スキーマだけ**に限定する。既存スキーマ・通常の `app_template` への上書きは拒否する。ZIP形式2・対象表一覧・アプリのマイグレーション版が一致しない場合も拒否する。まず対応版のアプリで復元し、その後の版更新として扱う。

1. 画像のチェックサムとアーカイブ形式を検査する。
2. Flywayで新しい復元先を作成する。
3. 画像を新しいキーへ保存し、取得し直してチェックサムを検証する。元画像は上書きしない。
4. 投稿・アイコンの参照を新しい画像キーへ変更し、DBデータを一つのトランザクションで登録する。
5. 全対象テーブルの値と件数を照合してからコミットする。ユーザーとの関係は外部キーでも検査する。
6. `RESTORE` 結果のスキーマ・投稿数・ユーザー数・画像数・取得日時・所要ミリ秒を記録する。

削除待ち記録はZIP内に残すが、復元先の実行キューへは投入しない。元環境の画像キーを復元先から削除する事故を防ぐためである。

失敗した場合、元の環境は維持される。登録途中のDB処理をロールバックし、新しくアップロードした画像を削除する。後片付けできなかった画像は元環境の削除待ちキューへ記録する。作成された独立スキーマは調査用に残り得るため、同じ名前で再実行せず、原因を確認して別の新しい名前を使う。

復元したアプリを実際に開く場合は、`APP_DB_SCHEMA` をその復元先、`SERVER_PORT` を別ポートに指定して起動し、一覧・詳細・画像・設定を確認する。本番への切替は、利用停止・最新バックアップ取得・復元先の受入・接続先切替・再起動・受入の順で実施する。元環境を削除してから復元を始めない。

## 環境と公開範囲

| 設定 | 用途 |
|---|---|
| `APP_ENVIRONMENT=local/test/production` | 環境名。CLIのシード変更・復元はlocalでのみ実行 |
| `APP_CONNECTION_LABEL` | 秘密情報を含まない接続先の識別名。例：自分用アプリ開発DB |
| `APP_DB_SCHEMA` | 実際に使用するスキーマ。公開先とローカルは別に指定する |
| `APP_ACCESS_MODE=local` | ループバック限定。公開バインドやproductionとの組合せは起動拒否 |
| `APP_ACCESS_MODE=basic` | Spring Security標準のHTTP Basicでアプリ全体を保護 |
| `APP_ACCESS_USER` | 環境に入るためのユーザー名。既定はstarter |
| `APP_ACCESS_PASSWORD` | 環境用の20文字以上の秘密パスワード。Gitへ保存しない |

アプリ内のユーザー管理にログイン・パスワードを追加していない。Basicは公開した環境へ入るための共通ゲートであり、投稿の操作主体選択とは別である。公開時はHTTPSを使い、環境パスワードを許可した利用者へだけ渡す。

Renderプロファイルはproduction・basicを既定にする。未設定や短いパスワードで起動しない。Blueprintの `APP_ACCESS_PASSWORD` と `APP_DB_SCHEMA` を設定する。ヘルスチェックだけは `/healthz` を認証なしにし、接続情報・投稿・管理情報を返さない。

CSRF保護はlocal・basicとも維持する。独自ログインを実装せず、[Spring Securityの標準認証](https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/index.html)を使用する。復元先のマイグレーションには[Flywayのスキーマ指定](https://documentation.red-gate.com/fd/flyway-default-schema-setting-277578987.html)を使用する。

## AI下書きの状態と保持

投稿の本文と今回選択した1画像を明示操作で送信する。保存済み画像は送らない。AI禁止・未設定・未許可モデル・画像禁止は送信前に拒否する。起動・表示・保存設定だけで課金APIを呼ばない。

`ai_requests` は要求ID、セッション所有ID、用途、入力ハッシュ、モデル、指示版、状態、生成結果を保存する。入力本文・画像そのものは保存しない。結果は同じブラウザーセッションだけで再取得でき、セッションを失った場合は管理DBを利用者へ公開して回収しない。

| 状態 | 操作 |
|---|---|
| RUNNING | 「同じ要求の結果を確認」。新しい要求を勝手に送らない |
| SUCCESS | 記録済み結果を取得し、本文へ反映／破棄。投稿の保存は別操作 |
| FAILED | 原因を確認し、必要なら明示的に新しい要求を作る |
| UNKNOWN | 外部処理済みの可能性あり。2分を超えた実行中もこの状態。自動再送しない |
| EXPIRED | 7日の保持期限超過。本文を消し、受付ID・ハッシュを残して古い再送を防止 |

結果本文は取得時に期限検査し、起動1分後・以後1時間ごとの整理でも削除する。停止中は整理が動かないため、起動後に反映される。受付記録を手動削除すると再送防止が失われるため、通常は削除しない。バックアップにはその取得時点の生成結果が含まれる。ZIPも機密データとして扱い、7日／週次4世代の運用に沿って期限管理する。

DB停止等で結果を記録できなかった場合も、自動でAIを再実行しない。DB復旧後に同じ要求の状態を確認する。外部APIとDBの厳密な一回実行を保証するものではない。

## リリース時の確認

ローカルでの実装・受入完了と公開先への反映を分ける。デプロイごとに、HTTPS、環境識別、匿名で投稿／管理へ到達できないこと、正しい環境認証で表示できること、CSRFなし更新が拒否されることを確認する。停止中のRenderを受入済みと記録しない。
