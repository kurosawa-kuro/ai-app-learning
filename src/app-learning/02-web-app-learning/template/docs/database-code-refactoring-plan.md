# 横展開前のDB・コードのリファクタリング計画

2026-10-27。状態：計画。機能を削らず、動作を固定してから構造とDBを整えるための文書。

## 目的と制作の位置づけ

提供者の制作順 **02 Web → 01 GAS** に従い、動作確認しやすいWeb側で再利用可能な実装・検証・解説を先に整える。受講順は01 GAS → 02 Webのままとし、フォルダー番号を変更しない。教育・横断設計の正本は[app-learning/docs](../../../docs/README.md)。

Clean Architecture × DDD Lite × Modular Monolithの機能境界を維持する。横展開先のアプリが必要な機能だけを使えること、変更箇所と失敗時の挙動を追えることを完了の基準にする。

## 教材の範囲から優先する整理

[共通仕様F3](shared-foundation-requirements.md)に従い、ユーザー照会の `posts` 結合、運用画面の投稿・アイコン画像SQL、バックアップ／復元の固定対象を優先する。教材側の参照・画像・保存データを小さなAdapterへ分け、既存の共通処理を再利用する。汎用CRUD生成や動的プラグイン機構へ拡大しない。

AI要求記録を追加するときも、既存のバックアップ対象から漏れないことを確認する。投稿テーブルを残したまま表示名だけ変えることを、教材への再利用完了と扱わない。既存データを削除せず、別の検証環境で投稿以外の小さなデータと復旧を確かめる。

## 進める順番

| 段階 | 作業 | 完了条件 |
|---|---|---|
| 0. 基準保存 | 作業ツリーの差分とDBの版を確認し、変更前を保存。DB・画像・設定のバックアップを取得し、別スキーマへ復元 | 元のデータを上書きせず復元でき、件数・参照関係・画像・設定を照合できる |
| 1. DBの棚卸し | 各表の所有機能・制約・索引・更新経路・削除方針を一覧化 | 一つの値の正本と更新責任が明確。未参照画像や再送・削除待ちの扱いを説明できる |
| 2. コードの重複整理 | 投稿作成／編集の入力検証・HTML／JSON応答・補償処理を共通化。巨大なControllerを分割 | 正常系と失敗時の挙動を維持し、共通化した単位に必要な検証がある |
| 3. DB変更 | 棚卸しで必要性が確認された制約・索引・運用列だけを新規マイグレーションで追加 | 既存データで移行でき、不整合を黙って削除・初期化しない |
| 4. 運用処理の整理 | バックアップ／復元、画像整合性確認、後片付け、操作記録を責務ごとに分ける | 業務処理から直接SQLやStorage実装を参照せず、復旧の順序を追える |
| 5. UI・検索の整理 | 共通シェル・投稿・ユーザー・管理のJS/CSSを見直し、フォームの状態管理を明確化 | 画像有無・失敗・戻る操作・未保存・再送・絞込み・ページ移動を維持 |
| 6. 横展開の受入 | テンプレートを別の検証用スキーマ・バケット・環境名で起動し、小さな用途差分を入れる | 元アプリとデータ・キー・設定を混同せず、変更範囲と戻し方を解説できる |

## DBで確認する論点

- `posts.version` の競合検査と、更新成功時の増分を全更新経路で統一する。
- 画像のバケット・キー・種別の一組、ユーザー参照、アイコン1人1件などの制約を、アプリとDBの両方で照合する。
- 一覧と検索の実行計画・取得件数を測定し、使われていない索引や同じ先頭列の索引を整理する。変更前後を記録し、推測だけで索引を増減しない。
- ユーザー名・投稿数の読取結合、既定ユーザーと機能フラグが同じ設定表にあることを、業務上の責任と物理配置に分けて評価する。
- 二重送信の受付記録・操作記録の保持期間と整理方法を決める。再送保証を壊す削除はしない。
- 削除待ち画像について、参照中・未参照・欠損・取得不能を区別する。復元先から元環境の画像を消さない。
- バックアップ形式・マイグレーションの版・復元対象の互換性を揃える。

## コードで確認する論点

- 機能外からは公開APIを使い、他機能の `internal` に依存しない。
- Domain/ApplicationのSpring・HTTP・SQL・ImageIO非依存を維持する。
- リクエストID・内容照合・競合・画像の補償・後片付けを、トランザクション境界が見える形で整理する。
- 業務上の失敗と技術障害を区別する。生の例外や上流の応答を画面・ログへ漏らさない。
- 操作記録でHTTPステータスと業務処理の成否を区別し、選択ユーザーを本人確認済みの実行者としない。
- 共通化するのは検証・通信・状態・部品等の責務。用途ごとの業務ルールを汎用設定へ無理に押し込まない。

## 実施時の不変条件

- 登録済みのユーザーID・投稿ID・画像・設定を保持する。
- 適用済みマイグレーションを書き換えない。変更は新しい版を追加する。
- 競合拒否、同じ要求の再送、画像差し替え失敗、DB保存失敗、後片付けの再試行を維持する。
- シードは固定IDの不足分を追加し、通常起動で利用者データを初期化しない。
- ローカルと公開環境の制限、CSRF、秘密情報の管理を弱めない。

## 検証と解説の完成条件

各段階を小さな差分で進め、関連テストが通ってから次へ進む。最後に、実DB・実Storage・バックアップ／復元・画像が混在する複数ページ・PC／スマホを確認する。

解説には「どこを変えるか」「なぜその境界か」「何を試せば正しいか」「失敗したらどう戻すか」を含める。Web側で実際に検証した小さな変更例を作り、GAS側へ展開できる仕様・期待結果と、GAS側で別途確認する事項を分ける。
