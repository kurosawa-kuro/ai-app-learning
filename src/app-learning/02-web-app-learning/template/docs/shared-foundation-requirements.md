# 5教材から逆算したWebテンプレートの共通仕様

2026-10-27。**追加する共通仕様の設計と、現コードを読んだ棚卸し**。本書の作成ではアプリ改修・API送信・動作試験を行っていない。「コードあり」は今回の動作保証や配布完了を意味しない。

## 結論：先に埋める共通の不足

既存の画面・管理・投稿・DB・画像・検証基盤を再利用する。致命的な不足は、**3教材が使うAI実行の共通経路**と、**投稿サンプルを別の教材に置き換えても共通管理・復旧が成立する境界**に絞る。

| ID | 土台で先に整えるもの | 現状と不足 | 最小の完成条件 |
|---|---|---|---|
| F1 | Geminiへのテキスト＋任意の画像入力 | `FeaturePolicy.requireAiEnabled()` と起動時のキー読込みはある。Geminiへ送信するJava実装・応答処理・疎通画面はない | AI禁止・未設定時に通信せず、明示操作でテキスト／検証済み画像を送り、応答か整理済みの失敗を返す |
| F2 | AI実行状態・再送と、結果を使う共通UI | 投稿の二重登録防止・入力保持はある。AI要求の状態、結果の再取得、生成結果を既存入力へ取り込む流れはない | 同じ要求の再送で成功済みAI呼出しを繰り返さない。生成結果を確認・破棄でき、日記・セリフは採用前に確定保存しない |
| F3 | 投稿専用処理と共通管理・復旧の切り分け | ユーザー照会の投稿数、画像検査、復元対象表等に `posts` 固有処理が残る | 投稿サンプル以外でもユーザー管理が動き、教材固有の参照・画像・保存データを明示した小さなAdapterで復旧対象にできる |

F1・F2は一つの小さなAI基盤として作る。F3は既存処理の移し替えで進める。5教材の完成実装、汎用アプリ作成エンジン、任意のテーブルから画面を生成する仕組みは作らない。

## 教材と共通部品の対応

| 教材の完成範囲 | 共通で使うもの | 教材側に置くもの |
|---|---|---|
| 写真日記：写真・タグ・AI下書き・手直し・保存・一覧・詳細 | 画像の検証・保存・表示、AIのテキスト＋画像入力、下書きUI、DB・一覧・詳細 | 日記と写真・タグの関連、文体・生成指示、採用・保存のルール |
| 英語：クイズ・AI採点・テキスト会話・振り返り・履歴 | 入力フォーム、テキストAI呼出し、要求状態、DB・履歴表示の部品 | 問題・回答・問題版、採点基準、必要な会話文脈、振り返り。問題管理画面は任意の応用 |
| キャスト評価：単一店舗の入力・ルール・月次集計・順位 | 管理画面、入力検証、DBトランザクション、一覧・設定部品 | キャスト・実績・配点・集計SQL・順位。アプリ内AIは不要 |
| じゃんけん：スキルあり＋AIセリフ事前作成 | ゲーム用レイアウト、テキストAI呼出し、結果の確認・採用・保存 | スキル・勝敗・得点・対戦履歴、セリフ用途と表示条件。対戦中にはAIを呼ばない |
| ショップ：カート確認後に注文 | 一覧・フォーム、DBトランザクション、二重登録防止の実装例 | 商品・カート・注文・明細、確定時点の価格、取消ルール。アプリ内AIは不要 |

User 1：Post 多は関連データの実装例。日記・回答・キャスト実績・注文をすべて `posts` に格納する設計にはしない。管理画面のユーザー選択も本人認証ではなく、キャストや注文者などの業務データと自動的に同一視しない。

## F1：小さなAI呼出し境界

### 共通処理

- `GEMINI_API_KEY` を `.env`／環境変数からサーバーだけで読む。キー未設定・AI禁止でも通常機能は起動する。
- `FeaturePolicy` を必ず呼出し開始時に確認する。起動・画面表示・設定保存ではAI通信しない。
- 入力は用途ID、要求ID、サーバーで決める生成指示・モデル・出力上限、利用者の入力文、任意の検証済み画像。画面から任意の接続URL・サーバーキー・内部Storageキーを指定させない。
- 写真日記では画像内容を送るため、画像を文章のファイル名だけで代用しない。`ImageCodec`／`ImageStore` を再利用し、アクセス可能な画像を取得して入力へ渡す。画像枚数と合計容量の上限を設定し、必須の画像が取得できなければ黙って省かず失敗を返す。
- テキスト応答、使用モデル、要求ID、成功／失敗／結果不明を返す。必要なJSON形式の検証や採点としての妥当性は教材側が担当し、不正な応答を正答・採点済みとして保存しない。
- タイムアウト、認証失敗、利用制限、接続失敗、空／不正な応答を区別する。画面・ログにはキーや上流の生のエラー本文を出さない。
- モデルとAPI仕様は実装時に公式情報で確認する。複数AI事業者への同時対応や自動切替は今回作らない。

### 用途ごとの指示

共通化するのは通信・制限・状態・失敗の扱い。日記の文体、英語の採点基準、セリフ生成指示は各教材のコードまたはテキスト資産に置き、用途と版を識別できるようにする。巨大なプロンプト管理画面や汎用会話エンジンを追加しない。資格学習への変更も、まずこの小さな設定・データ・文言の変更で試す。

## F2：生成と確定保存を分ける

### 画面で再利用する流れ

`入力 → 明示的にAI実行 → 生成中 → 結果の表示 → 内容を確認 → 教材の操作へ反映`

- 入力中の本文・添付を生成で消さない。結果を破棄したら元の入力に戻れる。
- 日記では結果を下書きへ反映し、本人が手直しして通常の保存操作を行う。セリフでは管理側が内容を確認して採用・保存する。
- 英語の採点・会話は教材側の仕様に従って結果を履歴へ記録する。採点結果を本人が自由編集する機能や、全会話で採用ボタンを押す操作を共通UIとして強制しない。
- 生成中・禁止・未設定・失敗・結果不明を区別する。通信断時に勝手に新しいAI要求を送らない。
- テンプレートの実装例は、**短文＋任意の1画像から下書きを作り、本文へ反映して通常保存する一例**まで。3教材それぞれの完成AI画面は土台に作らない。

### 再送の最小仕様

投稿の `post_requests` は投稿保存用であり、AI要求の記録として兼用しない。AI側は要求ID・用途・入力照合用の値・状態・モデル／指示の版・結果の再取得に必要な情報を持つ、小さな永続記録を用意する。

| 状態 | 同じ要求が再送されたとき |
|---|---|
| 実行中 | 同じAI処理を重ねて開始せず、処理状態を返す |
| 成功 | 記録済みの結果を返し、外部AIを呼び直さない |
| 失敗 | 原因と次の操作を示す。新たな実行は利用者の明示操作にする |
| 結果不明 | 外部で処理が完了した可能性を示し、自動再実行しない |

同じ要求IDで入力が変わった場合は拒否する。入力を変えて再生成する操作は別の要求とする。処理中断・起動し直しで実行中のまま残る記録は、期限と確認手順を定めて結果不明として扱えるようにする。外部AIとDBをまたぐ厳密な一回実行を保証したと説明しない。

要求記録は二重送信対策のためのもの。長期の全会話履歴・利用者監査画面・実課金集計には広げない。本文・画像を一般の操作ログへ出さず、再取得用の結果データの保存先・保持期限・削除方法は実装時に明記する。AI実行記録と、教材の確定済み日記・採点・セリフは別に扱う。

## F3：共通に見える投稿専用処理を分ける

| 現在の結び付き | 最小の整理 |
|---|---|
| `JdbcAuthorStore` が常に `posts` を結合し、`AuthorView` が `postCount` を持つ | ユーザー本体の照会と、教材データの利用件数・削除可否の照会を分ける。参照がある利用者を削除しない条件を維持 |
| `OperationsController` の画像検査が投稿・アイコンのSQLを直接持つ | 教材側が対象画像を列挙し、共通部は取得・欠損・失敗の表示を行う。既存の `ImageReferences` による参照保護を再利用 |
| `RecoveryService` の対象表・復元処理が投稿サンプルの構造に固定 | 対象表・画像・復元処理を明示する教材側のAdapterへ分ける。新しい教材データやAI要求記録をバックアップから漏らさない |
| ナビ・スタイル・スクリプトの組立てが投稿／じゃんけんの2例に固定 | 今の `UiContext` を教材の組立て箇所として使い、変更点を一覧にする。動的プラグイン管理画面は作らない |

全教材向けの登録機構を先に作り込まず、投稿サンプルと小さな検証用の別データで、共通部を維持できることを確かめる。既存のテーブル・画像を削除して依存を解消したことにしない。

## 既にあるため作り直さないもの

2026-10-27にソースを読んだ範囲。動作試験結果は別記録を参照する。

| 領域 | コード上で確認できるもの | 教材化するときの注意 |
|---|---|---|
| UI | AppShell、フォーム、フィード・一覧・詳細、ゲーム用レイアウト、モバイルナビ | 投稿画面を全教材へ強制しない |
| 管理 | ユーザー作成・名前変更・選択・既定・アイコン、画像／AI許可 | 管理画面は認証・役割制御と別 |
| DB | Flyway、`UnitOfWork`、外部キー、投稿の競合・再送対策 | 教材ごとに表と業務ルールを作る。汎用JSON項目へ押し込まない |
| 画像 | 検証・非公開Storage保存・表示・プレビュー・拡大・後片付け | 投稿例は0〜1画像。日記の複数写真・タグの関連は日記側。共通の画像I/Oを再利用する |
| 運用 | 接続状態、環境識別、画像再試行、CSV、バックアップ・別スキーマ復元 | 投稿に固定された部分はF3で整理。CSVを完全バックアップと扱わない |
| 公開・秘密 | ローカル限定、公開時の共通Basic認証、CSRF、`.env`、環境別スキーマ | 共通Basic認証は個人ログインではない。Supabase Authを一律必須にしない |
| 検証 | Java・構造テスト・Playwright、実DB／Storage用の隔離設定、シード | AI通信は模擬試験を基本にし、実疎通は明示的に実行する |

## 実装順と、ここまでで土台を完成とする条件

1. **F1の疎通**：[既存のGemini課題](gemini-connectivity-task.md)どおり、管理画面から固定文の1回の通信を確認する。
2. **F1・F2の一例**：テキスト＋任意の画像による下書き、結果の確認・破棄・入力への反映、通常の投稿保存までを一つにつなぐ。キーなし・禁止・失敗・再送・結果不明を模擬試験とPlaywrightで確認する。
3. **F3の最小整理**：[リファクタリング計画](database-code-refactoring-plan.md)のユーザー・画像・復旧の境界を直す。新しいAI記録も退避・復元対象に含め、テスト用の別用途で確認する。
4. **引き渡し**：実行方法、変更する場所、確認手順、失敗時の対処、各教材で作る範囲を説明する。AI OFF・画像OFFでも通常の教材操作が成立することを確認する。

土台の完成条件に、カート・注文・評価計算・問題管理・会話履歴管理・スキル体系そのものの完成を加えない。これらは教材の作業。音声・決済・在庫・POS・複数店舗・ストリーミング・実課金集計・汎用インポートも追加しない。
