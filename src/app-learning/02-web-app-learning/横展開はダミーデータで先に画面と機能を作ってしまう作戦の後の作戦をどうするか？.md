## 3. 次段階B：基本範囲と確認記録を照合する

[配布範囲](../docs/feature-allocation.md)を基準に、各基本機能へ「仕様・コード・確認結果」の対応を付ける。新しい機能一覧を作るのではなく、現在の基本範囲が本当に閉じているかを一度確認する。

| 照合するもの | 見る点 | 扱い |

| キャスト評価 | 単一店舗、月次集計、配点変更、同点順位と、管理者限定という利用条件 | 計算の完成と、実運用のアクセス条件を分ける |
| 英語訓練 | クイズ・採点・会話・振り返り・履歴の基本体験が両版で成立するか | GAS側の詳細仕様とWeb側の簡略実装の差を分類する |
| ショップ・じゃんけん | Web側のカート／スキル・事前AIセリフと、GAS側の小さい範囲 | 両版を同じ機能に揃えない |

特に[英語GAS版README](../01-gas-app-learning/english-trainer/README.md)には選択式クイズ・自由記述の再判定・3会話シナリオが記載される。一方、[現在のWeb処理](english-trainer/src/main/java/com/example/webapptemplate/learning/LearningService.java)は固定3問、クイズ・会話・振り返り、直近20件の履歴表示という構成である。「クイズがある」という項目名の一致だけで同等完成と判定しない。

差は次の3種類に分類する。

1. 基本の利用目的・期待結果を満たすために不足しているもの：対象教材だけ補修する。
2. 技術や表示の違いで、同じ基本体験が成立しているもの：違いを説明して受け入れる。
3. 既存版の詳細機能・過去の拡張：自動的にWebの追加必須要件へ戻さない。範囲を変えるなら配布方針と個別仕様を揃える。

**照合の成果物は「基本機能／期待結果／証拠／不足／扱い」の短い表でよい。** 汎用的な品質管理システムを作らない。試験件数を増やすことも目的にしない。

## 4. 写真日記を「人に渡せる教材」にする

### 4.1 現在の公開条件を、実態どおりに説明する

経過では[写真日記の公開先](https://learning-photo-diary.onrender.com/diary)は実AI有効である。[現在のWebSecurity](photo-diary/src/main/java/com/example/webapptemplate/platform/internal/adapter/web/WebSecurity.java)は認証なしで全リクエストを許可し、CSRF対策を維持する実装になっている。ユーザー選択やCSRFを本人確認の代わりにはできない。

したがって、次に決めるのは「ログイン機能を全教材へ追加すること」ではなく、**この公開サービスを誰が、何のデータで、どこまで使うのか**である。

| 利用形態 | 提案する条件 | 完了判定 |
|---|---|---|
| 現在の架空データによる公開体験 | 教材用データだけを扱い、誰でも操作できる範囲と実AI利用を案内する | 公開対象・利用量の管理担当・停止方法が明確 |
| 提供者同席の初回試用 | 架空画像・架空名で1課題を行い、提供者がAI利用量と保存結果を確認する | 本人の試行・結果確認と支援量を記録できる |
| 本人専用の日記・店舗の実績管理 | 必要なアクセス制限を用途別に設計し、画面・更新・画像取得を確認する | 実データを入れる前に、対象外の人が閲覧・更新できない |

公開記録には、不特定の利用者を含むAI利用量の管理が十分かを示す証拠はない。[日記の生成処理](photo-diary/src/main/java/com/example/webapptemplate/diary/DiaryController.java)には同じセッションの要求ID再利用があるが、これはサービス全体の回数・費用制御とは別である。公開対象を広げる前に、現状の利用枠・利用量・運用担当を確認する。

Geminiのレート制限はプロジェクト単位で、キー単位ではない。キーを分けただけで教材ごとの枠が独立するとは扱わない。実際の利用枠はAI Studioで確認する。[Google公式：レート制限](https://ai.google.dev/gemini-api/docs/rate-limits)

現在のlive公開は既存の状態として引き継ぐ。本書を理由に勝手に停止・固定応答へ変更しない。運用上必要になった場合の退避手順として、経過にある「Renderで `APP_AI_MODE=demo` に変更してデプロイ」を案内へ残す。変更後は固定応答であることを利用者にも示す。なお、固定応答化はAI通信を止めるためのもので、データ閲覧・更新の制限にはならない。

### 4.2 最初の操作を1枚にまとめる

受け取り手向けの案内には、次だけを先に置く。

- 何ができるか：写真とタグから下書きを作り、自分で直し、保存して読み返す。
- 開く場所：対象版の入口URL。公開版とローカル版を混同しない。
- 使うもの：配布用の架空写真、架空名、短いメモ。私的な写真や実店舗情報を使わない。
- 操作：写真・タグ・メモ → 下書き → 本人の手直し → 保存 → 一覧・詳細。
- 期待結果：自分で直した本文と写真が、再読込後も残る。
- 待機・失敗時：起動待ちとAI生成待ちを区別し、入力保持・再試行・相談先を案内する。
- 対象外：保存後編集・削除、本人限定運用は、この公開教材の達成済み機能として案内しない。

READMEの先頭には教材固有の入口を置く。引き継いだtemplate資料は参照用として残し、「8080の投稿ノート例」と「8091の写真日記」を混同しない導線にする。共通機能を削除する作業には広げない。

### 4.3 URLを渡すことと、アプリ一式を配布することを分ける

最初の1人には、目的に合えば既存公開URLまたは提供者管理の環境で体験してもらう。自分の端末・アカウントへの導入を初回成功の必須条件にはしない。

一方、アプリ一式を本人へ渡す段階では、現在の `-SecretsFile ../template/.env` は提供者の開発環境用である。受け取り手がそのファイルを持つ前提にはできない。

配布する場合は、以下を追加で確かめる。

1. 受け取り手用の設定ひな形と、本人の接続値を設定する場所が分かる。
2. DB・画像・AIのうち必要なものだけを準備でき、秘密値や実データを配布物に含めない。
3. 提供者のローカルファイルに依存せず、別の作業場所で起動・保存・再読込まで再現できる。
4. 更新対象、元の版への戻し方、相談が必要な変更が分かる。

既存の派生アプリを全体再コピーする必要はない。検証済みの配布対象版を用意し、その再現性を確かめる。新しい教材を起こす際の「template丸ごとコピー」という原則は引き続き守る。

## 5. 今見えている運用上の問題は、小さく解く

### DB接続枠：1アプリずつ確認する運用を続ける

経過には、同時起動・試験でSession poolerの接続枠15件に達した実測がある。これは今回の環境の記録であり、Supabase全般の固定上限ではない。

[写真日記の設定](photo-diary/src/main/resources/application.properties)はHikariの最大接続数3、最小待機接続0。仮に同じプール設定の5プロセスが各3接続を使えば15となり、公開サービスや試験用プロセスの余地がない。この計算は容量を考える例であり、現在の実接続数の測定結果ではない。

当面は確認済みアプリを停止してから次を起動する。試験前に公開中サービス・template・残存プロセスも含めた使用状況を確認する。Supabase公式も、接続数は他の内部サービス分を残し、実際のピーク利用量を踏まえて管理するよう説明している。[Supabase公式：接続管理](https://supabase.com/docs/guides/database/connection-management)

同時利用の必要が出たときだけ、アプリ側プール・試験の実行数・接続方式・プランを検討する。Render側は各アプリ最大2接続・最小待機0で公開している。ショップ・じゃんけんにも同設定を適用済みで、5本の公開承認を無制限の同時起動・試験と解釈しない。接続方式の一括変更や有料化を前提にしない。

### 表示速度：起動待ち・通常表示・AI待ちを混ぜない

2026-10-28の日記18件の一覧ロードは2.228／1.408／1.311秒。評価・英語の測定値も[横展開記録](docs/rollout-status.md)にある。いずれも稼働中の表示であり、長時間休止後の起動時間、画像完了待ち、AI処理時間とは別である。

Render Freeは無通信15分で停止し、再アクセス時に起動する。無料稼働時間はワークスペース全体で月750時間であり、サービスごとに750時間あるわけではない。ファイルシステムも再起動等で変更が失われる。[Render公式：無料インスタンス](https://render.com/docs/free)

次の試用前は、対象端末での休止後の最初の表示と、稼働中の操作を別々に一度確認する。AIは5秒を超えた記録があり、現設定は20秒タイムアウト、受入試験の待機は30秒。試験の待機を延ばしたことを、AI自体の高速化と説明しない。

待ち時間が本人の目的を妨げたときに、案内・処理・プランを検討する。常時アクセスによる休止回避や、キャッシュ基盤の追加を次工程の必須にしない。

### 保存・再起動：不足する証拠だけ補う

再読込、再送、再デプロイを経た記録はある。実施済みの試験はそのまま使い、「アプリ再起動後も保存済み本文・画像が残る」「未保存の下書きが失われる条件を説明できる」など、明示的な証拠が不足する点だけを予行で補う。

DB・画像・アプリの版は別に扱う。コードを戻すだけでデータまで元に戻るとは案内しない。既存の保存方式と運用手順を使い、独自復旧画面・監査DB・AI永続台帳は追加しない。

## 6. 1人・1課題の試用を、次の実証にする

対象は「自分の記録を整理したい」「英語学習に使いたい」など、教材に対応する目的を持つ人。開始時の障壁は、何を入力するか、どうAIへ伝えるか、出力をどう判断するかである。提供者が環境・サンプル・期待結果を準備して支える。

[初回支援シート](../../../docs/templates/ai-pairing-session.md)に、目的・1課題・回数・時間・期間・質問窓口・不具合時の扱いを記入する。[1人・1課題の検証案](../docs/06_first-pairing-pilot.md)は進め方の参考にし、古い教材状況を最新Web版の未実装判定に使わない。受講順はGAS→Webを維持し、Web利用者として試す対象者と、GASから学ぶ初学者の段階を区別する。

### 写真日記の具体案

架空の公園写真と「夕方に散歩した」というメモを渡す。本人の課題は「写真とメモに合う短い日記を作り、自分の表現へ直して残す」とする。最初から写真3枚を必須にせず、本人が取り組みやすい量を選ぶ。

| 見ること | 確認方法 |
|---|---|
| 何をすればよいか分かるか | 最初の操作で止まった場所と、必要だった説明を記録 |
| AIへ希望を伝えられるか | メモ・タグ・表現の希望に本人の意図が入っているか |
| AIの結果を判断できるか | 写真・メモにない事実があれば本人が気づき、手直しできるか |
| 保存結果を確かめられるか | 本人が一覧・詳細を開き、手直しした本文と写真を確認 |
| 提供者が支援を閉じられるか | 依頼文・確認方法・戻し方を渡し、合意した枠で終了できるか |

初回成功は支援付きでよい。手助けが必要だった場面を記録し、自力でできたことと分ける。操作の迷いを観察するときは、先回りして全手順を教えず、止まった箇所を見て必要な支援をする。具体的な課題に取り組む様子から言葉・配置等の問題を見つける考え方は、GOV.UKのユーザビリティ試験の案内を参考にした。[GOV.UK：操作を観察する試験](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)

本人が希望すれば、後日もう1回同じ用途で使ったかを、合意した支援期間内で確認する。再利用や独力操作は初回成功の追加条件にしない。1人の結果から教育効果や事業性を一般化しない。

### 試用後の分岐

- 目的の操作ができ、支援も枠内で終了：同じ案内を次の人にも使える形に残す。
- 操作はできたが支援が長い：環境準備・説明・課題の大きさのどこを直すか決める。
- 保存等に不具合がある：教材の不具合として直し、本人の理解不足にしない。
- 本人に使う理由がない：機能追加を始めず、対象者・題材・課題選びへ戻る。
- 別機能を希望：新しい相談として扱い、今回の基本範囲へ自動追加しない。

## 7. その次：GASとの対応を固め、必要な教材へ提供方法を広げる

提供者の制作順はWeb→GAS、受講順はGAS→Webのまま。今回はWebの確認結果ができたので、ここからGASの基本範囲・入力例・期待結果・解説を揃えられる。試用協力者を待つ間も、対応表の整理は進めてよい。
