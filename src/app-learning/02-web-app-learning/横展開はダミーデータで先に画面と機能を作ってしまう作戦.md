# 横展開はダミーデータで先に画面と機能を作ってしまう作戦

更新日：2026-10-27

## 1. 絶対に守る出発点

**5アプリすべて、`template` の中身を丸ごとコピーしてから実装を始める。コピーした土台をそのまま活かし、各アプリに必要な箇所だけ追加・修正する。この手順は提案ではなく必須条件である。**

今日までに作った画面、機能、構造、設定、起動手順、テスト、修正の積み重ねを、横展開先へそのまま引き継ぐ。その成果を捨てて作り直さない。他のアプリとの歪な差を最小限にし、用途の違いが必要な箇所にだけ現れる状態を保つ。

作業順を次のとおり固定する。

**templateの中身を丸ごとコピー → コピー漏れがないことを確認 → コピーした土台の起動・既存機能を確認 → 必要箇所だけ追加・修正 → ダミーデータで画面と機能をつなぐ → 必要な実接続を確認。**

### 禁止する進め方

- 空のプロジェクトや別のひな形から作り始める。
- 必要そうなファイルだけ選んでコピーする。
- templateを参考に読むだけで、似たコード・画面・設定を別に作る。
- コピー前にアプリ固有の実装を進め、後から土台を寄せる。
- 写真日記などの派生アプリを、他の4アプリのコピー元にする。
- 「このアプリでは使わない」という判断で、コピー時に既存機能・テスト・資料を間引く。
- アプリごとに共通UI、CSS、起動方法、設定方法、保存方式、AI接続を作り直す。
- ダミーデータを口実に、別の使い捨て画面や別技術のアプリを作る。

**丸ごとコピーを確認できるまで、アプリ固有の追加・修正へ進まない。** 作業者やAIが独自判断でこの条件を緩めてはいけない。

## 3. 「丸ごとコピー」の実施と確認

### 3.1 土台を選別しない

templateを構成するソース、画面、静的資産、admin-pico、画像・サンプル、設定ひな形、ビルド定義、Maven Wrapper、起動・公開スクリプト、テスト、ドキュメント、`AGENTS.md`、隠しファイルを一式で引き継ぐ。`src` だけ、画面だけ、使用予定のモジュールだけを抜き出さない。

`.gitignore`・`.gitattributes`・`.dockerignore`・`.env.example`・`.mvn` など、通常のファイル一覧で見落としやすいものも確認する。コピーするファイルを用途で絞るために除外指定を増やしてはいけない。

秘密値のある `.env` 等、実利用データ、ローカルキャッシュ、生成物はアプリの土台と区別する。これらを複製しないための扱いを「必要なソースだけ選ぶ」根拠にしてはいけない。除外対象がある場合は具体的なパスと理由を記録し、ソース・設定ひな形・必要資産・テスト・資料に欠落がないことを確認する。既存の `.gitignore` だけをコピー対象の判定に使わず、未追跡の必要ファイルも確認する。

### 3.2 追加・修正より先に複製を完了する

1. コピー元templateの版を記録する。コミットIDに加え、未コミットの変更・未追跡の必要ファイルがあればその内容もコピー元の記録に含める。今日の変更を古いコミットで置き換えない。
2. コピー先の中身を確認する。空ならその直下へ一式をコピーする。既存の作業がある場合は差分を保全してから整合させ、上書きや削除で消さない。
3. 5アプリとも同じ基準のtemplateから丸ごとコピーする。コピー中にtemplateが変わった場合は、差分を確認して基準を揃える。
4. アプリ固有の編集前に、相対パス一覧とファイル内容を比較する。ファイル数だけで同一と判断しない。欠落・意図しない内容差・二重の `template/` 階層がないことを確認する。
5. コピー完了の記録を残した後、アプリ名・接続先・ポートなど、起動に必要な設定差分だけを入れる。秘密値は各環境で設定する。
6. コピーした起動スクリプト・ビルド・既存画面で土台を確認する。起動できない箇所は原因を直し、別のひな形への置換で回避しない。
7. ここまで確認してから、教材固有の画面・データ・処理を追加する。

初回コピーとアプリ固有の変更は、差分で区別できる単位に分ける。コピー済みという宣言だけで済ませず、照合結果を残す。

### 3.3 コピー完了の記録

各アプリのREADMEに、少なくとも次を記録する。

```text
コピー元：02-web-app-learning/template
基準コミット／未コミット差分：
コピー日時：
コピー先：
ファイル一覧・内容の照合結果：
ローカル専用ファイル等の除外パスと理由（なければ「なし」）：
起動に必要な設定変更：
既存機能の確認結果／未確認事項：
アプリ固有に追加・修正した箇所と理由：
取り込んだ共通修正の版：
```

## 4. 土台を維持し、必要箇所だけ追加・修正する

### そのまま引き継ぐもの

| 対象 | 守ること |
|---|---|
| 技術・構造 | Spring Boot・Thymeleaf、既存の機能単位のフォルダー構成と処理の分担を使う |
| UI | Pico CSS・admin-pico・共通UI・画面組立てを使い、フォーム・一覧・詳細・メッセージの操作感を揃える |
| 保存 | JDBC・Flyway・既存のトランザクション処理を使う。適用済みマイグレーションは書き換えない |
| 画像 | 既存の検証・保存・表示・参照保護・失敗時の補償を使う |
| AI | 既存の許可設定・モデル制限・呼出し窓口・結果確認の流れを使う |
| 品質 | 入力検証・CSRF・入力保持・二重送信対策・競合対策を維持する |
| 開発・確認 | 起動スクリプト、Maven Wrapper、既存テスト、Playwright、説明資料を引き継ぐ |

アプリ名のためだけにJavaパッケージや全ファイル名を一括改名しない。別のCSS基盤・設定体系・独自起動スクリプトへ置き換えない。まず表示名と必要な設定値を変更し、機能上必要な差分に絞る。

### アプリ側で追加・修正するもの

- アプリ名、見出し、ナビゲーション、教材の説明文。
- 教材固有の入力項目、一覧・詳細の表示、必要な画面と導線。
- 日記・問題・回答・注文・実績・対戦等のデータと業務ルール。
- ダミーデータ、固定のAI応答、確認シナリオと期待結果。
- アプリ別のDB保存先・画像保存先・接続設定と、それに必要な最小限の変更。

コピーした既存機能は土台として保持する。教材の通常メニューに出す機能は[配布範囲](../docs/feature-allocation.md)に合わせるが、非表示とコード削除を混同しない。既存の投稿例・CSV・ゲーム例があることを理由に、そのすべてを各教材の必須機能へ加えることもしない。

### 共通修正を各アプリでばらばらにしない

共通UIや保存処理などの不具合を見つけたら、templateにも同じ修正を反映し、該当する5アプリへ同じ差分を取り込む。各アプリへ別々の回避策を積まない。共通修正の取り込みではアプリ全体を再コピーして固有部分を上書きせず、変更箇所を比較して反映し、取り込んだ版を記録する。

共通化のための新しいライブラリ・自動同期基盤・大規模リファクタリングを、画面制作の前提にしない。各変更を「教材固有の必要差分」か「templateへ戻す共通修正」かで説明できるようにする。

## 5. ダミーデータで画面と機能を先につなぐ

**コピーした実アプリの中で、架空のデータと固定応答を使い、入力から結果確認まで操作できる状態を先に作る。** 見た目だけの画面で終わらせず、後の実接続でも同じ画面と業務処理を使う。

| 対象 | ダミー段階での扱い |
|---|---|
| 人名・商品・問題・写真・実績・履歴 | 架空の固定データを用意し、期待結果を決める |
| AI応答 | 成功・失敗・待機などを固定応答で確認する。画面にデモであることを示す |
| 入力・勝敗・得点・合計・順位 | 実際の入力検証と業務処理で計算する |
| 保存・再読込 | コピーした既存DB処理を使い、開発用の保存先へ架空データを保存する |
| 画像 | 同梱サンプルで画面を先行する。実アップロードの確認は別に記録する |

ダミーデータはDBを作り直す指示ではない。現templateが使うDBを維持し、アプリごとに開発用の保存先を分ける。DB未準備でも画面の表示や通常計算は先行できるが、保存未確認なら「画面プレビュー」と記録する。DBなしの独立アプリを別途作ることはしない。

AIの模擬応答は既存の呼出し境界で切り替えるための最小限の追加とする。既存の許可・入力検証・結果利用を通し、画面にダミー専用の業務処理を複製しない。切替設定・コマンドは実装して確認後にREADMEへ記載する。本書では未実装のデモ起動手順を実行可能と扱わない。

実AIへ切り替えて失敗した場合、固定応答で成功したように見せない。ショップ・キャスト評価はアプリ内AIを使わず、AIキーの設定を起動・操作の前提にしない。

### ダミーデータの確認例

| アプリ | 用意する例 | 確認する操作と結果 |
|---|---|---|
| skill-janken-game | 仲間・スキル・勝敗3種・採用済みセリフ・定型文 | 選択→対戦→得点→履歴。セリフが変わっても勝敗・得点は変わらない |
| photo-diary | 架空写真・タグ・固定の下書き・空の一覧 | 写真とタグ→模擬下書き→手直し→保存→一覧・詳細。手直しが再読込後も残る |
| online-shop | 商品・数量・価格変更・販売停止・確定注文 | カート→確認→確定→履歴・取消。500円×2＋800円×1＝1,800円。後の価格変更で過去明細を変えない |
| english-trainer | サンプル問題・正答・誤答・固定の採点・会話 | 回答→採点→履歴、会話→振り返り。失敗応答を採点済みにしない |
| cast-evaluation | 架空メンバー・2か月の実績・配点・同点 | 実績登録・編集→対象月→集計・順位。月や配点を変えた結果を期待値と比較する |

通常・0件・長文・入力不備・失敗を確認できる小さな件数を使う。サンプル投入は既存のシード処理を土台に必要箇所だけ変更し、アプリ別の投入先を確認する。通常起動で勝手にデータを初期化しない。既存の `seed-reset` は開発スキーマの全投稿を置換するため、利用者データを残す投入方法として使わない。

## 6. 各アプリで完成させる基本範囲

| アプリ | Web版で先に作る画面と機能 | ダミー確認後の実接続 |
|---|---|---|
| skill-janken-game | 仲間・スキル・手の選択、対戦結果・得点・履歴、セリフの事前生成・確認・採用・保存 | 事前生成だけ実AIへ接続。対戦中は保存済み文または定型文を使う |
| photo-diary | 写真・タグ、下書き生成、本人の手直し・保存、一覧・詳細 | 必要な画像保存・読取と、画像を含むAI下書き。複数画像は教材の既存仕様に合わせる |
| online-shop | 商品一覧・詳細、画面内カート、注文確認・確定、注文・明細の確認、注文全体取消 | 保存の整合性、確定価格、販売状態の再確認、二重注文防止。AI不要 |
| english-trainer | クイズ・回答・採点、テキスト会話、振り返り、学習履歴 | 必要なAI採点・会話・振り返り、回答時の問題と履歴の整合性 |
| cast-evaluation | メンバー管理、実績登録・編集、評価ルール、月次集計・順位 | 保存、集計、同点、対象月の境界。AI不要 |

写真日記・キャスト評価・英語訓練はGASと同じ基本機能で完成とする。じゃんけんはWebでスキルとAIセリフ事前作成、ショップはWebでカート経由の注文を扱う。提供者の制作順はWeb→GAS、受講順はGAS→Webとする。

写真日記の保存後編集・削除、英語の問題管理画面・音声、ショップの決済・配送・在庫、キャスト評価の複数店舗、じゃんけんの合成等は、この横展開の必須作業へ加えない。完成範囲は[機能分担](../docs/feature-allocation.md)に従う。

## 7. 現在のtemplateを基準にする

[教育用スターターの最小構成](template/docs/educational-baseline.md)と[現在のコード構成](template/docs/architecture.md)を基準にする。古い計画の未完了項目を理由に、今日の土台を以前の構成へ戻さない。

- Gemini疎通と下書き生成は既存機能として再利用する。「AI通信が未実装」という旧説明に基づいて一式を作り直さない。
- AI下書きの状態はブラウザーセッションの直近1件を扱う既存方式を使う。AI要求の永続台帳・期限切れ定期処理・再起動後復元を共通要件へ戻さない。
- Basic認証・独自バックアップ復元・監査DB書込みは現templateから外されている。横展開の前提として再追加しない。
- 認証はなく、ユーザー選択は本人確認ではない。架空データでの教材確認と、管理者限定・個人利用の実運用条件を区別する。実利用でアクセス制限が必要なら、対象アプリの配布前の課題として扱い、達成済みにしない。
- 現行の共通仕様は[教材から決める共通機能](template/docs/shared-foundation-requirements.md)。旧F1〜F3や復旧基盤の完成待ちを、5アプリの画面制作の開始条件にしない。

## 8. 実行順と完了条件

| 段階 | 作業 | 完了条件 |
|---|---|---|
| 1. コピー | 同じ基準のtemplateの中身を5アプリへ丸ごとコピー | 固有編集前のファイル一覧・内容照合が完了し、コピー元と結果が記録されている |
| 2. 土台確認 | 必要な環境設定だけ変更し、コピーしたままの起動と既存機能を確認 | 土台が使える。未確認の接続や機能を明記している |
| 3. ダミー実装 | 必要箇所だけ追加・修正し、各アプリの主要操作をつなぐ | 架空データで入力・計算・結果・保存・再読込を確認できる |
| 4. 差分確認 | templateと他アプリからの不要な乖離を確認 | 固有差分の理由が説明でき、共通修正はtemplateと対象アプリへ反映されている |
| 5. 実接続 | 必要なAI・画像の接続と保存を確認 | 同じ画面・業務処理で正常・失敗時の操作を確認している |
| 6. 引き渡し | 対象版・操作手順・確認結果・残課題をまとめる | ダミー確認済み・実接続済み・公開受入済みを区別して説明できる |

最初の5アプリへのコピーを揃えた後、固有実装は写真日記→キャスト評価→英語訓練→ショップ→じゃんけんの順を目安に進める。順番を調整しても、各アプリがtemplateの丸ごとコピーから始まる条件は変えない。共通修正は後続のアプリにも取り込み、先行アプリ独自の土台を増やさない。

### 各アプリで残す確認記録

- コピーの照合結果、起動、引き継いだ既存機能の確認。
- 教材固有の最短操作、通常計算、保存と再読込。
- 空表示、入力不備、処理中、失敗、再試行、二重押下。
- PC幅・スマホ幅での画面、画像、一覧・詳細の操作。
- templateとの差分と理由、共通修正の反映先・版。
- DB・画像・AIのうち、実接続／ダミー／未確認の区別。

既存の `npm run test:unit`、`run-local.ps1 -Action test`、`npm run test:e2e` を土台とし、コピー先で設定と実行結果を確認して使う。教材固有の処理に必要な確認を追加し、既存テストを理由なく削除しない。テストの成功だけで実AI・公開環境・実端末も確認済みとはしない。
