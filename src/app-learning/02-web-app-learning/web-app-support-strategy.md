# Spring Boot・Thymeleaf・Render・SupabaseによるWebアプリ支援戦略

> 2026-10-28 方針更新：受講者のコード質問・改造依頼はDevin、プログラムからのAI呼び出しはOpenAI API、業務自動化の質問・作業はCursorとする。教材アプリのGemini採用は廃止。アカウント準備と接続案内はこの区分に合わせ、移行・実通信・公開先の確認状況を分けて記録する。 判断の正本は[AIの役割分担（ADR 0003）](../../../docs/adr/0003-ai-service-roles.md)。

## 制作順と受講順

受講者は **01 GAS → 02 Web**、提供者のコード・解説作成は **02 Web → 01 GAS** の順とする。提供者はWeb側のローカル起動・PostgreSQL・自動テストで動作を先に確認し、仕様・サンプル・期待結果・解説をGAS教材へ展開する。GAS側の保存・権限・公開等は別途実装・検証する。横断設計の正本は[app-learning/docs](../docs/README.md)。

## 採用決定

2026-10-27、Webアプリの標準スタックを **Spring Boot＋Thymeleaf＋Render＋Supabase** に統一する。Next.js＋Vercel案は廃止する。判断理由と適用範囲は[ADR](../../../docs/adr/0001-web-app-stack.md)を参照。

この文書は採用済みの支援・構成方針。アプリの実装、クラウド環境の作成、公開、実環境受入の完了を示すものではない。以前の会話メモにあった他サービスの比較、料金、対応状況、コマンドは採用手順として引き継がない。

## 誰の、どんなゴールを支援するか

対象は、**自分用・業務用のアプリを作って使いたい非エンジニア**。本人が困っている作業を小さなアプリで解決し、必要な変更をAIへ依頼して、結果を確認しながら使い続けられることを目指す。

Java資格の取得やプログラマーへの転職を、この取り組みの前提にしない。資格・実務学習側では同じJava・SQLの知識や実装例を利用できるが、本人のゴールと習得評価は分ける。

## スタートの支援

初回成功は、自分の用途に関係する1課題をAIと進め、本人が結果を確かめること。以下は提供者が準備・支援する項目であり、本人が全技術を習得する課程ではない。[初回支援シート](../../../docs/templates/ai-pairing-session.md)で対象と支援枠を決め、依頼・確認・復旧の材料を渡して終了する。継続改修や運用代行を無期限に含めない。

1. 現在の作業、入力、期待する結果を聞き、最初に使う1つの操作へ範囲を絞る。
2. サンプルデータと動作確認済みのひな形を準備し、本人が画面と保存結果を体験できるようにする。
3. Javaの実行環境、DB接続、設定、Renderでの公開は手順と伴走で支える。
4. 本人用の項目やルールを一つ変更し、変更前の予想と実際の結果を比べる。
5. 次回の変更、更新、復旧、相談に必要な操作と記録を引き渡す。

導入手順は今後実装とともに検証する。GitHub連携やDockerの準備を最初から本人だけに任せず、提供者が支援する範囲を示す。すべての技術を理解してから使い始める構成にはしない。

## 採用スタックと責務

| 領域 | 採用技術・方針 |
|---|---|
| 業務処理・HTTP | Java／Spring Boot／Spring MVC |
| 画面 | ThymeleafでHTMLを生成。CSSと必要な範囲のJavaScript |
| 実行・公開 | Render。Dockerによるデプロイを標準経路として整備 |
| 永続データ | SupabaseのPostgreSQL |
| DBアクセス | サーバー側からJDBC／Spring JDBC等で接続。SQL実習を残し、JPAは必要に応じて扱う |
| 画像・添付 | 必要な教材でSupabase Storageを利用 |
| 認証・認可 | 教材の利用者・公開範囲に応じて設計。Supabase Auth等の採否は個別に決める |

```text
ブラウザ（HTML / CSS / 必要なJavaScript）
  → Render上のSpring Boot
      ├─ Spring MVC・Thymeleaf：入力受付と画面
      ├─ 業務処理・認可・入力検証
      ├─ DBアクセス → Supabase PostgreSQL
      └─ 必要時のみ → Storage / AI API
```

Spring MVCとThymeleafによるHTML表示は[Spring公式ガイド](https://spring.io/guides/gs/serving-web-content/)を参照する。RenderはDockerfileからのビルドと、レジストリ上のイメージの実行を案内している。本教材では対象アプリのDockerfileを使う経路を整える。[Render公式](https://render.com/docs/docker)

SupabaseにはSpring BootからPostgreSQLへ接続する公式ガイドがある。接続先・方式は実環境とドライバーに合わせて選び、秘密情報はサーバー側で管理する。[Supabase公式](https://supabase.com/docs/guides/getting-started/quickstarts/spring-boot)

公式情報の確認日：2026-10-27。Java・Spring Boot等の版、プラン、接続方式、コマンドは実装時に固定し、実際に検証したものを導入手順へ記載する。

## AIでどう横展開するか

最初に動いたアプリの仕様・コード・入力例・確認手順を土台に、AIへ変更を依頼する。

| 本人の要望 | 再利用するもの | AIの支援と本人の確認 |
|---|---|---|
| 自分の項目・分類に合わせたい | 入力画面、保存、一覧の仕組み | AIが変更箇所と影響を提示し、本人がサンプルの保存・表示を確認 |
| 集計や計算を変えたい | データモデル、業務処理、期待値の例 | AIがSQLや処理・テストを変更し、本人が計算例と結果を照合 |
| 別の身近な業務にも使いたい | ひな形、導入手順、依頼と検証の進め方 | 対象者・データ・ルール・公開範囲を改めて定義し、必要な部分だけ応用 |

横展開はアプリの複製だけで完了しない。別用途のデータの意味と権限を確認し、本人の目的で使えるかを確かめる。利用者の応用と、正式教材を追加する判断も分ける。

## GAS教材・資格学習との関係

- [GASアプリ集](../01-gas-app-learning/README.md)の既存5題材は維持し、発展版の構成を本スタックに揃える。同じ題材では業務要件・入力例・期待結果を共通にする。
- 最初の1題材から検証し、5題材を一括移植しない。添付の議論にあるonline-shop先行は候補として扱い、対象の実装着手は個別に範囲・受入条件を決める。
- [Java・Oracle学習戦略](<../../java-career-learning/java-career-learning-strategy.md>)ではJava・SQLからSpring Bootへの接続に利用する。Oracle固有のSQL・管理操作はOracle環境で別途実習する。
- Web教材の公開先はRender、実行DBはSupabaseのPostgreSQL。Linux・AWSは資格／実務学習側の発展テーマとして残す。
- GAS、Webアプリ実利用、資格／実務学習、事務処理効率化の対象者・スタート支援・成功条件は統一しない。

## 実装時に確認すること

- 元の利用者・公開範囲を維持し、画面だけでなくサーバーで操作権限を検証する。
- DB接続ロールとスキーマ公開範囲を設計する。RLSを使う場合も、その接続ロールで制御が働くか確認する。Supabaseの所有者・特権ロール等ではRLSを迂回し得るため、採用しただけで利用者間の分離が完成したと扱わない。[SupabaseのRLS説明](https://supabase.com/docs/guides/database/postgres/row-level-security)
- DBパスワード、Storageの秘密キー、AI APIキーをブラウザ・ログ・ソースへ出さない。AIに送る情報と費用の扱いを決める。
- 画像は必要な場合にStorageへ保存し、閲覧権限、DBレコードとの対応、失敗時の回復を検証する。
- 注文や実績等の保存、重複送信、同時更新、トランザクション、バックアップ・復旧を対象の仕様に沿って確認する。
- 起動時間、応答、メモリ、DB接続数、停止・再開、データ保持、利用料金を実際のプランで確認する。無料枠で継続運用できると一律に約束しない。

ローカルテスト、RenderとSupabaseでの実環境受入、本人の操作・変更確認を分けて記録する。本人の用途で使えたか、変更結果を確認できるか、問題時に復旧・相談できるかを支援の成果とする。
