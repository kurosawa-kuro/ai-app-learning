## 移行前の確認と退避

公開5スキーマの表・制約・索引・Flyway履歴を読み取り照合。`pg_dump --no-owner --no-privileges` で対象だけを退避した。SQL・接続値・データをGitへ入れていない。

作業用ファイルは `template/.local/db-redesign-before.sql`、`db-redesign-catalog-before.json`。既存のID・値・件数は表ごとの全旧列ハッシュで照合する。Storageオブジェクト自体は変更しない。

公開スキーマのコピーを `*_redesign_check` の5スキーマに作り、追加DDLを適用。日記11・ショップ10・英語8・評価10・じゃんけん9表（Flyway表を含む）の旧列・行数が一致した。英語の新しい問題IDのみ既知の問題文から補完し、過去の参考回答を捏造していない。制約違反13ケースが23514で拒否され、検証書込みはロールバックした。

## SQLの比較

同じコピーDBでEXPLAIN ANALYZE / BUFFERSを実行。ショップの旧・新SQLの結果一致を確認。実データ1注文では0.317→0.188ms。検証用に1000注文・3000明細をトランザクション内で追加した比較では7.452→1.344ms、検証後ロールバック。新SQLは先に最新30注文へ限定する。商品照会は商品数N回から1回へ削減。

日記1.767ms、英語0.166ms、評価0.157ms、じゃんけん0.143msは現在の少量データでの単発値。既存索引を維持し、根拠のない索引や集計キャッシュを追加しなかった。これらはHTTP全体の高速化を示す値ではない。

ローカル画面受入後、Gitコミットを固定し、既存Renderの5サービスへ1本ずつ反映。新規サービスは作らない。今回のDDLは追加中心で旧コードの列参照を壊さない。問題時は対象サービスを停止し、旧コミットへ戻す。追加DDLを無条件にDROPしない。DB復元が必要な場合は退避を別スキーマへ読み、切替後の新規データの有無を照合してから対象スキーマだけを復旧する。今回の作業手順であり、アプリに復元UIは追加しない。
