# 応用パターン資料：既存教材から学べる設計の型

[全体案内](../../01-gas-app-learning/README.md) · [出典・編集対応表](00_source-map.md)

状態：**参照資料・未採用の応用例**。新規教材、実装タスク、業界向け完成仕様ではない。既存5教材のどの型を応用でき、何を追加で設計する必要があるかを整理する。

## アプリから学ぶ基本の型

基本 4 アプリ（日記・英語訓練・EC・じゃんけん）に、実績集計・評価ルールを扱うキャスト評価を加えて整理する。

| プロジェクト | 学ぶ構造・処理 | 応用先の例 |
|---|---|---|
| photo-diary | 記録の登録・一覧・絞り込み、画像添付、タグ、AI 下書き | 作業日報、点検記録、問い合わせ受付、記事管理 |
| english-trainer | 出題・回答・評価、対話、履歴、教材の版管理 | 社内研修、面接練習、理解度確認、文章添削 |
| online-shop | マスターと取引、注文と明細、確定時点の情報保存 | 受発注、見積、経費申請、貸出管理 |
| skill-janken-game | 選択と条件判定、行動履歴、状態復元、更新競合の検出 | 申請・承認、進捗管理、ポイント管理、操作履歴 |
| cast-evaluation | 日次実績、設定による計算、月次集計、順位 | 営業実績、活動実績、ルールに基づく評価一覧 |

共通して学ぶのは、対象の登録・表示、1 対多と多対多、入力検証、状態変更、履歴保存、ファイルや外部サービスとの関連付け。アプリ全体を合体するより、必要な処理とデータ構造を取り出して応用する。

| 組み合わせ例 | 応用する型 | 別途設計すること |
|---|---|---|
| 点検システム | 写真日記の画像付き記録＋英語訓練の評価 | 点検基準、判定、訂正のルール |
| 経費精算 | EC の申請・明細＋じゃんけんの状態変更・履歴＋写真日記の添付 | 承認経路、権限、締め処理 |
| 実績ダッシュボード | キャスト評価の期間集計＋日記の記録・絞り込み | 指標定義、対象期間、集計結果の公開範囲 |

日記・英語訓練・じゃんけんの README には、再送制御・途中失敗への対処・更新競合や AI 重複実行への対処が記載されている。再利用する際は対象の仕様・コード・検証記録を確認する。設計案や過去の試験結果を、そのまま現在の動作保証にはしない。

業務アプリへ広げる場合は、認証・認可、訂正・削除・承認、決済・通知・外部同期、データ量・同時更新への対応を用途ごとに追加する。たとえば写真日記は保存後の編集・削除が対象外であり、汎用的な更新機能まで備えるわけではない。

## 追加するとカバー範囲が広がる型

この節と続く銀行・転職・人材の説明は、既存アプリの応用範囲を考えるための参照資料として残す。新規教材を追加する計画ではない。題材は既存5つに固定し、当面は同じ題材の理解・改修・技術基盤の違いを深める。

ここで扱うのはシステム設計の型。各業界の法令・制度・認証要件を網羅したものではない。また、型を学習用に再現できることと、本番サービスとして必要な性能・可用性・安全性を満たすことは別に評価する。

| 追加の型 | 代表的なシステム | 基本4アプリから追加で必要になる中心概念 |
|---|---|---|
| 台帳・残高・照合 | 銀行、ウォレット、会計、ポイント口座 | 複式の記録、整合する入出金、取消仕訳、利用可能残高、外部記録との照合 |
| マッチング・選考 | 転職、人材紹介、業務委託、取引先紹介 | 双方の条件、候補の順位付け、応募・推薦、段階別の進行、情報開示の範囲 |
| 予約・在庫・資源割当 | 宿泊、診療予約、座席、設備貸出、倉庫 | 有限の枠や数量、時間帯の重複、仮押さえ、期限切れ、取消による解放 |
| 組織・権限・承認 | 社内申請、グループウェア、企業向けSaaS | 組織階層、役割、企業別データ分離、代理承認、差戻し、承認ルート |
| 定期契約・利用量 | サブスクリプション、会員サービス、従量課金 | 契約期間、プラン変更、利用権、利用量集計、更新・解約、料金の適用期間 |
| 多人数のリアルタイム共有 | チャット、共同編集、対戦、ライブ状況表示 | イベント配信、接続・再接続、順序、同時編集の競合、在席状態 |
| 検索・推薦・公開配信 | 求人検索、商品検索、ナレッジ、SNS | 検索索引、関連度、推薦、公開範囲、投稿審査、フィード、検索エンジン向け公開ページ |
| 非同期処理・外部連携 | 一括取込、動画変換、メール配信、データ同期 | ジョブ、キュー、再試行、進捗、定期実行、Webhook、外部との不整合の検出と回復 |
| 集計・分析 | 売上分析、経営指標、利用分析 | 時系列集計、指標定義、集計用データ、遅れて届くデータ、過去値の再計算 |
| 地理・経路・現場連携 | 配送、配車、訪問業務、設備監視 | 位置と範囲、経路、移動時間、端末からの継続データ、圏外時の保存・再同期 |

特に大きく抜けているのは、**「量を矛盾なく移す」「有限資源を取り合う」「条件の合う相手を探す」「複数人・組織で権限を分けて進める」**という4つ。既存アプリにも履歴や競合対策はあるが、これらの業務ルールまで備わっているわけではない。

## 銀行系で加わるもの

銀行のWeb画面にある一覧・詳細・入力・履歴は、基本アプリの型を応用できる。追加の学習価値が大きいのは、口座間の価値の移動と、その記録の整合性。

- **台帳と残高**：残高だけを書き換えず、何によって増減したかを記録する。複式の台帳では、1取引内の借方・貸方を一致させる。
- **一体として成立する振替**：A口座の減額だけが保存され、B口座の増額が失われる状態を防ぐ。同じ送金要求を再送しても二重に移動させない。
- **取消・訂正**：確定済みの記録を消して帳尻を合わせず、元の取引を参照する取消・訂正の記録を追加する。
- **確定と保留の区別**：帳簿上の残高、保留中の金額、実際に利用可能な金額を区別する。
- **照合**：内部台帳と外部から得た取引記録を突き合わせ、不一致を検出して調査・修正する。

`skill-janken-game`の行動履歴と二重実行防止、`online-shop`の取引・明細構造は出発点になる。ただし、ゲームの得点加算だけで複数口座の資金移動の整合性を満たせるわけではない。

学習用には「架空の口座間でポイントを振り替えるミニ台帳」が適している。実際の銀行システム全体には、このほか本人確認、不正検知、外部決済接続、運用統制など別の設計領域がある。

## 転職・人材系で加わるもの

転職・人材系は、**基本4アプリを組み合わせる効果が大きく、マッチングと複数当事者の業務を追加で学べる題材**。

| 機能 | 既存の型を応用できる部分 | 追加で設計する部分 |
|---|---|---|
| 求職者・求人の登録 | 日記の登録・一覧・絞り込み、タグや多対多の関係 | 求職者・企業・求人・スキル・希望条件のモデル |
| 履歴書・職務経歴書 | 日記の添付管理の考え方 | PDF等の取扱い、差替え・版、企業別の閲覧権限、開示の同意 |
| 求人への応募・企業への推薦 | ECの取引構造、じゃんけんの状態変更と履歴 | 応募・推薦の違い、重複応募、辞退、選考段階、担当者 |
| 条件のマッチング | タグによる絞り込み、英語訓練の評価構造 | 双方の必須条件と希望条件、順位付け、判定理由 |
| 面接練習・文章支援 | 英語訓練の対話・フィードバック、日記のAI下書き | 職種別のシナリオ、職務経歴書の改善支援、人による確認 |
| 面接日程 | 既存の一覧・入力画面 | 候補日時、複数参加者の空き、確定・変更、通知 |
| 人材紹介会社の案件管理 | 履歴、管理画面、取引情報 | 求職者・企業・担当者の三者関係、紹介経路、成約の記録 |

基本モデルの例は、`求職者`、`企業`、`求人`、`スキル`、`求職者スキル`、`求人スキル`、`応募`、`選考履歴`、`面接予定`。人材紹介に広げる場合は、`紹介会社`、`担当者`、`推薦`などを追加する。

「求職者と求人が多対多」だけでは不足する。両者を結ぶ応募には、応募日時、経路、現在の段階、辞退などの独自情報があるため、応募自体を業務上の対象として扱う。選考段階の履歴も別に残す。

マッチングは、まず勤務地・雇用形態・必須スキル等の明示的な条件で実装できる。推薦順位やAIによる補助はその後に追加する。AIの文章評価機能をそのまま採否判定に転用する設計にはせず、支援機能と採用判断の責務を分ける。
