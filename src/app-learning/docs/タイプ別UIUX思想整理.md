## 1. 設計の起点：使う体験と、仕組みを学ぶ体験

まず一つのアプリで本人の目的を達成できるようにする。その後、関心のある小さな変更をAIへ依頼し、結果を確かめる。アプリの初期画面へDB構造・接続設定・技術解説を並べる必要はない。仕組みの説明は教材・解説・必要な設定画面で行う。

| 教材 | 対象者と本人の目的 | 最初の障壁と支援 | UIで確かめる成功 | AIと試せる小さな変更例 |
|---|---|---|---|---|
| じゃんけん | 遊びやプログラミングに関心のある子供。大人が伴走する | ルールや設定を読む前に一回遊べるサンプルを用意 | 手を選び、結果と得点が分かり、もう一度遊べる | 得点や表示文言を変え、期待結果と比べる |
| 写真日記 | 写真から日記を残したい人 | 写真・短いメモ・タグの例を用意し、文章の書き出しを助ける | 自分で確かめた文章を保存し、写真と一緒に読み返せる | 文体や案内文を変え、保存前後を確認する |
| 英語訓練 | 英語の回答・会話を練習したい個人 | 一問または短い会話から始め、回答例や操作を必要時に支援 | 自分の回答とフィードバックを見比べ、履歴で振り返れる | 問題文や採点基準を変え、回答と評価の対応を確認する |
| キャスト評価 | 店長など、実績と配点の関係を確かめたい店舗運営者 | 架空メンバー・実績・期待する点数を用意 | 誰のいつの実績か分かり、月次の点数・順位の根拠を追える | 既存項目の配点を変え、サンプルの再計算を比較する |
| ショップ | 商品と注文の仕組みを学びたい人 | 架空商品と計算しやすい数量・価格を用意 | 注文内容を確認して確定し、保存された明細を読める | 商品や表示を変え、注文時の価格が記録に残ることを確認する |

変更例は学習課題であり、すべてが現行の設定画面で操作できるという意味ではない。対象者は[学習設計](02_learning-design.md)の仮説を起点に、本人の関心と困りごとで選ぶ。全5教材の修了、独力での改修、別用途への応用は初回の必須条件にしない。

アプリで保存できたことと、本人が仕組みを理解したことは別に確かめる。提供者の支援付きでも「依頼→試行→結果確認」を一課題で経験できれば、初回の成功とする。

## 2. タイプ比較：アプリ名ではなく、作業段階で分類する

一つのアプリに複数の型があってよい。写真日記は作成時と閲覧時、キャスト評価は実績入力時と月次確認時で、主役も適切な密度も変わる。

| 型 | 主役 | 操作の流れ | 必要な場面で見せるもの | 後段・別の場所へ置くもの | 成功の見方 |
|---|---|---|---|---|---|
| A 遊ぶ・繰り返す | 自分の選択と結果 | 選ぶ→対戦→結果→もう一度 | 手、選択状態、決定、勝敗・得点、再開 | 長い履歴、セリフ制作、接続設定 | 一回の結果と次の操作が迷わず分かる |
| B 書く・残す | 本人の文章・写真・記録内容 | 素材→下書き→手直し→保存→読む | 対象者・日付、入力、下書き、保存、保存結果 | タグ管理、AI設定、過去の全記録 | 本人が確かめた内容を意図どおり残せる |
| C 答える・対話する | 問題・自分の回答・フィードバック | 問題／会話→入力→送信→評価／応答→振り返り | 問題、回答欄、送信、処理状態、回答と応答の対応 | 問題管理、過去履歴の全展開、接続情報 | 答える前に正解を見せず、結果から次へ進める |
| D 業務を入力する | 対象者・日付・実績 | 対象確認→入力→保存→結果確認 | 単位、必須項目、対象、入力エラー、保存範囲 | 低頻度のメンバー・配点変更 | 別人・別日への誤登録や二重登録を防げる |
| E 比べる・根拠を確かめる | 月次集計・順位と計算根拠 | 期間選択→比較→実績・配点を確認 | 対象月、数値の単位、順位、集計条件 | 長い設定フォーム | 数字が何を表し、なぜそうなったか分かる |
| F 選ぶ・注文を確定する | 商品・数量・価格・確定内容 | 選ぶ→内容確認→確定→明細確認 | 注文者、数量、単価・合計、修正、確定結果 | 管理機能、注文に不要な説明 | 確認した内容と保存された注文が一致する |
| G 探す・読む | 写真、本文、商品、過去の記録 | 一覧→必要なら絞る→詳細→戻る | 内容、対象範囲、必要な条件、戻る入口 | 全文の一斉展開、診断情報 | 読みたい対象へ到達し、元の文脈へ戻れる |

| 教材 | 主な型 | 優先する体験 | 共通レイアウトだけでは不足する点 |
|---|---|---|---|
| じゃんけん | A、履歴G、セリフ制作B | 選択と結果の分かりやすさ、反復のしやすさ | 管理フォームが対戦より目立つと遊びを妨げる |
| 写真日記 | B、一覧・詳細G | 本人の言葉を残すこと、写真と文章の読みやすさ | AI生成ボタンやタグ管理で本文を圧迫しない |
| 英語訓練 | C、履歴G | 回答への集中、応答からの振り返り | クイズ・会話・振り返りを一つの意味不明な送信欄にしない |
| キャスト評価 | D・E、実績一覧G | 正確な入力と数値の比較 | 比較に必要な表を、見た目だけでカードへ分解しない |
| ショップ | F、商品・注文履歴G | 選択中と確定済みの違い、確認して注文する安心感 | カート追加や数量変更を注文完了の見た目にしない |

管理は独立した6番目の教材ではなく、各教材を支える作業。同じ画面内の区画・折りたたみ・別ページのどれにするかは、頻度と入力の長さで決める。

## 3. 教材別の思想と操作の流れ

### 3.1 じゃんけん：説明より先に一回遊べる

GASは「手を選ぶ→対戦→勝敗・得点→履歴」、Webはその前に仲間・スキルの選択が加わる。選択状態を絵と名前で示し、決定前に何を選んだか確認できるようにする。結果では勝敗、今回の得点、スキルの効果を区別する。

- 主役は対戦。Webのセリフ生成・手直し・採用は制作側の作業として区画を分け、遊ぶたびの必須手順にしない。
- 対戦中はAIを呼ばない。AI未設定・生成失敗でも定型文で遊べる。勝敗・スキル効果は通常の処理で決める。
- 「選んだ」「対戦が成立した」「履歴へ保存された」を同じ成功表示にしない。通信が不明なら、同じ対戦を重複加算しない既存の再送処理につなぐ。
- 子供の自由なプロンプト入力やAI契約を参加条件にしない。短い案内、手の名前、選び直し、再開を優先する。

**確認例:** 同じ要求の再送で得点・履歴が増えず、セリフを変えても勝敗の計算は変わらない。

### 3.2 写真日記：AIの文章を本人の日記へ仕上げる

「写真・メモ・タグ→AI下書き→確認・本文へ反映→手直し→保存→一覧・詳細」が基本。自分で本文を書く入口も維持する。AI生成、本文への反映、日記の保存を別の操作として示す。

- 作成中の主役は写真と本文。誰の日記か・日付・選択画像・タグ数を入力の近くで確認できるようにする。
- 再生成で手直し中の本文を黙って置き換えない。生成失敗と日記保存失敗を分け、同じ画面で保持できる入力と画像を残す。
- 一覧では写真と短い本文を読みやすくし、詳細では画像を縦横比のまま見せる。読込中・画像なし・取得失敗を区別し、利用できる再読込・拡大を案内する。
- タグは日記に付く。複数タグのOR絞込み、タグ追加・改名・未使用タグ削除は、日記本文の保存と区別する。
- 保存前に文章を確認する意味を説明する。保存後の日記編集・削除、画像差し替え、SNS機能は基本範囲へ追加しない。

**確認例:** AI下書きを手直しして保存し、再表示した日記で本文・写真・タグ・日付が一致する。画像取得失敗を「写真なし」と表示しない。

### 3.3 英語訓練：一つ答え、応答を読んで続けられる

基本の入口は「クイズ・テキスト会話・振り返り・履歴」。GASの基本クイズは自由記述であり、旧稿の別アプリにあった「クイズ／フリーテキストの二形式を対等な入口にする」という要件は持ち込まない。

- クイズは問題→本人の回答→明示的な送信→評価の順。回答前に正解や解説を露出しない。
- 会話は本人の発言とAIの返答を対応させる。振り返りは今日できたこと・難しかったことを入力する目的を明示する。
- 結果ではAIの評価と本人の回答を見比べられるようにする。採点エラーを低得点や学習完了に置き換えない。
- 入力・処理中・応答・履歴保存を区別する。学習する人を切り替えるときは、表示中の履歴と送信先の人が一致していることを確かめる。
- 長い履歴は必要時に開き、今取り組む回答欄を圧迫しない。問題管理は任意のWeb応用、音声・能力別画面・候補承認は基本導線に加えない。

**確認例:** 一問回答し、本人の回答とフィードバックを履歴で再確認できる。AI失敗後も入力を直して再試行でき、失敗を成功履歴へ記録しない。

### 3.4 キャスト評価：実績とルールから結果を説明できる

主役は日々の実績入力と月次の比較。入力する場面では「誰の・いつの・何件／何円」、集計を見る場面では「どの月の・どの配点による・何点／何位」を先に示す。

- 入力項目へ単位を付け、実績の保存、メンバー情報の保存、配点の保存を分ける。一括保存へ統合しない。
- 月次表では名前・評価項目・点数・順位の対応を保つ。スマホでも表の比較関係を残し、必要なら表だけを横スクロールする。
- Webの配点変更は過去月にも影響する。変更操作の近くにその影響を示し、当時の確定成績を保存する機能があるように見せない。
- メンバーは評価対象、共通ユーザーは操作側のデータであり、同じ意味で表示しない。在籍変更と履歴削除も区別する。
- AIによる人物評価は行わず、既存の計算・同点順位を使う。GASの現行CR版には編集・在籍変更・配点変更UIがないため、その操作を案内しない。

**確認例:** 架空実績から手計算した点数と月次結果が一致する。Webでは実績・配点変更後の再集計、GASでは登録・一覧・集計と同日重複拒否を確認する。

### 3.5 ショップ：選択中と確定済みの境界を見せる

GASは商品と数量をフォームで指定して直接注文する。DB・セッション・画面内のいずれにもカートを持たない。Webは画面内カートで数量・合計を確認・変更してから注文する。

- 商品名・単価・数量・合計と注文者を、確定する前に確認できるようにする。確認のためにGASへカートを追加しない。
- Webの確認画面からは数量を保って戻れるようにする。カート追加や確認画面への移動を注文完了として扱わない。
- 完了画面と履歴は保存された注文・明細を表示する。現在の商品価格から過去注文の金額を作り直さない。
- 応答不明時は同一要求の照合・再送を使い、連打や再表示で注文を増やさない。価格変更等で確定できない場合は、内容の再確認へ戻す。
- Webの取消は注文全体が対象と分かる確認を残す。現行GAS CR版には取消がない。決済・返金・配送・在庫・永続カートを画面上で約束しない。

**確認例:** 数量と単価から計算した合計と保存明細が一致する。同じ要求を再送しても注文は一件。Webでは数量を保った戻り操作と注文全体の取消も確認する。

## 4. 共通ルール：対象・操作・状態の読み方をそろえる

### 4.1 主役と操作を近くに置く

| 判断 | 基準 |
|---|---|
| 初期表示 | 何のアプリか、何をする画面か、最初の操作が分かる。設定や診断を毎回通過させない |
| 主操作 | 「保存」「注文を確定」「この手でじゃんけん」など、結果が想像できる動詞にする。影響の異なる操作を同じ「実行」にしない |
| 操作距離 | 入力・選択・適用・結果を同じ視線の流れに置く。横幅が増えても確定ボタンだけが画面端へ離れない |
| 常設と折りたたみ | 必須の回答・対戦・保存・注文は必要な段階で見せる。低頻度の管理や長い履歴は別区画・別ページ・折りたたみを使う |
| 長い画面 | 画面内リンク等で目的の区画へ到達できるようにする。分割する場合も未保存入力と対象を失わない |
| 一覧と詳細 | タイトル・日時・対象者などの必要情報を示し、戻るときの条件・位置の保持範囲を決める。全ページの永続復元を一律には追加しない |
| 空状態 | 初回0件、絞込み結果0件、未読込、取得失敗を分け、登録・条件解除・再確認のうち可能な次の操作を示す |

短い選択は起点の近くへ、長い本文・画像拡大・注文の重要確認は十分な面積のある画面へ置く。旧稿の8px間隔・固定パネル寸法・専用Reactフックを、このリポジトリの採用仕様として扱わない。

### 4.2 状態と保存の意味をそろえる

| 状態 | 利用者に伝えること | 守る境界 |
|---|---|---|
| 未選択・未入力 | 足りない項目と次にすること | 無効ボタンだけで理由を隠さない |
| 入力済み・未確定 | 対象と変更内容、何を押すと確定するか | 選択変更を勝手に保存・注文・対戦へ進めない |
| 処理中 | 何を処理しているか | 同じ操作の連打を抑止。提供していない取消や進捗率は表示しない |
| 成功 | 生成・反映・保存・注文成立のどこまで済んだか | 下書きができただけで保存済みと表示しない |
| 入力エラー・処理失敗 | 修正箇所、残っている入力、可能な再試行 | トーストだけで消さず、対象の近くにも残す |
| 応答不明 | 保存済みの可能性と確認方法 | 新しい要求として自動再送しない。教材固有の照合・再送方式へつなぐ |
| 履歴・再表示 | 保存済みの内容と対象者・日時 | 画面内の一時値や現在のマスター値と混同しない |

画面内の入力保持と、再読込・セッション終了・サーバー再起動後の復元は別の保証。保持できる範囲を各教材の仕様に合わせ、共通UIを理由に永続下書き・AI要求台帳・自動保存を増やさない。ボタン無効化だけでサーバー側の二重登録対策が済んだとも扱わない。

### 4.3 端末・視認性・操作性

Webでは既存の[共通UI](../02-web-app-learning/template/docs/ui-foundation.md)を起点に、フォーム・本文・一覧・ゲームの幅を使い分ける。全教材の列数やカード密度は統一しない。

- PCは入力と比較の見渡しやすさ、スマホは読める文字・押せる操作・自然な縦の流れを優先する。PCの多列をそのまま縮小しない。
- 色に加えて名前・文字・選択印で意味を示す。項目にはラベルを付け、キーボード操作とフォーカス位置を確認する。
- モーダルやポップアップは閉じ方と元の操作への復帰を用意する。画面端、ソフトキーボード、拡大表示で確定操作を隠さない。
- 写真の読込待ちでも枠が潰れないようにし、画像の縦横比と拡大時の閉じる操作を保つ。
- 既存のPico／admin-picoと配色を再利用する。教材の違いはまず見出し・内容・操作順・密度で表し、共通部品を全面的に作り直す理由にしない。

## 5. 共通化の境界

### 5.1 GASとWebは目的をそろえ、基盤差を許容する

| 対象 | GAS | Web | UIUXとして保つこと |
|---|---|---|---|
| じゃんけん | 通常対戦・得点・履歴 | 仲間・スキル・AIセリフ事前作成 | 選択→結果→再開の分かりやすさ。GASへ旧スキル版の操作を戻さない |
| 写真日記 | 写真・タグ・AI下書き・手直し・保存・閲覧 | 同じ基本機能 | 本人が確かめて保存し、読み返せる。追加読込方式や画像保存先の差は許容 |
| 英語訓練 | 自由記述クイズ・会話・振り返り・履歴 | 同じ基本範囲 | 回答と応答の対応、失敗時の入力保持。問題管理・音声を必須化しない |
| キャスト評価 | 現行は登録・参照を先行するCR版 | 実績・メンバーの編集、配点変更も実装 | 実績・配点・集計の関係。同じ基本機能で完成させる全体方針との差は残す |
| ショップ | カートなし直接注文。現行CR版は取消なし | カート経由注文・履歴・取消 | 確定前の内容確認、二重注文防止、確定後の明細 |

両基盤の完成版配布が必要なのは写真日記・キャスト評価・英語訓練の3教材。じゃんけん・ショップへ両版の完成品をそろえる要件を追加しない。受講順はGAS→Web、提供者のコード・解説の制作順はWeb→GAS。Webで確認した結果をGASの実環境受入へ流用しない。

### 5.2 共通テンプレートは土台、教材の主画面は固有

共通化するのはナビ・現在地・フォーム・エラー・確認・画像表示などの操作の読み方。日記、問題と回答、評価計算、スキル、カートと注文の意味は教材側が持つ。

テンプレートの投稿CRUD、ユーザー管理、CSV、AI疎通、ゲーム例が存在しても、各教材の必須メニューや完成要件にはしない。既存の投稿ノート例と教材本体を区別し、CSVが共通ユーザー・投稿だけを出す場合は、日記・実績・注文等も出力されるように説明しない。

共通のユーザー選択は本人認証ではない。GASの本人限定公開と架空利用者選択、Webの認証方式・有効化・受入は[認証方針](../../../docs/adr/0004-auth-gas-simple-web-supabase.md)と[設定・確認手順](../02-web-app-learning/docs/Googleログインの設定と確認.md)に従う。名前を切り替えられることを、他人のデータを守れる証拠にはしない。

### 5.3 公開先で変えるもの

[公開分離の正本](publication/separation-policy.md)に従い、一般向けは「写真日記」、ナイトワーク向けは「写メ日記」として文言・例・素材を調整する。基本の保存・生成・確認の意味は変えない。

一般向けの2出口へキャスト評価の名称・存在・リンクを出さない。本書の5教材比較をそのまま公開メニューにせず、出口間の切替や全教材ランチャーも自動追加しない。名義・連絡先・許可素材は出口ごとに管理する。

### 6.2 文書整合と横展開の順番

画面改修の準備として、[機能分担](feature-allocation.md)末尾の旧差分、GAS評価・ショップのCR範囲、認証の古い未着手記述を現行の正本と照合する。実装済みの通常じゃんけん・直接注文を未実装へ戻さず、GASの編集・取消追加は範囲の判断と切り分ける。

共通部品の変更が必要ならtemplateを修正し、影響のある派生アプリへ同じ差分を反映する。固有の問題は対象教材で直す。Webで操作・保存・失敗時の期待結果を固めてから、GASの同じ基本体験を確認し、実際に差がある箇所だけ修正する。WebのコードをGASへそのまま移植しない。

最後に余白・配色・アイコン・文字の仕上げを行う。認証有効化やGASの機能追加を、このUIUX整理だけで実施することにはしない。

なお、共通 `form-protection.js` には送信時の `saved=true` 設定があるが、日記・英語は後から登録される固有submit処理で `false` に戻している。この行だけを根拠に「通信失敗でも必ず保存済みになる」とは判定しない。項目3の待機中編集・成功応答時の扱いとは別に確認する。

## 7. 受入条件と更新方法

### 7.1 共通の確認

| 観点 | 確認すること |
|---|---|
| 目的と入口 | 初見で何をする画面か分かり、設定を毎回通らず基本操作へ進める |
| 型固有の体験 | 第3節の確認例を、当該基盤で実装している範囲に合わせて実施する |
| 対象と入力 | 誰の・いつの・何に対する操作か一致し、エラー後も保持範囲内の入力が残る |
| 確定と保存 | 下書き・生成・保存・注文・対戦を区別し、再表示で保存内容を確認できる。再送で重複しない |
| 失敗からの復帰 | 未設定・処理失敗・応答不明・画像読込失敗で、実際に利用可能な次の操作が示される |
| 表示と操作 | 既存検証に合わせPC1440×1000／狭幅390×844を起点に、必要な768／1280／1920pxや200%拡大を追加。表以外の不要な横はみ出し、文字切れ、隠れる操作を確認 |
| キーボード | Tabで主要操作へ到達でき、選択・送信・閉じる・フォーカス復帰が機能する |
| データのある状態 | 0件だけでなく、長い名前・本文、複数画像、複数明細、履歴、同点順位などを架空データで確認 |
| 実環境 | 模擬GAS／固定AI／ローカルDBの成功と、実GAS・DB・画像・AI・公開URLの受入を分ける |
| 端末と学習成果 | ブラウザーの狭幅確認を物理スマホの操作確認と呼ばない。操作成功を学習効果の実証と呼ばない |

画面幅の例は検証の起点であり、全画面で合格済みの一覧ではない。既存の教材別受入スクリプト・記録を再利用し、無関係な全機能の検査を毎回増やさない。

### 7.2 記録すること

改修したら、対象教材・GAS／Web・画面・変更した判断・操作と期待結果・実際の結果・日付・版・環境・未確認事項を既存のタスク／検証記録へ残す。UIの改善候補は再現した不具合と分ける。

本書には思想・共通ルール・例外・現状の差だけを残し、日々のログを積み上げない。新しい案は基本範囲か任意の応用かを先に区別し、配布範囲を変える場合は対応表・機能分担・対象教材の正本を一緒に更新する。
