# 技術基盤と検証：同じ題材を段階的に深める

配布範囲と両版の機能差は[機能分担](feature-allocation.md)に従う。両版の完成版配布は写真日記・キャスト評価・英語訓練のみ。じゃんけん・ショップは段階ごとに必要な体験を提供し、同等の完成品を2つずつ用意する要件を課さない。

## 提供者の制作はWebから始める

受講順は **01 GAS → 02 Web**、コード・解説の制作順は **02 Web → 01 GAS**。提供者は、ローカル起動・DB確認・自動テストを行いやすいSpring Boot＋PostgreSQL側で、題材の業務ルール・データ・失敗時の挙動を先に確認し、そのコードと解説を基にGAS側を整える。

再利用するのは仕様・サンプル・期待結果・テスト観点・解説の構成。GAS側ではSheets・Drive・GAS固有の保存・権限・排他・公開・実行制約を別途確認する。Webのテスト成功をGASの実環境受入済みとは扱わない。Web側の実装状況は[テンプレート](../02-web-app-learning/template/README.md)、横断方針は[文書索引](README.md)を参照する。

## 題材を固定し技術レベルを広げる

2026-10-27の[採用決定](../../../docs/adr/0001-web-app-stack.md)により、発展版のNext.js＋Vercel案は廃止し、Spring Boot＋Thymeleaf＋Render＋Supabaseに統一した。[Webアプリ支援戦略](../02-web-app-learning/web-app-support-strategy.md)の構成と検証方針に従う。DBはPostgreSQL、Storageは必要時に利用する。既存GAS版の詳細仕様を参照し、新方針と異なるじゃんけんのスキル・AI、ショップのカートは個別に差分を管理する。

サーバー側の認可、DB接続ロール、データの公開範囲を設計し、必要なRLSが実際の接続経路で有効かを検証する。技術の共通化と、利用者のゴール・スタート支援・成功条件の共通化は分ける。Oracle固有の実習は資格学習側で行う。

### 完成版を両基盤で配布する3教材

写真日記・キャスト評価・英語訓練の3教材に限り、**GAS版**と**Spring Boot＋Thymeleaf＋Render＋Supabase版**の完成版を配布する方針。模範実装は単一のコード上の正解ではなく、両版に共通する基本範囲の仕様・受入条件を満たす検証済みの比較対象とする。じゃんけん・ショップには両版の完成品を揃える要件を課さない。3教材は同じ基本機能で完成とし、Webの英語問題管理画面は任意の応用とする。横展開は目標・参考プロンプト・確認例を渡し、提供者の追加制作を増やさない。教材版の準備・検証状況は各READMEに従い、共通テンプレートの実装済み機能を教材の完成実績に読み替えない。

| 学習の入口・発展 | 技術・道具 | 学ぶこと |
|---|---|---|
| GASで体験・利用 | Google Apps Script＋Google Sheets | データの関係、登録・参照、業務ルール、AIへの開発指示。更新・削除は各アプリの仕様に応じて扱う |
| Webアプリを開発・利用 | Spring Boot＋Thymeleaf＋Render＋Supabase | 提供者が環境と確認手順を準備し、本人は用途に必要な操作・AIへの依頼・結果確認から始める。Java・SQL等の詳細は必要時に学ぶ |
| AIと改善 | Devin等＋仕様・テスト・模範実装 | 独自要件を整理し、AIの変更案を検証・比較して改善する |

受講案内の順番は01 GAS → 02 Web。全教材の修了やWebへの進級を初回成功の条件にはせず、本人に意味のある一つの課題を選ぶ。AI活用は最初から両基盤で行え、本人の理解・判断・検証を伴う改善を目指す。

| 既存教材 | GAS版を通じて学ぶこと | 発展版で深める観点 |
|---|---|---|
| skill-janken-game | 通常のじゃんけんの勝敗・得点・対戦履歴 | 小さなスキル構成とAIセリフ事前作成 |
| english-trainer | クイズ・AI採点・テキスト会話・振り返り・学習履歴 | 同じ内容をWebでも使う。資格学習への変更は目標と参考プロンプト。問題管理画面は任意 |
| photo-diary | 写真・日記の登録と参照・タグ | Storage、リレーショナルDB、画像と記録の権限 |
| cast-evaluation | 管理者限定・単一店舗の実績・評価ルール・月次集計・順位 | 同じ内容をWebでも使う。SQLによる同じ集計結果の確認 |
| online-shop | カートなしの直接注文、商品・注文・明細・確定時点の保存 | カートで確認・数量変更して注文。確定後の整合性は共通 |

同じ完成範囲を配布する3教材では基本機能と必要な公開範囲を揃え、基盤の違いを検証する。音声、決済・在庫、キャスト用画面・複数店舗・POS等は今回の制作計画から外す。Web側の共通テンプレートにある機能を、各教材へ一律に追加しない。

### 正解は共通の受入条件で判断する

学習サイクルは **AIに開発・改修を依頼 → 自分で検証 → 模範実装と比較 → 理由を説明して改善** とする。比較前に期待する結果を言葉にし、実際の動作とデータで確かめる。

同じ教材のGAS版、Spring Boot版、学習者の実装では、両版の基本範囲について業務要件・入力例・期待結果・守るべき制約を共通にする。Web限定の機能をGAS版にも必須とはしない。異なる5教材の業務ルールまで同一化するものではない。見た目やコード構造が違っても、合意した仕様と受入条件を満たせば正解とする。模範コードの丸写しを合格条件にしない。

| 共通化するもの | 基盤ごとに用意するもの |
|---|---|
| 機能仕様、非対象、利用者と公開範囲 | GAS／SheetsまたはSpring Boot／Thymeleaf／Render／Supabaseの具体構成 |
| データの意味、業務ルール、入力と期待値 | 物理スキーマ、通信、認証・認可の実装 |
| 中核の操作シナリオ・受入テスト仕様 | 各環境で動かすテストコード・テストデータの投入方法 |
| 学習目標、問いかけ、変更課題 | 導入・公開・復旧手順、画面操作の動画 |
| 仕様版と受入条件の対応 | 実装版・検証結果・既知の差分 |

同じテストコードを無理に共用するのではなく、同じ受入テスト仕様を各基盤で実行できる形にする。DBや認証の違いによる検証は、共通の業務テストに加えて行う。

たとえばキャスト評価では、期間合計後のポイント計算、同点順位、重複防止、退店後の実績保持を共通条件にできる。ルール履歴・キャスト用画面は今回の提供範囲に含めず、配点を変えて同じサンプル実績の結果を確かめる程度の任意の課題に留める。

### 現在の配置と制作手順

横断設計は `src/app-learning/docs`、GAS教材は `01-gas-app-learning`、Web共通テンプレートは `02-web-app-learning/template` に置く。教材名の下へ `gas/`・`spring-boot/` を再配置する旧案は採用しない。Web個別教材を追加するときは、既存の配置・命名に沿って範囲を決める。

制作では小さなダミーデータで画面・操作・期待結果を先に確認できる。ただし、ダミー応答の確認をDB保存・画像保存・AI実通信の検証と呼ばない。同じ入力と期待結果を実接続へ引き継いで確認し、実データへの置換だけで完成としない。5教材を同時に完成させる前提も置かない。

Webの追加共通作業は[共通仕様](../02-web-app-learning/template/docs/shared-foundation-requirements.md)のF1・F2・F3に絞る。既存の画面・管理・画像・DB・復旧を再利用し、教材の業務モデルまで土台に実装しない。

模範実装には仕様、確認用データ、期待結果、導入・復旧手順、AIへ依頼する際の変更箇所を添える。動画一式や全応用の模範コードを先に作り切る必要はなく、実際につまずいた操作を記事・短い実演へ戻す。

### 配布範囲を絞り、段階的に完成させる

最初に選ぶのは1題材。完成版を両基盤で配布する3教材では、Web側からコード・解説を整え、共通の基本範囲をGAS側へ展開して各基盤で検証する。じゃんけん・ショップは教材として提供する範囲を個別に決める。

全5教材×2基盤の完成品を前提にしない。両版の配布が必要な3教材は共通仕様と実装差分を分け、変更時には両版への影響を確認する。未対応の版は未対応と明記し、仕様も挙動も揃っていない状態を同等の模範実装として配布しない。

Spring Boot版はGASコードの単純変換で完成としない。認証、サーバー側の認可、DB接続ロールと必要なRLS、許可されていないデータへのアクセス拒否、Storageの公開範囲、秘密情報、AIの外部送信、注文等の更新整合性を、その環境で検証する。具体的な構成・コマンド・サービス条件は実装時に公式情報と照合する。

対面30分×3回は初期導入・理解・AI活用の伴走の構成案。90分で全基盤を習得させるものではなく、その後も記事・動画・模範実装を使って同じ題材を深められるようにする。

## 教材提供前の検証と教育モデルの検証

プロジェクト一覧の実装状況と、教材として提供できる状態は分けて管理する。

| 段階 | 確認すること |
|---|---|
| ローカル | 配布対象の最新版でテストと画面確認を行う |
| 実環境 | GASは実GAS・Sheets・必要なDrive／AI、Webは採用した公開環境・PostgreSQL・必要なStorage／AIで主要操作を確認する |
| コピー・引き渡し | 新規環境で初期設定・権限・保存先を確認し、元のデータや秘密情報が混入しないことを確かめる |
| 教材との一致 | 配布版と記事・動画の手順を揃え、学習者または保護者・講師が再現できるか確認する |
| 少人数の指導 | 各対象者の成功条件、必要な介助、所要時間、次も改善したいかを観測する |

提供者管理端末で使う子供向けと、本人の環境へ導入する成人向けでは、引き渡し・準備の条件を分ける。公開環境が既にあるアプリでも、最新版の受入やコピー先での動作を省略しない。キャスト評価は設計段階から検証用MVPを用意する必要がある。

検証結果は、アプリが動いたこと、本人が理解して変更できたこと、指導時間・支援負担、支払い意思を分けて記録する。教育効果や販売需要を、既存の相談があることだけで実証済みにはしない。


## 検証記録の共通書式

以下は今後の記録用書式であり、今回検証を実施した記録ではない。個別プロジェクトに既存の記録様式がある場合はそれを正本とし、必要な項目を対応付ける。

| 記録項目 | 記載内容 |
|---|---|
| 対象 | プロジェクト、基盤、仕様版、実装版、教材版 |
| 環境と範囲 | ローカル／実環境／コピー先、利用者、公開範囲、対象操作 |
| 受入条件 | 前提データ、入力・操作、期待する画面・保存結果、守る制約 |
| 結果と根拠 | 実施日、実測結果、合否、証跡への参照、未実施・対象外の理由 |
| 差分と残件 | 両基盤の差分、未確認事項、不具合、次の検証 |
| 引き渡し・復旧 | 初期設定と権限、コード・データ・設定の退避と復旧の確認 |
| 教育の観測 | 本人の説明・操作、必要な介助、所要時間、次の改善意欲 |

ローカル合格だけで「実環境受入済み」、過去版の合格だけで「最新版検証済み」、公開URLがあるだけで「コピー配布可能」と記載しない。


## 今後の進め方

当面は事業化と新規題材の追加を行わず、既存5教材を深める。[役割分担と全体最適化](01_portfolio.md#5教材の役割分担と全体最適化) を先に判断基準とし、機能の重複を薄くすることと、必要な基本機能を削ることを混同しない。

1. **配布範囲と機能分担を決める。** 両版の完成版配布は写真日記・キャスト評価・英語訓練のみ。じゃんけん・ショップは提供する基本体験と発展課題を決め、全5教材の両版完成を前提にしない。
2. **共通仕様と受入条件を整える。** 個別アプリの正本から業務要件・非対象・利用者・入力例・期待値を整理し、学習者の実装にも使える確認方法を用意する。
3. **最初の1題材を選ぶ。** 実際の利用・学習体験、現行版の安定性、発展版で学ぶ価値を基に選ぶ。全5教材を一括で移植しない。
4. **Webからコード・解説を整え、必要な基本範囲をGASへ展開する。** Spring Boot＋Thymeleaf＋Render＋Supabaseで先に検証し、GAS固有の権限・保存・公開・復旧はGAS側でも確認する。
5. **説明と演習へ落とし込む。** 記事・動画・AIへの改修依頼・比較観点を揃え、本人に合う支援枠で、AIへの依頼・試行・結果確認を一度経験できるか確認する。6工程・30分×3回は必要時の参考案に留める。
6. **教材資産として蓄積する。** つまずきと支援工数を記録し、共通手順へ戻す。他の題材の発展版は教育効果と保守余力を確認して追加する。
7. **横断レビューで再整理する。** 3教材の両版配布と、じゃんけん・ショップの教材提供を、それぞれの範囲・受入条件で確認する。比較材料が揃った時点でPortfolio Architecture Reviewを行う。専門性の強化、重複機能の簡素化、共通教材への整理を判断し、個別仕様と検証へ反映する。

将来事業化を検討するときに、需要・支払い意思・価格・初回成功と支援枠内での引き渡しを別々に検証する。現在の準備と有料募集を混同しない。銀行・転職等の応用例やAI利用金額の案は参照として保持し、実装範囲へ自動的に追加しない。

GAS版と発展版は、両版に共通する基本範囲で業務要件を満たす比較対象とする。Web限定の追加機能がGASにないことを不備とは扱わない。仕様を満たす方法は一つに限定せず、AIで作った結果を自分で確かめ、理由を説明できることを到達目標とする。

## 最小の受入例

| 対象 | 入力と期待結果 | 共通・基盤固有の区分 |
|---|---|---|
| 写真日記 | 許可されたサンプル写真で下書きを作り、本人が手直しして保存。一覧・詳細で写真・タグ・本文の対応を確認 | 両版共通。画像保存先と取得権限は各基盤で確認 |
| 英語訓練 | 既知の問題へ正答・誤答を入力し、評価の根拠と回答・履歴の対応を確認 | 両版共通。AIの表現の完全一致は求めず、事前の評価観点で判断 |
| キャスト評価 | 架空の実績を登録し、月次集計・同点順位を既知の期待値と照合。配点変更時の再計算も確認 | 両版共通。入力権限と保存の整合性は各基盤で確認 |
| じゃんけん | 固定した手で勝敗・得点・履歴を確認。Webはスキル効果と採用したセリフ表示も確認 | GASにはスキル・アプリ内AIを要求しない。Webの対戦中はAI通信しない |
| ショップ | 商品・数量・確定時の金額と注文明細を照合。再送しても二重注文にならない | GASは直接注文。Webのみカートで数量変更後に注文 |

PlaywrightはWebの主要操作・失敗時表示・ページ分割・画像あり／なしを繰り返し確かめるために使う。シードはその確認に必要な件数と状態を用意し、外部AIは模擬試験と明示的な実疎通を分ける。今回の文書更新ではアプリの試験を実行していない。
