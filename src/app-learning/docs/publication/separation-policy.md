# 情報出口の分離ポリシー

状態：確定要件の正本。内部限定。2026-10-28更新。

同日の追加依頼による紹介WIP・固定URL・名刺は[WIP公開・印刷運用](wip-release.md)を参照。教材の下記ゲートを維持し、仮名の紹介ページだけを別設定で公開する。

## 1. 三つの出口と二つの軸

| 出口ID | `identity_mode` | `audience` | 含める内容 |
|---|---|---|---|
| `realname-general` | `realname` | `general` | 本名で案内する一般教材。ナイトワークに触れない |
| `alias-nightlife` | `alias` | `nightlife` | 本名を出さず、写メ日記・キャスト評価を案内 |
| `alias-general` | `alias` | `general` | 本名を出さず、ナイトワークにも触れない |

出口IDは内部管理用。実際のブランド名・人名・ドメインをフォルダー名に使わない。2軸の組合せから任意の第4出口を自動生成せず、上記3出口だけを許可する。

①の準備が②・③を止めないよう、公開準備の判定は出口単位で行う。ただし本名サイトの準備中という事情は③の利用者向け説明へ出さない。

## 2. 情報の境界

- ①・③へ、キャスト評価、専門用サンプル、専門側URL、専門側の存在を知らせる案内を出さない。
- ②・③へ、本名、①のプロフィール・個人メール・アカウント・本名との対応関係を出さない。
- **2026-10-28ユーザー確定：②と③は別の活動名にする。** プロフィール・問い合わせ・公開設定も分け、設定を自動継承しない。名前検索から両出口が結び付く共通の公開名や、共用の連絡先を使わない。具体的な名前は未設定。
- 全出口で、別出口への切替・姉妹サイト・全商品一覧・内部資料へのリンクを作らない。
- 公開ファイル、検索、配布教材、デモ、問い合わせに加え、名刺、署名、ファイル属性、共有資料の所有者表示、予約・会議の主催者表示まで対象にする。
- 公開してよい実名表記を①へ設定する工程と、内部の本人情報・対応表の管理は分ける。今は実際の氏名をGitへ追加しない。

## 3. 正本と出力

既存アプリの機能・業務ルール・DB仕様は現位置の正本を参照し、出口別に複製しない。`docs/publication/` は内部設計、`publishing/*/content/` は外向き原稿、`publish.yaml` は出口別設定、`catalog.yaml` は素材の許可・依存物の正本とする。

公開できる素材は、台帳で当該出口へ許可され、かつ当該出口で選択された素材とその許可済み依存物だけ。未分類・未知ID・未許可依存物・出口をまたぐリンクは拒否する。素材台帳や内部の全体READMEをブラウザーへ渡さない。

共通公開素材は中立的な説明に限る。内部の共通方針、両名義の関係、全体ポートフォリオは共通公開素材ではない。写真日記の基本説明は再利用できるが、写メ日記の例・画像は②へ限定する。

教材そのものとして①・③から外すのはキャスト評価だけ。他の既存教材は、ナイトワークの文脈を外した説明・サンプルで掲載候補にできる。これは全教材を今すぐ台帳へ登録・公開する意味ではなく、素材ごとの許可と準備状態を引き続き確認する。

公開名や問い合わせ先が未設定でも、本名・別出口の設定を代わりに使わない。未設定は公開準備未完了とする。

## 4. 配布と個人情報

配布物は許可ファイルを列挙する。ソース配布・ZIP・PDF・画像を追加するときは、本文だけでなく著者、履歴、ファイル名、メタデータ、同梱物を確認する。必要なライセンス表記は保持する。

①・②・③の実データ・デモ・保存先・接続権限は別に扱う。教材デモには架空データだけを使う。ユーザー選択は本人認証ではなく、店舗の評価情報を扱う実利用の権限設計は別途必要。

名義対応表、秘密値、本名照合辞書、実顧客情報は公開設定や公開ログへ入れない。現在の検査は提供者の本名を取得・照合しないため、個人情報の混入がないことを自動保証するものではない。

## 5. 公開水準

「本名非開示」は「閲覧に認証が必要」と同義ではない。教材用 `publish.yaml` は全出口で公開無効。②の教材・デモは招待制を推奨し、採否未決定の `access_mode: undecided` を維持する。名刺用紹介WIPは3出口とも一般公開する。②では題材名を案内するが、実データや教材を配信しない。

②を一般公開すれば、一般の人も検索・共有URLから見られる。別ドメインやnoindexは認証の代わりにならない。招待制を採る場合はページだけでなくAPI・画像・添付・デモ・標準URL・プレビュー・配信元も保護する。認証を共通教材へ一律追加する要件にはしない。

### 5.1 ドメインと公開方式

| 出口 | ドメイン | 公開方式 |
|---|---|---|
| ① | 独自ドメイン必須 | 正式な公開先として構築する |
| ②・③ | 独自ドメインは不要 | 簡易サービスで足りる。ただし公開技術はできるだけ①と揃える |

「公開技術を揃える」とは、原稿の形式、`catalog.yaml`・`publish.yaml`、生成・検査処理、成果物の形をできるだけ共通にすることを指す。名義・掲載内容・公開権限は出口ごとに変え、インフラ上の差を配置先の設定へ寄せる。簡易サービス専用の編集画面へ原稿を直接書き、正本を二重に持つ運用にはしない。

②・③の配置先は、①のドメイン配下・別名、本名や①のアカウント名が表示されるURL・プロフィールを使わない。サービスの標準URL・アカウント名・管理者表示も名義境界の対象とする。②で招待制を採る場合は、その簡易サービスが閲覧制限を強制できるかを選定条件に含める。

公開範囲の原則の根拠は[元の調査](../ナイトワーク特化版の情報出口と否かで設計を分ける.md)を参照。過去のコピー・検索・第三者の共有まで消せるとは扱わない。

## 6. 3出口から将来の2出口へ

基本想定は①本名公開・一般と、②本名非開示・専門を残すこと。③の継続・終了・内容移管の時期と方法は別途決める。①が完成しても③の設定をそのまま本名に書き換えない。

③の中立的な本文は共通素材から①でも再利用できる。一方、③の連絡先・ユーザー情報・プロフィール・問い合わせ履歴は自動移管しない。③から①へのリダイレクト、移転告知、canonical、SNS告知は本名との対応を明かす可能性があるため、自動実行しない。

出口を終了するときは旧ページ・添付・デモ・検索・窓口の扱いを記録し、必要な案内と公開範囲を個別に判断する。出口IDと過去のリリース記録は再利用しない。

## 7. 受入条件

| 対象 | 条件 |
|---|---|
| 設定 | 3出口の本人情報の扱いと題材が上表に一致する |
| ①・③ | 本文・取得物・検索・添付・リンクに専門情報が含まれない |
| ②・③ | プロフィール・著者・返信・共有資料に本名や①との対応が出ない |
| ②と③の名義 | 別々の活動名・連絡先を使い、他方への案内や対応関係を出さない |
| 全出口 | 相互リンク・内部README・台帳・作業ログを配信しない |
| 原稿 | 実装と版を照合し、設計段階の機能を完成済みと案内しない |
| 生成物 | 検査済みの当該出口の成果物だけを配信する。制作元・publishing全体を配信しない |
| 限定公開を選ぶ場合 | 直接URL・別配信経路・キャッシュでも内容を取得できない |
| 公開準備 | 名義・連絡先・公開水準・素材レビューの未設定が残らない |

ローカル検査の成功は、上表の実環境確認すべての完了を意味しない。混入時は影響する公開物を停止し、公開元・添付・配布先・検索・キャッシュを確認して正本から修正する。
