## 結論

GASの実行主体と同じ所有者の非公開Driveフォルダへ静止画を保存し、SheetsにはファイルIDと表示順を保存する方式を推奨する。現在のデータモデルはすでに1対多なので、画像1枚版を作っても将来の複数枚対応のためにpostsへ画像列を追加しない。

必要なのはDrivePhotoProviderの追加だけではない。アップロード入力・検証・再送処理・非公開画像の表示・未保存ファイルの管理・既存ダミーとの互換が必要になる。Drive認証・保存先確認 → 基本的な1枚アップロード → 日記への添付 → 1対多対応の順に分ける。動画は対象外。

## アカウント・保存先

manifestは `MYSELF` / `USER_DEPLOYING`。この実行主体のDriveに専用フォルダを作り、そのIDをサーバー側設定で参照する案。新規フォルダは共有フォルダの配下を避け、実際の共有権限を確認する。利用者が同じアカウントであることと、保存先が非公開であることを別々に確認する。

GASのFolder.createFile(blob)でフォルダ内へ保存できる。DriveアクセスのOAuth権限と再承認が必要になる。DriveAppを使う案では広いDrive権限が必要となるため、より狭いdrive.file権限を求める場合はDrive APIと認可方式を別設計する。[Folder公式資料](https://developers.google.com/apps-script/reference/drive/folder)

共有を「リンクを知っている全員」にしてimg表示を成立させる案は採らない。OAuthトークンをブラウザに渡す案も採らない。

## ブラウザからGASへの転送方式

| 方法 | 評価 |
|---|---|
| HTML formをgoogle.script.runへ渡す | 公式サンプルあり。file inputはサーバー側Blobになる。ただしformは唯一の引数にする必要がある |
| FileReader等でbase64にし、通常のオブジェクトとして送る | 圧縮済み画像・複数枚・再送IDを扱いやすい。base64で約4/3に増えるため小容量限定 |
| ブラウザからDriveへ直接アップロード | 大容量には検討余地があるが、別のOAuth・転送設計が増える。初期案では採用しない |

初期案は画像をブラウザで正規化し、1枚ずつbase64オブジェクトで送る。HTML form方式を採る場合はuploadId等をhidden inputに含め、`form, requestId` のように2引数で渡さない。File / FileListをそのまま既存App.apiへ渡す案は避ける。いずれもgoogle.script.runの非同期処理であり、順序が必要なら明示的に待つ。[HTML Service通信](https://developers.google.com/apps-script/guides/html/communication)

### 初期上限案（Google公式上限ではない）

- Phase P2a / P2b：1枚、Phase P3：最大3枚。
- 端末で選ぶ元画像は1枚10MiB以下、ピクセル数上限も検証する。過大な画像はデコード前に容量で止める。
- 保存・送信用は長辺1600px以下、1枚1MiB以下のJPEGまたはPNG。JPEG品質は目安0.8から実機調整し、上限を満たせなければ利用者へ通知する。
- P3は逐次送信で合計3MiB以下。初期表示へbase64を埋め込まない。

これらは速度・メモリ・画質のバランスを測る開始値。iPhone / Androidの大きな写真、回転、透明PNGを確認して決める。GASは1実行6分、URL Fetchは送受信50MBという制限があるが、後者はブラウザ→google.script.runの保証サイズではない。今回参照した公式資料からRPCの安全な最大ペイロードは確定できないため、実測する。[GAS制限](https://developers.google.com/apps-script/guides/services/quotas)

## 静止画の検証

`accept` 属性は選択補助でありサーバー側検証の代わりにしない。

- P2aからJPEG / PNGだけを許可。動画、GIF（アニメーションを含み得る）、SVG、WebP/APNG等の未対応形式は拒否または静止JPEGへ変換できたものだけ受け付ける。
- HEIC / HEIFは端末依存。GASでJPEGへ簡単に変換できると仮定しない。初期版ではJPEGでの選択を案内し、変換対応は別段階。
- クライアントでデコード成功・寸法・正規化を確認し、サーバーでbase64形式・復号後サイズ・許可MIME・ファイルシグネチャ・可能な範囲のヘッダーを再検証する。MIMEと拡張子だけを信用しない。
- PNGを保持するならAPNGのacTLチャンク等も検査する。完全な画像デコーダによる検証が必要な要件へ進む場合はGAS単体の限界を評価する。
- 保存名はサーバー発行IDを主体にし、元ファイル名をHTMLとして描画しない。任意の外部URLや任意のDrive IDをアップロード扱いしない。
- 正規化で位置情報等のメタデータを残さない方針とするが、端末ごとの出力を確認するまで除去を保証しない。元写真そのものの保管は初期対象外。

## 非公開画像の表示が最大の検証点

DriveのthumbnailLinkは短命で、非公開ファイルでは認証付き取得が必要。恒久的な公開画像URLとしてSheetsに保存したり、ブラウザのログインCookieだけで常に表示できると仮定しない。[Drive file metadata](https://developers.google.com/workspace/drive/api/guides/file-metadata)・[filesリソース](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)

推奨案は、アプリ管理下の画像をGAS側で読み、サイズ制限したプレビューをbase64で必要時に返す方式。表示用サムネイルをアップロード時に別途生成・保存すれば、一覧表示で原寸画像を毎回読まずに済む。Drive自動サムネイルの取得可否・生成待ちはP2bで試す。

- 一覧は表示中のカードの代表画像だけをまとめて遅延取得する。詳細の全画像は詳細を開いてから取得する。
- presenterはID・種別・ラベル等だけを返し、PhotoService.view呼び出しのたびにDriveへアクセスしない。初期一覧の軽量化を維持する。
- ブラウザ側では読み込み中・失敗・再試行表示を設け、セッション内で再利用する。CacheServiceへ大きな画像本体を入れる前提にしない。
- HTML ServiceのdoGetは現在HTMLを返す入口であり、画像Blobをそのまま返すルートを足せば済むとは扱わない。

## アップロードと日記保存の整合

写真は日記保存前にAIへ渡す場合があるため、「画像の仮保存」と「日記への添付確定」を分ける。DriveとSheetsをまたぐトランザクションはない。

```text
選択 → ローカルプレビュー → uploadId発行 → 画像仮保存
     → 返されたphotoIdを選択状態へ登録 → 必要ならAI下書き
     → createで参照を検証 → images / post_tags / postsへ保存 → 添付確定
```

提案APIは `uploadPhoto({ uploadId, name, mimeType, base64 })`、必要時取得は `getPhotoPreviews(ids)` 等。名称は設計案。controllerは入口だけ、転送・検証・再送はUploadService、Drive操作は専用adapter、台帳操作はmodel / SheetStoreに分ける。

### 台帳案

既存imagesシートは「保存済み日記との関連」のまま維持する。別のuploadsシートを追加する案を推奨する：upload_id / file_id / thumbnail_file_id / mime_type / bytes / created_at / state / attached_post_id。

この追加は5シート構成への仕様変更になる。列順・文字列列・Seeder・テスト・docs/05の変更が必要。4シートを絶対に維持する場合はDriveのappProperties等を使う代案を検証する必要があり、今回その代案は実装検証していない。

- uploadIdを再送時も維持し、成功済みなら同じ結果を返す。ファイル作成と台帳書込の間の失敗に備え、ファイル名やDriveメタデータにも回復用IDを持たせる。
- CacheServiceだけで永続的な重複防止を保証しない。短いロック・永続台帳・再照合を組み合わせ、画像処理やAI待ちでシート用ロックを長時間保持しない。
- ファイル作成成功後に応答を失っても再送で二重作成しないこと、台帳書込失敗時の回復をテストする。
- createでは専用フォルダ・台帳登録・state・必要な添付権限を確認する。Driveで読めるというだけで任意ファイルを受け付けない。
- 保存失敗時は仮画像を保持し、同じrequestIdで再試行できるようにする。日記成功後に添付確定記録だけ失敗したケースはimagesの参照で回復する。
- 破棄・離脱で発生した孤立ファイルは、最初は一覧化して手動で確認する。自動削除は別段階。導入時は候補の経過時間（仮案24時間）だけで判定せず、imagesからの参照と台帳を再確認して競合を防ぐ。

## ダミーからの移行

現行のサンプル日記はsample-a等のダミーIDを参照する。provider設定をdriveへ変えるだけでは既存の日記画像が消える可能性がある。

写真窓口で登録済みダミーIDと実アップロードIDを解決できる移行adapterを設ける案とする。画面・日記サービスにprovider名の条件分岐を散らさない。既存サンプルを削除して移行を済ませない。catalogはDrive全件列挙ではなく、今回の選択・必要な最近の項目だけを扱い、maxPerPostは目録件数と切り離す。

## 実装Phase（段階分けを優先）

認証と基本アップロードを先に成立させる。日記との関連・複数画像・後片付けを一度に実装しない。各Phaseの結果を確認してから次に進む。P1は完了、P2a以降は実装済み・実環境検証の残項目あり。

| Phase | 到達点 | 依存 |
|---|---|---|
| P1 | Driveアカウント認証・保存先へのアクセス確認 | なし |
| P2a | ブラウザから静止画1枚を非公開Driveへアップロード | P1 |
| P2b | その1枚を日記に添付し、アプリで再表示 | P2a |
| P3 | 日記1件に複数画像を添付（1対多） | P2b |
| P4 | 孤立ファイル整理・サムネイルと容量の最適化 | P3 |

### P1：Driveアカウント認証・保存先確認

**目的**：どのアカウントの、どのフォルダへ保存するかを固定する。

- GAS実行主体と所有者アカウントを確認し、Driveアクセスに必要なOAuth承認を行う。
- 専用の非公開保存フォルダを用意してIDを設定する。共有権限、保存先、アクセス可否を確認する。
- GASエディタから実行する内部の診断用入口でフォルダ情報を取得する。必要な権限と拒否時の結果を記録する。
- この段階では画像選択UI、日記の保存構造変更、Gemini連携を入れない。

**完了条件**：意図した所有者のフォルダへGASからアクセスでき、公開共有されていないことを確認する。読取成功だけで書込成功とは報告しない。実際の画像書込はP2aで検証する。認証画面の表示やフォルダIDの設定だけを完了としない。

### P2a：基本的な1枚アップロード

**目的**：最小の画面操作で、選んだ画像がDriveへ保存されることを確認する。

- 単一ファイルの選択・ローカルプレビュー・送信ボタン・送信中表示・成功／失敗表示を作る。
- JPEG / PNGと容量上限の検証を入れ、1枚をGAS経由で専用フォルダへ保存する。小さい検証用画像から始める。
- uploadIdを発行し、同じ要求の再送を識別できる最小の記録を残す。連打の抑制だけで重複防止済みとしない。
- 保存結果のIDを受け取り、所有者がDrive側で実画像を確認する。この段階のアプリ内プレビューはローカル画像でよい。
- 一時的な検証用UIは通常の日記作成と区別する。一般利用の完成版としては公開しない。
- 日記との関連付け、アプリ再読込後の非公開表示、複数選択、AI送信、サムネイル最適化、自動削除は次段階へ分ける。

**完了条件**：ブラウザで選んだ静止画1枚が意図したフォルダに非公開で保存され、内容が一致する。動画・過大ファイルを拒否でき、通信失敗を表示し、同じuploadIdの再送でファイルを増やさない。Driveで保存画像を確認した証跡を残す。

**失敗処理の最低線**：ファイル作成後に応答や記録を失った場合の再照合を用意する。自動削除は不要だが、作った検証ファイルのIDは追跡可能にする。P2aだけの成功を「写真日記が完成」と報告しない。

### P2b：1枚を日記へ添付・再表示

**目的**：基本アップロードを既存の日記アプリへ接続する。

- P2aのupload処理を再利用し、通常フォームへ接続する。画像状態と日記の保存状態を分ける。
- 台帳方式を確定し、仮保存→添付確定と、失敗時の再試行を実装する。P2aの記録を引き継ぎ、同じ機能を別実装しない。
- 既存imagesシートに1行を追加し、`sort_order = 1` とする。postsへ単独画像列を追加しない。
- 非公開画像をGAS経由で取得し、一覧・詳細・ページ再読込後に表示する。最初はサイズ制限した保存画像を必要時取得し、高度なサムネイル処理はP4に分けられる。
- 既存のダミー日記も表示できるようにし、AI下書きは現行モードのまま維持する。

**完了条件**：1枚選択 → アップロード → 日記保存 → 詳細 → 再読込で同じ画像を表示できる。日記保存失敗後に再試行でき、フォルダ外の任意IDは添付できない。既存サンプルを壊さない。

### P3：1対多対応

**目的**：P2bで成立した1枚の流れを複数枚へ拡張する。

- 複数選択、最大枚数・合計容量、逐次送信を追加する。初期案は最大3枚。
- 各画像の未送信／送信中／成功／失敗を区別し、失敗分だけを再試行できるようにする。
- 選択の解除・並び替え・代表画像を扱い、順序をimages.sort_orderへ保存する。
- 送信未完了や失敗中は日記保存を止める。利用者が失敗画像を明示的に外した場合は、成功分だけで保存できる設計とする。
- 日記の保存成功後に未確定記録が残る場合の回復も複数枚で検証する。

**完了条件**：複数枚の選択順・変更後の順序が再表示まで維持される。2枚目だけ失敗した場合などに、成功分の重複アップロードや意図しない欠落を起こさず保存できる。1枚・画像なしの既存経路も確認する。

### P4：運用・性能の整理

- 仮保存ファイルの一覧化・保持期間・整理手順、サムネイル生成と遅延取得、容量管理を仕上げる。
- 自動削除を入れる場合は、参照中画像と保存途中の画像を除外する検証を先に行う。
- 一覧・詳細・複数アップロードの時間と転送量を端末別に測り、枚数・容量の初期案を調整する。

**完了条件**：参照中ファイルを消さない整理手順があり、計測結果から速度・容量の制約を説明できる。自動化が不要なら、手動の整理手順を完成形として記録してよい。

### Gemini側との依存

Drive P1とGemini G1、画像P2aと挨拶推論G2はそれぞれ独立して検証する。日記向けのテキスト推論G3a / G3bは画像側を待たずに進められる。写真1枚の推論G4aはP2b後、複数画像の推論G4bはP3後に実施する。[AI・Gemini方針](AI-Gemini対応.md)

### Phaseごとの完了記録

実装対象・触ったファイル、ローカルテスト、実アカウントでの操作結果、作成した検証ファイル、残った制約を記録する。失敗したらそのPhase内で原因を切り分け、次の機能を積み増さない。今回のPhase整理は文書更新のみで、認証・アップロード・GAS反映は実施しない。
