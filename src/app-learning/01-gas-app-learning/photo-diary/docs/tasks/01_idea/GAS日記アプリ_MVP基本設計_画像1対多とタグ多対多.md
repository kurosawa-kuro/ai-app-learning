## 2. RDB設計

### 2.1 エンティティとリレーション

4テーブル構成。

| テーブル | 説明 | 関係 |
|---|---|---|
| `posts` | 日記投稿 | 親 |
| `images` | 投稿画像 | postsと1:N |
| `tags` | タグマスター | postsとN:M |
| `post_tags` | 投稿・タグ中間テーブル | N:Mの実現 |

### 2.2 リレーション構造

**投稿と画像：1対多**

`posts (1) → (N) images`

1投稿に0枚以上の画像を登録できる。画像1件は投稿1件だけに属する。

**投稿とタグ：多対多**

`posts (1) → (N) post_tags (N) ← (1) tags`

1投稿に複数タグを付けられ、1タグを複数投稿で利用できる。

### 2.3 テーブル定義

#### posts

| カラム | 型相当 | 制約・役割 |
|---|---|---|
| id | string | PK |
| title | string | 必須 |
| body | string | 必須 |
| created_at | datetime | 作成日時 |

#### images

| カラム | 型相当 | 制約・役割 |
|---|---|---|
| id | string | PK |
| post_id | string | FK → posts.id |
| file_id | string | ダミー画像識別子 |
| sort_order | number | 表示順 |

MVPでは `file_id` に `sample-a` などを保存する。

将来Google Driveへ対応した際に、実際のDriveファイルIDへ変更する。

#### tags

| カラム | 型相当 | 制約・役割 |
|---|---|---|
| id | string | PK |
| name | string | UNIQUE相当 |

タグ名は重複させない。MVPでは初期マスターを用意し、タグ管理ページは作らない。

#### post_tags

| カラム | 型相当 | 制約・役割 |
|---|---|---|
| post_id | string | FK → posts.id |
| tag_id | string | FK → tags.id |

`(post_id, tag_id)` を複合主キー相当として扱う。

同じ投稿に同じタグを二重登録しない。

※ Google Sheetsには実際のPK・FK・UNIQUE制約が存在しないため、GAS側で検証する。

### 2.4 サンプルデータ

**posts**

| id | title |
|---|---|
| 1 | カフェに行った |
| 2 | 休日のお出かけ |

**images**

| id | post_id | file_id | sort_order |
|---|---|---|---|
| 101 | 1 | sample-a | 1 |
| 102 | 1 | sample-b | 2 |
| 103 | 2 | sample-c | 1 |

**tags**

| id | name |
|---|---|
| 10 | カフェ |
| 11 | 休日 |
| 12 | スイーツ |

**post_tags**

| post_id | tag_id |
|---|---|
| 1 | 10 |
| 1 | 11 |
| 1 | 12 |
| 2 | 11 |

### 2.5 JOIN相当の処理

Google SheetsにはRDBMSのJOIN機能がない。

GASで必要なシートを一括取得し、JavaScript上で結合する。

- Read-many：投稿一覧に代表画像とタグを付与
- Read-one：投稿1件に全画像と全タグを付与
- タグ検索：post_tagsから対象投稿IDを特定

行単位で何度もSheetsへアクセスせず、一括読み込みを基本とする。

## 3. ページ設計

ページは3つだけ。

| No. | ページ | 主な役割 | 主要処理 |
|---|---|---|---|
| P01 | 日記一覧 | 一覧・タグ検索 | Read-many |
| P02 | 日記作成 | 新規投稿・AI下書き | Create / Mock AI |
| P03 | 日記詳細 | 投稿と関連データ表示 | Read-one |

### P01：日記一覧

**目的：Read-manyとタグを用いた検索**

表示項目：

- 代表画像（ダミー）
- タイトル
- 本文の冒頭
- 投稿日時
- タグ一覧

操作：

- 新規投稿画面へ移動
- 投稿を選んで詳細へ移動
- タグを選んで投稿を絞り込み

データ取得：

`getAll(tagId?)`

取得結果は作成日時の降順。

ページネーションは実装しない。

### P02：日記作成

**目的：複数テーブルへのCreateとAI下書きモック**

入力・表示項目：

| 項目 | 内容 |
|---|---|
| 写真 | ダミー画像を複数選択 |
| キーワード | 既存タグを複数選択 |
| AI下書き | 固定レスポンスの生成ボタン |
| タイトル | 自由入力・AI下書き反映 |
| 本文 | 自由入力・AI下書き反映 |
| 保存 | 日記を新規登録 |

#### AI下書きモック

写真とキーワードを入力して、AI下書き生成ボタンを押す。

`generateDraft(input)` は固定のタイトル・本文を返す。

実際のGemini APIはまだ呼び出さない。

生成された文章は、利用者が自由に編集できる。

#### 保存処理

1. タイトル・本文・タグID・画像IDを検証
2. postsへ投稿を登録
3. imagesへ画像の関連情報を登録
4. post_tagsへタグの関連情報を登録
5. 保存後、日記詳細へ遷移

MVPでは生成用キーワードと保存するタグを兼用する。将来必要になれば、AI入力キーワードと公開タグを分離する。

### P03：日記詳細

**目的：Read-oneと関連データの結合**

表示項目：

- タイトル
- 本文
- 投稿日時
- 全画像（表示順）
- 全タグ

操作：

- 日記一覧へ戻る
- タグ選択で一覧の該当タグ絞り込みへ移動

データ取得：

`getOne(postId)`

存在しないIDの場合は「日記が見つかりません」と表示。

編集・削除ボタンは設置しない。

## 4. GAS処理設計

### 4.1 主要関数

| 関数 | 用途 | 対象テーブル |
|---|---|---|
| `create(data)` | 日記登録 | posts, images, post_tags |
| `getAll(tagId)` | 日記一覧・検索 | posts, images, tags, post_tags |
| `getOne(id)` | 日記詳細 | posts, images, tags, post_tags |
| `generateDraft(input)` | 固定AIレスポンス | なし |

加えて、GAS Webアプリの入口に `doGet()` を用意する。

タグマスターは初期表示時に取得するか、一覧取得レスポンスに含める。独立したタグCRUDは作らない。

### 4.2 Createの入力例

```json
{
  "title": "カフェに行った",
  "body": "今日はカフェでケーキを食べた。",
  "imageIds": ["sample-a", "sample-b"],
  "tagIds": ["10", "11", "12"]
}
```

### 4.3 Read-oneの出力例

```json
{
  "id": "1",
  "title": "カフェに行った",
  "body": "今日はカフェでケーキを食べた。",
  "created_at": "2026-10-24T10:00:00+09:00",
  "images": [
    {
      "file_id": "sample-a",
      "sort_order": 1
    },
    {
      "file_id": "sample-b",
      "sort_order": 2
    }
  ],
  "tags": [
    { "id": "10", "name": "カフェ" },
    { "id": "11", "name": "休日" },
    { "id": "12", "name": "スイーツ" }
  ]
}
```

### 4.4 GAS側の役割

- `SpreadsheetApp` によるデータ取得・保存
- 配列・Mapを利用したJOIN相当の処理
- ID生成
- 入力値検証
- 関連データの存在確認
- 重複紐付けの防止
- エラー処理

`google.script.run` でフロントからサーバー関数を非同期呼び出しする。

## 6. 整合性・制約

Google SheetsはRDBMSではないため、次の制御はアプリ側の責務とする。

### 最低限のチェック

- 投稿IDの一意性
- 存在するタグIDだけを受け付ける
- 不正な画像IDを拒否する
- post_tagsの重複登録防止
- 不正な投稿IDへのアクセス時のエラー処理

### 複数シートへの保存

GASにはRDBMS相当のトランザクションがない。

投稿保存時には、事前検証を完了してから書き込みを開始する。

小規模な学習用PoCでは正常系を先に完成させるが、書き込み途中で失敗した場合の不完全データ検出・復旧は、本番移行前の必須対応とする。

同時作成が必要になった場合は `LockService` 等を利用する。

## 10. 実装メモ（2026-10-24）

MVP の範囲（3 ページ × 4 シート × 4 主要処理）はすべて実装した。完了条件（9 章）は `src/tests/` で確かめている（@5 の時点で 21 項目、今は 48 項目）。GAS 実機（特にスマホ）での確認は未了（R1）。

### 設計から変えた点

| 設計 | 実装 | 理由 |
|---|---|---|
| CSS は素の CSS（フレームワークなし） | admin-pico（Pico CSS ＋ admin-* の 3 ファイル。`src/client/vendor/admin-pico/`）に統一。配色は明るくガーリー・ポップ（@9） | owner が先にデザインテンプレートでの統一を決めていた。足りない部品だけ `src/client/styles/` に置く |
| ファイルは `Code.js` と `Index.html` の 2 つ | サーバーは `src/server/` の層ごとのファイル、画面は `src/client/` の部品とビューごとの HTML に分ける（@8） | GAS の公式ベストプラクティス（HTML・CSS・JS を分けて include）と、owner の指摘（責任を 1 つのファイルに混ぜない）。ローカルを `.js` で統一する点は設計どおり |
| 保存の順は posts → images → post_tags | images → post_tags → posts（親を最後） | 途中で失敗しても、親の無い子は一覧にも詳細にも出ない（結合は posts から始まる）。6 章の「不完全データ」への最小の手当て |
| ダミー画像（`sample-a` など） | 画面側（`App.photoView`）で、写真の提供元が返す色と名前から SVG を描く。目録は `data/sample-data.yaml` | GAS は画像ファイルを配れず、外部への通信は Pico の CDN だけという約束のため |
| タグマスターは初期表示時に取得するか、一覧の応答に含める | 両方。初期表示で `CONFIG.tags` に入れ、`getAll` の応答でも更新する | シートでタグを足したとき、再取得で画面に反映される |
| Read-many は代表画像とタグを付ける（4.1） | 一覧の 1 件に本文と全画像も入れる（@10） | 詳細を往復なしで出すため（`docs/tasks/02_backlog/GAS性能_調査と対応方針.md` 対応 B）。`getOne` は URL で詳細を直接開いたときだけ使う |
| 初期表示の後に一覧を取得する（P01） | 最初の HTML に一覧を入れて返す（@10） | 開くときの往復を 1 回減らす（同 対応 A） |
| 行単位で何度も Sheets へアクセスせず、一括読み込み（2.5） | さらに、読んだ表を `CacheService` に置き、次からは Sheets を読まない（@11）。保存の後も読み直さない | 実機で 1 表の読みが約 0.5 秒かかったため（同 対応 E・D） |

### 設計に足した点

- **二重送信の防止**：作成画面を開くたびに `requestId` を作り、`create(data, requestId)` に渡す。同じ値の再送は `CacheService` に 10 分残した前の結果を返し、新しい行を作らない
- **数値・日付への化けの防止**：Sheets は `"10"` を数値に、`"3/4"` を日付に変える。ID・タイトル・本文の列は、書く前に書式を「書式なしテキスト」にする
- **重複の扱い**：同じ写真・同じタグを複数回送られたら 1 つにまとめる（post_tags の二重登録を防ぐ）。目録に無い写真、tags に無いタグは書き込む前に拒否する
- **初期データ**：シートを新しく作ったときだけ、2.4 のサンプル（投稿 2・画像 3・タグ 3 ＋ 追加 5）を入れる
- **画面の URL**：`#tag-11`（一覧の絞り込み）、`#new`（作成）、`#post-<id>`（詳細）。スマホの「戻る」でアプリの中を戻れる
- **書籍管理（books）の廃止**：owner 決定（2026-10-24）。前の題材のシート `books` は、次に開いたときに自動で消える（`data/config.yaml` の `retiredSheets`）
- **設定とデータの分離**：アプリ名・上限などの設定は `data/config.yaml`、タグマスターは `data/tags.csv`、写真の目録・サンプル日記・AI 下書きの固定文は `data/sample-data.yaml` に置く。GAS はローカルのファイルを読めないので、`npm run build:data` が検証してから `src/server/config/generated.js`（`APP_CONFIG` / `APP_DATA`）に書き出す。サンプル日記が無いタグや写真を指すなどの壊れは、push の前に理由つきで止まる
- **MVC・単一責任への分割**（2026-10-24、owner 指摘）：サーバーを controllers / services / models / presenters / db に、画面を core / views / app に分けた。写真と AI 下書きは差し替えられる提供元（`data/config.yaml` の `providers`）にした。4.1 の関数名（`create` / `getAll` / `getOne` / `generateDraft`）は `server/controllers/api.js` の公開関数として保っている。詳細は `docs/tasks/02_backlog/リファクタリング方針.md`
