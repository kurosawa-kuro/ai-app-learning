# Spring Bootスターターテンプレート仕様

2026-10-27時点の実装仕様。起動・設定・検証記録は[README](README.md)に記載する。

## 目的と現在の範囲

提供者が、Java・Spring Bootで「ユーザー1人に複数の投稿」という小さな題材を実装・検証し、AIとの改修・結果確認へ再利用できる土台を用意する。GAS版の完成や、学習者による全技術の習得を前提にしない。

**管理画面を前提とするスターター**とし、ユーザー管理・機能管理を初めから備える。ログイン機能がないGASアプリも想定した設計方針であり、GASへ移植した実装ではない。投稿は共通管理機能の利用例とする。ユーザーの指示により、**現在はユーザー認証を実装しない**。Userは投稿者データとして扱う。Storageなしでもテキスト投稿が動く構成とする。

## 実行構成

```text
Windowsのブラウザー
  → WindowsのSpring Boot / Thymeleaf（127.0.0.1）
      ├─ Supabase PostgreSQL（ユーザー・投稿・画像の参照・管理設定）
      └─ 画像の保存・表示・削除：Supabase Storage（非公開バケット）
```

- Java 17 / Spring Boot 4.1.2 / Maven。初期生成はSpring Initializr。
- 開発用SupabaseはTokyo。PostgreSQLはSession poolerの5432番へ証明書・ホスト名検証付きで接続する。
- Mac miniのDB・SSHトンネル・WindowsへのDocker導入は使わない。
- Data APIはOFF。Supabase Authは今回利用しない。
- 公開先はRender。Dockerfile・render.yaml・`render` プロファイルを用意し、画像OFFで動作を確認済み。認証・アプリ専用DBロールがないため常時公開は前提にしない。現在の認証なし構成はローカル利用を初期設定とする。

## データモデル

```text
app_users（User）1 ── 多 posts（Post）
                           └─ 任意の添付画像 0〜1枚
```

| テーブル | 項目・制約 |
|---|---|
| app_users | UUIDのid、1〜80文字のname、created_at |
| posts | UUIDのid、必須のuser_id、1〜120文字のtitle、5000文字以内のbody、created_at |
| posts内の画像情報 | image_bucket、image_key、image_type。画像なしではすべてNULL |
| app_settings | id=1の1行。images_enabled、ai_enabled、default_user_id、updated_at。アプリ全体で共有 |

- `posts.user_id` は `app_users.id` への外部キー。投稿が残る投稿者の削除はDBでも拒否する。
- アプリのUser IDは独立したUUID。Supabase Authのユーザー作成や外部キーを前提にしない。
- `app_settings.default_user_id` は `app_users.id` への外部キー。対象ユーザーの削除時はNULLへ戻す。
- 通常の専用スキーマは `app_template`。Flywayでバージョン管理し、初回起動時に作成する。
- RLSは有効にするが、現在の管理用DB接続はRLSによる利用者分離を提供しない。Data APIロールへのテーブル権限は与えない。

## 画面・操作

詳細な部品の責務・拡張方法は[共通UI設計](docs/ui-foundation.md)を正本とする。配色は写真日記のパレットを移植し、淡いピンクの背景・白い面・ピンクからパープルのグラデーション・パステルの補助色を使う。同梱admin-picoとPico CSSの部品・レイアウトを維持する。`templates/ui` と `static/ui` にAppShell・PageLayout・PageHeader・Form・List・Detail・Feedbackを分離し、投稿固有の状態とURLを共通シェルへ持ち込まない。

| 画面 | URL | kind / 上限 | 内容 |
|---|---|---|---|
| 投稿一覧 | `/posts` | standard / 1200px | 件数・絞込み・一覧。0件と絞込み0件を区別 |
| 投稿詳細 | `/posts/{id}` | detail / 960px | 補足情報→本文・画像→次の操作→削除。本文40em以内 |
| 新規投稿 | `/posts/new` | form / 800px | 投稿者の確認・変更・追加、タイトル・本文・画像 |
| 管理画面 | `/admin` | standard / 1200px | ユーザー管理・機能管理の入口 |
| ユーザー管理 | `/admin/users` | standard / 1200px | 作成・選択・デフォルト指定・削除 |
| 機能管理 | `/admin/settings` | form / 800px | 画像投稿・AI連携の許可／禁止 |
| ゲームUI体験 | `/examples/skill-janken` | play / 960px | サイドバーなし。仲間・スキル・手の選択→決定→結果 |

- 見出し・主操作・本文を一つのPageLayoutに収め、基準線と最大幅をそろえる。個別画面で独自の最大幅を追加しない。
- ナビは `UiContext` に定義し、PCとモバイルで同じリンクを描画する。投稿・管理は1024px以下でドロワー、768px以下では表を縦積みする。ゲームは上部ナビと中央の操作領域を使う。
- 投稿者はフォーム冒頭で確認・変更する。URLの明示指定→選択済みCookie→DBのデフォルト→未選択の順で初期値を決める。フォーム内の追加・選択は下書きを維持する。一覧の絞込みは投稿先を変えない。
- サイドバーをアプリのリンク・「管理・設定」ポップアップ・左下のユーザー切替に分ける。管理メニューはユーザー管理・機能管理・CSV出力・管理の一覧へ誘導する。追加・削除・機能設定の編集は専用画面に残す。
- 左下のユーザー名から検索付きポップアップで選択する。CSRF付きPOSTでCookieを更新し、画面遷移しない。投稿フォームでは入力・添付を保ったまま投稿者を更新し、既存投稿とDBのデフォルトは変更しない。読み込み・失敗・空一覧を表示し、名前はHTMLとして解釈しない。
- ポップアップは同時に一つ、Esc・外側クリック・閉じるボタンで閉じる。キーボードで操作でき、Escで開いたボタンへ戻す。スマホのEscはまずポップアップだけを閉じ、もう一度でドロワーを閉じる。
- ラベル・必須／任意・補足・項目エラーとエラー概要を共通化する。本文16px・補足14px、主要操作の高さ44px以上を基準とする。
- JavaScript有効時の投稿は同じ文書内で送信し、成功後に詳細へ移動する。通信・DB・画像エラーで本文や選択画像を消さず、再試行を案内する。通信断は保存結果が不明なため、一覧確認を案内し自動再送しない。
- クライアントで5MB超を送信前に止める。サーバーの容量・内容検証も残す。通常のHTML POSTに戻った場合、画像の再選択を案内する。サーバーがリクエスト全体を拒否した場合の通常POSTの下書き復元は保証しない。
- 保存中はボタンを無効化する。削除は対象名を示す共通ダイアログで確認し、初期フォーカスはキャンセル。Escapeで閉じて元のボタンへ戻る。
- ドロワーを開いている間は本文を操作対象から外し、Tabをメニュー内に収める。閉じたらメニューボタンへ戻す。
- 投稿が残るユーザーは削除できない。存在しない投稿は404。旧 `/users`・`/settings` は管理画面へ転送する。
- ゲームUI体験は固定サンプルで、GASの所有状態・保存・AIには接続しない。体験用であることを画面に明記し、GAS移植完了と扱わない。

投稿の編集・並べ替え・複数画像・アカウント登録は今回含めない。ユーザーの選択は本人確認を意味しない。

## 認証とフォーム保護

ログイン画面、パスワード管理、認証トークン検証は組み込まない。Spring Securityはログインを無効化し、CSRFとセキュリティヘッダーのために残す。全ルートを認証なしで利用できる。

画面へアクセスできる人は全ユーザー・投稿・管理設定を扱える。管理画面は機能の分類であり、管理者権限を提供するものではない。初期のバインド先はlocalhostとする。認証が必要になった段階でSupabase Auth等を追加し、ユーザーとの対応付け・操作権限を設計する。

## 管理画面の共通設定

- `AppSettings` と `app_settings` を正本にし、同じスキーマの全ユーザー・ブラウザー・サーバーで共有する。毎回DBから読み、保存後のリクエストで反映する。処理開始済みの投稿やAI処理を途中で取り消す設定ではない。
- 画像投稿とAI連携は1回のUPDATEで保存する。保存前のStorage確認が失敗したら、どちらも更新せず入力とエラーを表示する。保存中表示・二重送信抑止・変更取消を備える。
- `APP_IMAGES_ENABLED` と `-Images` は設定行がないときの初期値のみ。既存設定を再起動で上書きしない。AI連携は初期値禁止、デフォルトユーザーは初期値未指定。
- 画像許可で保存する際はStorageの非公開バケットを確認し、なければ作成する。接続情報が未設定・接続失敗なら許可を保存しない。
- 機能管理の見出しと本文は最大800px。admin-picoのカードとスイッチを利用し、投稿・AI連携をカテゴリで分ける。
- AI連携は許可／禁止設定と `AppSettings.requireAiEnabled()` のみ実装。AI処理・接続先・課金は未接続であることを画面に明記する。将来のAI呼出しは必ずサーバー側でこの判定を通す。
- 次の機能は新しいマイグレーションと型付き設定・カテゴリを追加して拡張する。接続秘密情報は画面や設定テーブルに持たせず環境変数で管理する。

AI連携カードに「今日使ったAI金額」「今月使ったAI金額」「今まで使ったAI金額」を表示する。アプリ全体の金額を円で示し、PCでは3列、スマホでは縦に並べる。現在は128円・2,480円・12,640円の固定値で、「ダミーデータ」「実際の利用・請求額ではない」と明記する。許可設定と独立した読み取り専用の表示で、外部通信・実額集計・課金連携は行わない。

## CSVエクスポート

管理画面からユーザー・投稿を個別のCSVに出力する。全件出力とし、ユーザー選択・一覧フィルターとは独立させる。UTF-8 BOM・CRLF・日本語の列名・日本時間の日時で、Excelでの閲覧を想定する。すべての項目を二重引用符で囲み、引用符・改行を正しく扱う。数式として解釈され得る値はアポストロフィで文字列化する。

ユーザーIDと投稿のユーザーIDで関連を追えるようにし、画像は添付の有無だけを出力する。画像実体・Storage内部パス・秘密情報・管理設定は出力しない。DB取得失敗時はCSVのダウンロードを成功扱いにせず、再試行を案内する。現段階では全件をメモリ上で組み立てる小規模教材向けの実装とする。大量データ向けの分割・ストリーミングと、アプリ別のインポートは後続対応。

## オプションの画像機能

- 初期値はOFF。管理画面の「機能管理」で許可／禁止を変更する。
- OFF時はStorageのURL・キーがなくても起動でき、ファイル選択欄は表示しない。サーバーも画像付きの送信を拒否する。
- ON時も添付は任意。JPEG・PNGを1枚、5MB・1600万画素以下とする。
- ファイルの内容をデコードして形式・サイズを確認し、再エンコードして保存する。申告MIMEや拡張子だけを信用しない。SVGや他形式は対象外。
- バケットは非公開。画像許可の保存時と画像投稿時に存在を確認し、未作成なら非公開で作成する。既存の公開バケットを自動で非公開に変更せず、エラーとする。
- DBはバケット名・UUIDのオブジェクトキー・画像形式を保持する。元ファイル名や期限付きURLを保存しない。
- Spring BootがStorage APIから取得して画像を返す。ブラウザーへサーバーキーを渡さない。現在は認証なしなので、アプリ経由で画像を閲覧できる利用者の範囲はアプリへの接続範囲と同じ。
- OFFへ戻しても既存画像の表示・削除を妨げず、DB・Storageの画像を自動では消さない。Storageの接続情報は引き続き必要。禁止するのは新しい添付であり、古いフォームや直接POSTでもサーバーが拒否する。

画像保存後のDB保存失敗には削除で補償する。削除も失敗した場合はバケット名・オブジェクト名をログへ記録し、DB参照を確認して残存画像だけ後片付けする。投稿削除時はStorage削除を先行し、Storage障害ではDBレコードを残して再試行する。DBとStorageをまたぐ原子的な保存・削除や、プロセス停止後の自動復旧は保証しない。

## UI確認用シード

- 提供者が専用コマンドで、架空の3ユーザー・8投稿を投入する。通常起動では既存データへ触れない。
- 短文・長文・段落・英語・日付の分散・投稿者別の複数投稿で、一覧と詳細の見え方を確認する。画像許可ON時はオリジナルの図2枚を添付し、OFF時はテキストだけにする。
- 追加モードは固定IDの未登録投稿だけを追加する。リセットモードは対象スキーマの全投稿を置換する。既存ユーザー・デフォルト・選択Cookie・機能設定は維持する。
- 画像を先に準備し、DBの削除・登録は一つのトランザクションで行う。成功後、旧投稿に紐づくStorage画像だけ削除する。失敗した後片付けは専用キューへ残し、参照中の画像は削除しない。
- 操作は開発スキーマ `app_template` とテスト専用 `app_template_seed_test` に限定する。共有DBへの即時反映と全投稿削除の範囲を、[READMEの手順](README.md#ui確認用のシードデータ)に明記する。
- リセット・冪等性・設定維持・画像準備失敗・DBロールバック・削除再試行を専用スキーマでテストする。

## ユーザーアイコンと画像表示

- 投稿画像は保存前のプレビュー、一覧サムネイル、詳細表示に対応する。投稿の画像許可設定を維持し、画像なしの投稿も可能とする。
- ユーザーアイコンは `user_icons` でUser 1：Icon 0〜1を管理する。JPEG・PNGを5MB・1600万画素まで検証し、中央を切り抜いた256px四方のPNGへ変換する。ユーザー管理の専用画面で登録・変更・削除する。
- アイコンの利用は投稿画像の許可設定とは独立し、Storageの接続設定を必要とする。投稿と同じ非公開バケット、UUIDオブジェクトキー、サーバー経由の表示を用いる。
- 左下・切替ポップアップ・ユーザー一覧・投稿一覧・詳細の投稿者に表示する。未設定・読み込み失敗時は頭文字へ戻す。
- 差し替えはアップロード後にDBを更新し、成功後に旧画像を削除する。ユーザー行をロックし、差し替え・ユーザー削除の競合を防ぐ。投稿があるユーザーの削除はDB制約で拒否し、アイコンも保持する。
- 旧画像の削除は共通 `image_cleanup` キューへ記録する。後片付けでは投稿・アイコンの現行参照を確認し、参照中の画像を削除しない。シードのリセットはユーザーアイコンを保持する。CSVには画像実体やStorageパスを含めない。

## 秘密情報

DBパスワード・Storageのサーバーキー・Render APIキー・環境ごとの初期値はGit管理対象外の `.env` または環境変数で管理する。Render APIキーは運用スクリプト専用とし、アプリのプロセスへ渡さない。共有するのは値を含まない `.env.example` のみとし、旧 `.secret` は廃止する。起動スクリプトがKEY=value形式を安全に読み、既存の環境変数を優先する。起動引数とテスト用の分離設定はさらに優先する。ソース・HTML・ログ・テスト証跡へキーを含めない。JDBC用CAは公開証明書として同梱する。

現在はDashboardが提供する管理用DB接続を使う。外部公開前のアプリ専用DBロール、最小権限、認証・認可は別途設計する。

## 検証と完了条件

Playwrightは提供者の動作確認負担を減らすために必須とする。学習者全員にテストツールの習得を要求する意味ではない。

- Javaテスト：実PostgreSQLへの接続、SQL・日本語データの往復、画像内容・サイズ検証、画像OFF時の拒否、DB保存失敗時の画像削除、Storage削除失敗時のDB保持。
- 管理設定：別インスタンスからの再読込み、初期値による上書き防止、デフォルトとCookieの優先順位、デフォルト対象削除、Storage接続失敗時の非更新。
- Playwright：サイドバーでの画面移動、投稿者の追加・選択と記憶、入力エラー時の入力保持、同じ投稿者への複数投稿、詳細表示、再読込後の一覧、投稿者による絞込み、確認つき削除、404画面、CSRF拒否、モバイルでの横はみ出しなし。
- 画像ONでは実Supabase Storageへアップロードし、再読込後に画像が実際に読み込めたことを確認する。不正画像の拒否も確認する。
- 管理画面は別ブラウザーへの設定反映、取消、CSRF拒否、古いフォームからの画像送信拒否、禁止後の既存画像の表示・削除を確認。機能管理は390・820・1280・1920pxで表示を確認する。
- Javaテストは `app_template_test`、シードの置換試験は `app_template_seed_test`、E2Eは `app_template_e2e_text` と `app_template_e2e_images` を使い、通常の開発データと分離する。
- 画像E2Eは専用の非公開バケット `template-post-images-e2e` を使う。自分で作成した投稿者・投稿・画像のみ後片付けする。
- 模擬した障害試験と実サービスの正常系試験を区別する。失敗時のスクリーンショット・トレースはGit管理対象外に保存する。

2026-10-27、共通UI改修版でJava 13件・Playwright 10件が成功。画像OFFの実Storage専用ケースと画像ON側の重複ゲームケースの2件は対象外。390・768・1280・1920pxの投稿・管理・ゲーム画面を検証し、画像でも配置を確認した。今回の改修版はローカル検証済みでRenderへは未反映。GASゲームの移植やAI処理の接続は含まない。詳細はREADMEの検証記録を参照。

## 今後、必要になったときに決めること

- 投稿編集、複数画像、他の画像形式、一覧のページ分割。
- Supabase Authなどによる認証と、ユーザー・投稿・画像の操作権限。
- 実利用用SupabaseとRenderの公開設定・費用・バックアップ・運用。
- DBとStorage間の障害・プロセス停止からの自動復旧。
