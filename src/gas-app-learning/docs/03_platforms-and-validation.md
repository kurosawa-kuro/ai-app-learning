# 技術基盤と検証：同じ題材を段階的に深める

[全体案内](../README.md) · [出典・編集対応表](reference/00_source-map.md)

状態：**基盤展開の方針・検証計画**。Spring Boot＋Thymeleaf＋Render＋Supabase版は今後の準備対象。今回の文書整理では、移植・配置変更・テスト実行・実環境受入・公開を行っていない。

## 題材を固定し技術レベルを広げる

2026-10-27の[採用決定](../../../docs/adr/0001-web-app-stack.md)により、発展版のNext.js＋Vercel案は廃止し、Spring Boot＋Thymeleaf＋Render＋Supabaseに統一した。[Webアプリ支援戦略](../../web-app-starter/GASではなくSpringBoot-render-supabase戦略.md)の構成と検証方針に従う。DBはPostgreSQL、Storageは必要時に利用する。既存GAS版の個別仕様は維持する。

サーバー側の認可、DB接続ロール、データの公開範囲を設計し、必要なRLSが実際の接続経路で有効かを検証する。技術の共通化と、利用者のゴール・スタート支援・成功条件の共通化は分ける。Oracle固有の実習は資格学習側で行う。

### 同じ題材に2つの模範実装

既存の5教材に対し、**GAS版**と**Spring Boot＋Thymeleaf＋Render＋Supabase版**を模範実装として用意する方針。模範実装は単一のコード上の正解ではなく、同じ仕様・受入条件を満たす検証済みの比較対象とする。発展版は今後の準備対象であり、現行GAS版も検証状況はプロジェクト一覧に従う。

| 学習の入口・発展 | 技術・道具 | 学ぶこと |
|---|---|---|
| Level 1：GAS | Google Apps Script＋Google Sheets | データの関係、登録・参照、業務ルール、AIへの開発指示。更新・削除は各アプリの仕様に応じて扱う |
| Level 2：Web開発 | Spring Boot＋Thymeleaf＋Render＋Supabase | Java・SQL、画面とフォーム、リレーショナルDB、認証・認可、デプロイ、テスト、運用 |
| Level 3：AIによる改善 | Devin等＋仕様・テスト・模範実装 | 独自要件を整理し、AIの変更案を検証・比較して改善する |

GASを修了しなければ発展版へ進めない、という制約は設けない。経験・関心・目的に応じて入口を選ぶ。Level 3のAI活用は両基盤で行え、本人の理解・判断・検証を伴う改善を目指す。

| 既存教材 | GAS版を通じて学ぶこと | 発展版で深める観点 |
|---|---|---|
| skill-janken | 条件分岐・状態管理・仲間とスキルの関係 | ゲームロジックとDB設計、更新の整合性 |
| ai-english-trainer | AI API・問題と回答・評価・学習履歴 | 認証・AI連携・学習データの管理 |
| ai-photo-diary | 写真・日記の登録と参照・タグ | Storage、リレーショナルDB、画像と記録の権限 |
| cast-evaluation-system | 実績・評価ルール・期間集計 | サーバー側の認可、DB権限、複数利用者を扱う場合のデータ分離 |
| ec-shop | 商品・注文・明細・確定時点の保存 | 注文整合性、DBトランザクション |

発展の観点を、現在のGAS版の追加要件にしない。特にキャスト用画面・複数店舗・複数利用者への拡張は、既存の管理者限定MVPとは別に範囲と受入条件を決める。認証機構が異なっても、同じ基本課題では元の利用者・公開範囲を尊重する。

### 正解は共通の受入条件で判断する

学習サイクルは **AIに開発・改修を依頼 → 自分で検証 → 模範実装と比較 → 理由を説明して改善** とする。比較前に期待する結果を言葉にし、実際の動作とデータで確かめる。

同じ教材のGAS版、Spring Boot版、学習者の実装で共通にするのは業務要件・入力例・期待結果・守るべき制約。異なる5教材の業務ルールまで同一化するものではない。見た目やコード構造が違っても、合意した仕様と受入条件を満たせば正解とする。模範コードの丸写しを合格条件にしない。

| 共通化するもの | 基盤ごとに用意するもの |
|---|---|
| 機能仕様、非対象、利用者と公開範囲 | GAS／SheetsまたはSpring Boot／Thymeleaf／Render／Supabaseの具体構成 |
| データの意味、業務ルール、入力と期待値 | 物理スキーマ、通信、認証・認可の実装 |
| 中核の操作シナリオ・受入テスト仕様 | 各環境で動かすテストコード・テストデータの投入方法 |
| 学習目標、問いかけ、変更課題 | 導入・公開・復旧手順、画面操作の動画 |
| 仕様版と受入条件の対応 | 実装版・検証結果・既知の差分 |

同じテストコードを無理に共用するのではなく、同じ受入テスト仕様を各基盤で実行できる形にする。DBや認証の違いによる検証は、共通の業務テストに加えて行う。

たとえばキャスト評価では、期間合計後のポイント計算、同点順位、重複防止、退店後の実績保持を共通条件にできる。一方、ルール履歴やキャスト用画面を追加する課題は拡張仕様として分け、元の正解を暗黙に変更しない。

### 教材の管理構成案

```text
skill-janken/
├── spec/       # 共通の機能仕様・非対象
├── gas/        # GAS模範実装
├── spring-boot/     # Spring Boot＋Thymeleaf＋Render＋Supabase模範実装
├── tests/      # 共通の受入テスト仕様・入力例・期待値
└── lessons/    # 記事・動画・AI演習
```

これは将来の整理案であり、現在のファイル配置ではない。既存のsrc/・docs/等から直ちに移動せず、発展版を作る題材を選んだ時点で移行方法と参照を設計する。同じ役割を既存の構成で満たせるなら、名前を揃えるためだけに移動しない。

模範解答にはコードに加え、仕様、データ設計の理由、テスト、導入・運用・復旧手順、学習者が比較する観点を含める。記事・動画と両実装がどの仕様版に対応するかを記録する。

### 10実装を抱え込まない進め方

最初に選ぶのは1題材。利用実績・教育効果・現行版の安定性・発展版で学ぶ価値を見て選び、GAS版と発展版を共通条件で検証してから、他の題材へ進む。

5教材×2基盤の保守負担を前提に、共通仕様と実装差分を分け、変更時には両版への影響を確認する。未対応の版は未対応と明記し、仕様も挙動も揃っていない状態を同等の模範実装として配布しない。

Spring Boot版はGASコードの単純変換で完成としない。認証、サーバー側の認可、DB接続ロールと必要なRLS、許可されていないデータへのアクセス拒否、Storageの公開範囲、秘密情報、AIの外部送信、注文等の更新整合性を、その環境で検証する。具体的な構成・コマンド・サービス条件は実装時に公式情報と照合する。

対面30分×3回は初期導入・理解・AI活用の伴走の構成案。90分で全基盤を習得させるものではなく、その後も記事・動画・模範実装を使って同じ題材を深められるようにする。

## 教材提供前の検証と教育モデルの検証

プロジェクト一覧の実装状況と、教材として提供できる状態は分けて管理する。

| 段階 | 確認すること |
|---|---|
| ローカル | 配布対象の最新版でテストと画面確認を行う |
| 実環境 | 実GAS・Sheetsと、採用しているDrive・AIサービスで主要操作を確認する |
| コピー・引き渡し | 新規環境で初期設定・権限・保存先を確認し、元のデータや秘密情報が混入しないことを確かめる |
| 教材との一致 | 配布版と記事・動画の手順を揃え、学習者または保護者・講師が再現できるか確認する |
| 少人数の指導 | 各対象者の成功条件、必要な介助、所要時間、次も改善したいかを観測する |

提供者管理端末で使う子供向けと、本人の環境へ導入する成人向けでは、引き渡し・準備の条件を分ける。公開環境が既にあるアプリでも、最新版の受入やコピー先での動作を省略しない。キャスト評価は設計段階から検証用MVPを用意する必要がある。

検証結果は、アプリが動いたこと、本人が理解して変更できたこと、指導時間・支援負担、支払い意思を分けて記録する。教育効果や販売需要を、既存の相談があることだけで実証済みにはしない。


## 検証記録の共通書式

以下は今後の記録用書式であり、今回検証を実施した記録ではない。個別プロジェクトに既存の記録様式がある場合はそれを正本とし、必要な項目を対応付ける。

| 記録項目 | 記載内容 |
|---|---|
| 対象 | プロジェクト、基盤、仕様版、実装版、教材版 |
| 環境と範囲 | ローカル／実環境／コピー先、利用者、公開範囲、対象操作 |
| 受入条件 | 前提データ、入力・操作、期待する画面・保存結果、守る制約 |
| 結果と根拠 | 実施日、実測結果、合否、証跡への参照、未実施・対象外の理由 |
| 差分と残件 | 両基盤の差分、未確認事項、不具合、次の検証 |
| 引き渡し・復旧 | 初期設定と権限、コード・データ・設定の退避と復旧の確認 |
| 教育の観測 | 本人の説明・操作、必要な介助、所要時間、次の改善意欲 |

ローカル合格だけで「実環境受入済み」、過去版の合格だけで「最新版検証済み」、公開URLがあるだけで「コピー配布可能」と記載しない。


## 今後の進め方

当面は事業化と新規題材の追加を行わず、既存5教材を深める。[役割分担と全体最適化](01_portfolio.md#5教材の役割分担と全体最適化) を先に判断基準とし、機能の重複を薄くすることと、必要な基本機能を削ることを混同しない。

1. **現在のGAS版を検証する。** 最新の変更、実GAS環境での主要操作、コピー・引き渡し・復旧を確認する。設計段階のEC・キャスト評価は小さなMVPを具体化する。
2. **共通仕様と受入条件を整える。** 個別アプリの正本から業務要件・非対象・利用者・入力例・期待値を整理し、学習者の実装にも使える確認方法を用意する。
3. **最初の1題材を選ぶ。** 実際の利用・学習体験、現行版の安定性、発展版で学ぶ価値を基に選ぶ。全5教材を一括で移植しない。
4. **発展版の模範実装を用意する。** Spring Boot＋Thymeleaf＋Render＋Supabaseで同じ基本要件を満たし、共通の受入条件と基盤固有の権限・保存・運用を検証する。
5. **説明と演習へ落とし込む。** 記事・動画・AIへの改修依頼・比較観点を揃え、共通6工程と対面30分×3回の指導案で、本人が変更・検証・説明できるか確認する。
6. **教材資産として蓄積する。** つまずきと支援工数を記録し、共通手順へ戻す。他の題材の発展版は教育効果と保守余力を確認して追加する。
7. **横断レビューで再整理する。** 各題材の両版が揃うごとに確認し、比較材料が揃った時点でPortfolio Architecture Reviewを行う。専門性の強化、重複機能の簡素化、共通教材への整理を判断し、個別仕様と検証へ反映する。

将来事業化を検討するときに、需要・支払い意思・価格・有料伴走後の自立を検証する。現在の準備と有料募集を混同しない。銀行・転職等の応用例やAI利用金額の案は参照として保持し、実装範囲へ自動的に追加しない。

GAS版と発展版は基盤が違っても同じ業務要件を満たす比較対象とする。仕様を満たす方法は一つに限定せず、AIで作った結果を自分で確かめ、理由を説明できることを到達目標とする。
