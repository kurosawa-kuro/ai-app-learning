# AGENTS.md

AI コーディングエージェント（Claude Code / Codex / GitHub Copilot 等）共通の作業ガイド。
Codex は作業前にこのファイルを読むため、ここには repo 共通方針のみ記す。
ツール固有の指示は各ツールのファイル（例: Claude Code は `CLAUDE.md`）に置く。

## プロジェクト概要

- 目的: 既存店舗システムとの共存を前提に、ガールズバー・スナックのキャスト評価業務だけを最適化する独立型システム。
- 方針: **Small Core / Integration First**。責任範囲は Member → Performance → Evaluation Rule → Evaluation Result。スマートフォン中心の操作を前提とする。
- 初期技術: GAS + Google Sheets + HTML Service、通信は `google.script.run`、バージョン管理はGit / clasp。GASは初期開発・検証用とし、業務モデルをGAS固有の仕組みに依存させない。
- プロダクト仕様の正本: [Cast Evaluation System — プロダクト方針・基本仕様・設計書 v0.3.0（Draft）](<docs/tasks/01_idea/Cast Evaluation System — 基本仕様・設計.md>)。他の文書・雛形と矛盾する場合はこの仕様を優先する。
- 現状: `src/` のアプリケーション実装は未着手。設計上の採用技術・機能と、設定・実装・検証済みの状態を区別する。

## MVPの実装境界

- F01 メンバー管理、F02 営業実績管理、F03 評価ルール管理、F04 月次評価一覧の4機能。UIはメンバー管理・営業実績入力・評価一覧の3画面とし、タッチ操作で主要操作が完結するよう設計する。
- メンバーIDは自動発行する。状態は `ACTIVE` / `INACTIVE`。退店時は削除せず無効化し、過去実績を保持する。本名など不要な個人情報は管理しない。
- 実績はドリンク杯数・ボトル本数・指名件数・同伴件数・個人売上（整数円）の5項目で、すべて0以上の整数。`business_date` + `member_id` を一意に保ち、過去実績も修正可能にする。
- 個人売上の正本は店舗の既存会計・POS等。本システムは確定済みの評価用金額を手入力し、会計・売上確定、自動計算、商品明細、売上按分、自動照合を実装しない。
- データは `members` / `daily_records` / `evaluation_rules` の3シートのみ。型・カラムは正本§10に従い、行番号を業務IDに使わない。評価結果は3シートから都度算出し、固定保存しない。
- `evaluation_rules.category` は `DRINK` / `BOTTLE` / `NOMINATION` / `ACCOMPANIMENT` / `SALES` の固定値。ルールはGoogle Sheetsで直接設定し、専用画面や汎用ルール・ワークフローエンジンを追加しない。
- 配点例は設計確認用の仮設定であり、業界標準ではない。数量4項目は初期有効、個人売上ポイントは初期無効。売上自体の記録・表示・並び替えは対象とする。

### 計算・順位・ルール変更

- **対象期間の数量・金額をキャスト別に集計してから**ポイント計算する。日次で売上ポイントを切り捨てて合算しない。
- 数量4項目: `ポイント = 期間数量 × ポイント単価 / 計算単位`。
- 個人売上: `売上ポイント = floor(期間売上 / 計算単位) × ポイント`。
- 総合ポイントは有効項目の合計。ランキングは総合ポイント降順、同点なら個人売上降順、両方同じなら同順位。個人売上順の表示にも対応する。
- ルール変更時は過去期間も新しいルールで再計算される。運用開始後の変更には管理者の確認が必要。履歴管理は過去結果の固定が必要になった段階で検討する。
- 数量ポイントの端数表示、同順位の次の順位番号、営業日の区切り、具体的な認証方式など正本にない詳細は、実装に必要な段階で判断事項として明示する。正本で定義済みの売上ポイントの切り捨てや同点判定を未定義扱いしない。

### アーキテクチャ・品質

- UI・業務ロジック・Sheetsデータアクセスを分離する。ポイント計算をSheets関数や画面処理へ埋め込まず、独立したロジックとして保持する。
- 過度な抽象化や大量のService・Repositoryクラスを導入しない。将来API・DB基盤へ移行できる余地を残す。
- 管理者限定アクセス、サーバー側入力検証、レコードID、排他制御、重複防止、GASの実行制限を考慮した一括読み書きを必須とする。
- GAS Webアプリの公開・実行権限は運用するGoogleアカウント環境に合わせる。MVPでネイティブアプリは作らない。将来ネイティブ化する場合は独立API基盤を検討し、`google.script.run` 依存UIの単純移植を前提にしない。

## 機能追加の判断

- POS・注文・決済、商品・在庫、勤怠・シフト、顧客・予約、給与計算、会計・税務・経理は原則として本体に実装しない。必要性が生じても既存SaaSの利用・連携を優先する。
- 指名種別、共同売上按分、CSV、POS API連携、ルール履歴、評価ランク、キャスト用画面、ネイティブアプリ、複数店舗は正本§14の条件に応じた検討候補。詳細KPI分析・高度なグラフ・複雑な評価アルゴリズム・時給査定／給与反映もMVP対象外。
- 正本§15の5基準（評価への直接的必要性、既存システムでの代替可否、実店舗の課題確認、評価モデルを変えず実装可能か、未実装でも業務が成立するか）で判断する。未実装でも成立する機能は原則後回しにする。
- Phase 1は最小MVPの検証、Phase 2は実運用で確認した課題の改善、Phase 3は横展開・API／DB・モバイル技術の必要性判断。Phase 2以降の候補を確定仕様にせず、需要確認前のSaaS化を先行しない。
- 二重入力の負担、設定で吸収できないルール、POS相当の機能要求、過大な連携・保守コスト、需要不足は正本§18に従って方針の再検討事項とする。

## 受入・検証

- 正本§16に従い、キャスト登録・編集・在籍状態管理、実績登録・編集、重複防止、ポイント設定・計算、月次一覧・ランキングを確認する。
- スマートフォンでの主要操作、既存POS・会計を変更しない運用、管理者の理解、日次入力の負担も受入対象とする。
- KPIは全キャスト分の日次入力5分以内、営業日の登録継続率90%以上、評価計算のテストケース100%一致、既存業務の変更は原則不要という仮目標。実店舗で検証・調整し、達成済みと記載しない。
- 計算検証では期間集計後の売上切り捨て、有効／無効、数量計算、同点順位、ルール変更後の過去再計算を確認する。データ検証では0以上の整数、重複防止、退店後の実績保持を確認する。
- ローカル検証・GAS実機受入・実店舗での運用検証を区別し、未確認事項を明示する。

## セットアップ / 主要コマンド

`Makefile` の `setup` / `build` / `run` / `dev` / `test` / `fmt` / `lint` はメッセージを出力する雛形。実際の依存取得・ビルド・検証は未実装で、成功終了を検証済みの証拠にしない。GASの接続・公開手順も未整備のため、実装時に実在する手順・コマンドを確認する。

## コーディング規約

- 既存のコード・命名・パターンに合わせる。新規導入より既存の再利用を優先する。
- 変更に対応する実際の検証を行い、実行内容と結果を記録する。テスト・フォーマッタが未整備ならその制約を明示し、雛形コマンドを検証の代用にしない。
- 評価ルールは `evaluation_rules` シートで管理する。開発環境用の `env/config.yaml` / `doppler.yaml` を業務ルールの保存先と混同しない。GASとの設定・秘密情報の連携方法は未定義。ローカル秘密情報（`env/secret.yaml` 等）はコミットしない。

## 探索と出力量

GAS / Retoolを使う場合は[プラットフォームの入口](docs/runbooks/platforms.md)と対象ディレクトリのAGENTS.mdを読む。対象kindではgas-workflow / retool-workflowをCodexとClaudeの両方へ配布する。生成・ローカル検査・公開・実機受入を区別する。

小さな修正は`rg`と必要範囲の読取りを使う。RTKが利用可能ならGit status・Cargo test・pytest・ruff checkを明示的に圧縮できる。正確なdiff・全件一覧・診断原文が必要なら通常コマンドを使う。Serenaは既定無効で、参照調査が必要なセッションだけ有効化する。導入・実利用確認・復元・効果測定は[運用手順](docs/runbooks/ai-coding.md)を参照する。
