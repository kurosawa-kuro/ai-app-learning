## 更新手順

### 保存先ID指定への切替（2026-10-25のレビュー修正・未反映）

今回の修正版は実行時にScript Propertiesの`DIARY_SPREADSHEET_ID`を読み、`openById`で接続する。公開Webアプリで`getActiveSpreadsheet`には依存しない。

1. テスト成功後にコードをpushする。既存の公開版を更新する前に、対象の保存先スプレッドシートから「拡張機能 → Apps Script」を開く。
2. エディタで`bindDatabaseSpreadsheet`を実行する。`bound: true`を確認する。この操作は保存先IDとキャッシュ世代だけを設定し、業務表の作成・移行・削除はしない。既存v2環境で初期化・移行をやり直す必要はない。
3. `inspectApplicationSetup`でDBを確認し、既存デプロイを更新する。公開URLで一覧と保存を確認する。

保存先未登録は`setup_required`で停止する。登録済みIDとエディタの保存先が異なる場合は`setup_conflict`で停止し、自動で切り替えない。スタンドアロンのGASなどエディタにもactiveがない場合は、対象ブックIDを確認してScript Propertiesへ`DIARY_SPREADSHEET_ID`を手動登録する。誤ったIDの訂正は書込停止・バックアップ確認後に行い、`clearDatabaseCache`も実行する。

この修正では、起動JSONの安全な埋め込み、数式風文字列の保存、キャッシュ公開・ロック解除前の書込確定も追加した。実GASの保存・再送・同時実行・性能は公開前後の受入確認で検証する。既に数式化されたデータは自動修復しない。

### 通常の反映

すべて src/ で実行し、各段階が成功したことを確認して次へ進む。

```powershell
npm test
npx clasp show-file-status
npm run push
npm run deploy
```

push は build:data の後に clasp push --force を実行し、GAS のソースを更新する。deploy は既存 ID の更新であり、ビルド・テスト・push は実行しない。push だけでは /exec の公開版は変わらない。既存環境の URL を維持するため、新しいデプロイを作らない。

## DB v2の移行手順（2026-10-25）

この手順は2026-10-25に実行済み。旧表は削除せず、同じブックのv2_表へコピーする。通常起動は旧表を検出して停止するため、v2コードを公開するだけでは利用再開できない。

1. 書込を停止する。単一所有者の全ブラウザ・タブを閉じ、実行中の保存・アップロード・AI処理の終了をApps Script実行履歴で確認する。移行中は公開URLを操作しない。旧公開版も同じブックへ書けるため、コードpushだけでは停止にならない。
2. スプレッドシート全体をコピーしてバックアップを作り、日時・元ID・コピー先を手元に記録する。Drive画像は移動・改名・削除しない。コピーの見出し・件数・日時型を確認し、旧デプロイ版を記録する。
3. srcでnpm test、npm run test:browser、npx clasp show-file-statusを実行。npm run pushでエディタのコードを更新する。この時点では既存/execは旧版。
4. GASエディタでauditDatabaseV2を実行。ok=trueと6表の件数・checksumを確認。不整合は修復方針を決めてから再監査する。監査だけではDrive実体の健全性を保証しない。
5. migrateDatabaseV2をstate=verifiedまで繰り返す。1回最大500行。既にコピーした範囲が一致すれば続行し、不一致なら止まる。旧表に変更が入った場合も止まる。失敗したv2表を独断で消して再開しない。
6. verifyDatabaseV2Filesをresume=falseまで実行。1回最大10画像。所有者・共有・保存先・旧ファイル名・内容hashを検証する。readyのDrive画像がある場合、この検証なしで切替できない。pending／trashedは実画像読取の対象外であり別途監査する。
7. activateDatabaseV2を実行。全対象行と元checksumを再照合後、DB_SCHEMA_VERSION=2を設定する。DB_CACHE_GENERATIONは内部管理値で手動設定しない。
8. npm run deployで既存デプロイを更新。開いていた画面は破棄して新しく開く。既存URLで一覧・画像・順序・生成・手直し保存・同ID再送・未添付整理を確認し、版番号と実環境の結果を記録する。

新規環境はSeederが初期化する。途中で止まった場合のみresumeInitializeDatabaseV2で再開できる。既存データ環境では使わない。必要表が消えた場合はバックアップ復元を先に検討する。

### 中断・復旧

- コピー中の失敗：書込停止を維持し、同じmigrateDatabaseV2を再実行する。checksum／内容不一致は自動修復しない。
- 切替前：旧表は無変更なので旧公開版を維持できる。再開する場合は移行中のv2表を通常運用に使わない。
- 切替後、新規v2書込なし：記録済みの旧公開版へ戻す。v2表は保全し、旧コードは旧表を読む。DB_SCHEMA_VERSIONを手で消す必要はない。再度v2へ進む際には旧表の追加変更を監査する。
- 切替後、新規v2書込あり：旧版へ戻すだけでは新規日記が見えなくなる。書込停止し、v2を修復するか、差分の逆移行を別作業で設計・検証する。自動逆移行ツールはない。旧uploadsの名前・hash・画像ID対応も復元対象。
- AI結果不明：inspectPendingGenerationsで照合。実行終了と15分経過を確認後、エディタからabandonGeneration_(id)を呼ぶ一時ラッパーで明示中止する。画像整理の保護解除も伴うため、実行中には行わない。

本番移行・画像検証・有効化はユーザー提示のGASログ、公開版@18はCLIで確認。実GAS同時実行・実機速度・旧版への復旧成功は未確認。模擬GASのテスト成功をそれらの成功扱いにしない。
