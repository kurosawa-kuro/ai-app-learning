# Devin × GAS｜生成AIアプリ開発・アイデア展開ロードマップ

> 現在は cold/ に置く将来構想。現在の実装範囲は [README](../../../../README.md)・[CLAUDE](../../../../CLAUDE.md)・[AGENTS](../../../../AGENTS.md) を基準とする。写真はダミー、下書きは固定文で、Drive・Gemini は未実装。この構想を実装済み仕様として扱わない。現状の詳細は [docs 索引](../../../00_index.md) を参照する。

作成日：2026-10-24  
ステータス：構想整理

## 1. 結論・基本戦略

**日記 → 写真日記 → AI写真日記 → AI英語日記**

この順序で、同じGAS基盤を使いながら機能を段階的に発展させる。

その後、共通基盤をスタッフポイント管理などの実務アプリに横展開する。

### 最重要方針

- 最初から高機能なアプリを作らない
- 一段階ごとに新しい技術要素を一つずつ追加する
- 前段階の実装を次の段階で再利用する
- Claude Code・Codex・Devinで変更可能な構造にする
- 利用者は完成テンプレートから独自改修を始められる
- 利用者へのGitHubアカウント作成を必須にしない
- 黒澤側の継続サポートを早期終了できる提供モデルにする

## 2. アイデアの展開順序

### Phase α-0：日記アプリ

**テーマ：Webアプリの最小構造を理解する**

技術：

- GAS
- Google Sheets
- HTML / JavaScript
- `google.script.run`

実装機能：

1. Create：日記投稿
2. Read-one：日記詳細
3. Read-many：日記一覧

データ：

`id / title / body / created_at`

実装しないもの：

- ログイン機能
- 画像アップロード
- Update / Delete
- CSSフレームワーク
- AI連携

**検証目的：GASからGoogle Sheetsへの保存・取得と、HTML画面との通信を理解する。**

この段階では開発環境とデプロイを含む最小の成功体験を得る。

### Phase α-1：写真日記アプリ

**テーマ：画像と複数データの関連付け**

α-0から追加するもの：

- Google Driveへの画像アップロード
- 写真プレビュー
- 投稿と画像の関連付け
- カテゴリー
- 複数タグ
- タグ検索

DB設計：

- posts
- images
- categories
- tags
- post_tags

1対多と多対多のリレーションを扱う。

Instagram風のUIは参考にするが、SNS機能は再現しない。

**検証目的：GAS＋Sheets＋Driveで、実用的なデータ管理・画像管理ができるかを確認する。**

### Phase α-2：AI写真日記アプリ

**テーマ：既存アプリに生成AIを組み込む**

追加するもの：

- Gemini API
- プロフィール
- AI生成ハーネス
- キーワード入力
- 写真理解
- 日記の下書き生成
- 文章のトーン調整
- タグ自動提案

入力：

`写真＋キーワード＋プロフィール＋生成ルール`

出力：

`タイトル＋本文＋タグ`

#### ハーネスの役割

プロフィール：

- 本人のキャラクター
- 好きな表現
- 文章の口調
- 読者との距離感

生成ルール：

- 文字数
- 絵文字の使用頻度
- 写真・キーワードの優先度
- 事実を創作しない
- 禁止表現
- 下書きのみ生成する

本人が最終確認・編集して保存する。

**検証目的：生成AIによる開発と、アプリ内部に生成AIを組み込むことの違いを理解する。**

この段階で、単なるCRUD教材から実務的なAIアプリへ発展する。

### Phase α-3：AI英語日記アプリ

**テーマ：同じAI基盤を別用途に転用する**

英会話コミュニティ向けの派生アプリ。

#### モードA：日本語の英文化

日本語で書いた日記を、本人の英語レベルに合わせて自然な英文へ変換する。

例：

- A1：短い基本文
- A2：日常会話程度の表現
- B1：少し複雑な出来事や感想

単純な直訳ではなく、本人が理解して話せる英文を優先する。

#### モードB：英語日記の添削

本人が書いた英文に対して、

- 文法の修正
- 不自然な表現の改善
- 修正理由の日本語解説
- 覚える表現の抽出

を行う。

#### モードC：会話練習への発展（任意）

書いた日記から英語の質問を3つ生成する。

日記作成を英会話練習につなげる。

**検証目的：同じGemini API・プロフィール・ハーネス基盤を、プロンプトと入出力仕様の変更だけで異なる業務へ転用できるか。**

※英語日記はα-0のテキスト日記から直接派生できる。写真機能の完成を必須条件にしない。

## 3. 業務アプリへの横展開

### Phase β：スタッフポイント管理

**テーマ：教材で作った共通基盤を実際の業務へ応用する**

最初の相談者向け。

機能：

- メンバー管理
- ポイント付与・減算
- 残高照会
- 履歴管理
- ポイントルール管理
- 店主とメンバーの権限管理

初期ルールは勤務・貢献評価型。

売上や指名に関連したポイントも、設定によって対応できる汎用構造とする。

既存の集客・予約サービスが提供している機能は作らない。

### LINEフロントへの対応

LINE連携は、日記アプリとポイント管理の双方へ適用できるアダプターとして扱う。

想定：

- α-LINE：写真日記のLINE対応
- β-LINE：ポイント管理のLINE対応

ただし、LIFFの認証・通信制約、対象業種に関する利用条件を検証する。

LINE利用が不適切な場合は、独立したGAS Webアプリで提供する。

**βはα-3の完成を待たず、共通CRUD基盤が安定した時点で並行開発可能。**

## 4. 全体の技術構造

```text
                  共通基盤
            GAS + Google Sheets
                     │
             α-0 日記アプリ
                     │
             α-1 写真日記
                     │
                Gemini API
                     │
              α-2 AI写真日記
                     │
                 AIハーネス
                     │
              α-3 AI英語日記


       共通基盤から独立して派生
                     │
              β ポイント管理
                     │
          LINEフロント（条件付き）
```

※これは機能の発展イメージ。実装上は、α-3とβを別テンプレートとして管理する。

### 設計上の原則

- Core：GAS・Sheets・Drive・認証などの共通処理

- Config：一般利用者が変更できる設定

巨大な汎用フレームワークは作らず、必要な共通処理だけ切り出す。

## 6. 生成AI開発・運用の提供モデル

### 黒澤側

- 共通テンプレートを開発
- 各段階の実装例を用意
- AI向け開発ルールを整備
- ZIP形式で提供
- 動画教材を制作
- 初回導入の範囲を明確化

### 利用者側

- Devin Desktopを導入
- ZIPを開く
- 完成済みテンプレートを使用
- 日本語でAIへ改修を指示
- テストとデプロイを実行
- 独立運用する

利用者にGitHub登録を要求しない。

DevinのFreeを初期候補とし、利用枠不足時のみ有料プランを検討する。プラン条件・実際の利用量は導入時に確認する。

Gemini APIの利用料はDevinの開発支援料金とは別に管理する。

## 7. アイデア展開の優先順位

| 優先 | 開発内容 | 主な価値 |
|---|---|---|
| P0 | α-0 日記 | GAS最小実装の成立 |
| P1 | α-1 写真日記 | Sheets＋Driveの理解 |
| P2 | α-2 AI写真日記 | 生成AI統合とハーネス |
| P3 | β ポイント管理 | 実際の相談案件への提供 |
| P4 | α-3 AI英語日記 | 別コミュニティへの横展開 |
| 条件付き | LINE連携 | 対象用途で必要な場合のみ |

### この優先順位の理由

**学習順序と、実際の提供順序は異なる。**

学習上は、日記から写真・AIへ順番に機能を増やすことに意味がある。

一方、実務提供ではβポイント管理の完成を優先する。

α-3の英語日記は独立したユーザー層への横展開として後続に置く。

LINE対応は利用規約・技術的成立性が未確定のため、実装判断を分離する。

## 8. 破綻条件・スコープ管理

### 開発を拡大しない条件

- 日記教材にSNS全機能を追加しない
- AIに自動投稿まで任せない
- 画像生成・動画生成は初期対象外
- 複雑な認証基盤をα-0へ持ち込まない
- テンプレート共通化のために過剰抽象化しない
- LINEが使えない業種でLINE連携を前提にしない

### 品質面の条件

- Geminiの出力をそのまま公開しない
- AIが事実を創作しないよう設計する
- 写真やプロフィールの外部送信範囲を明確にする
- APIキーをフロントに渡さない
- ポイント履歴は追記型とし、整合性テストを行う
- 本番公開前に利用者自身が承認する

## 9. 教材としての価値

この構想では、アプリの発展に合わせて次の知識を自然に学べる。

| 段階 | 理解できること |
|---|---|
| 日記 | データを保存・取得する |
| 写真日記 | 画像とデータを関連付ける |
| AI日記 | AI APIをアプリに組み込む |
| 英語日記 | ハーネスを変更して別用途に使う |
| ポイント管理 | 同じ基盤で違う業務を作る |
| Devinで改修 | 自分で改善を継続する |

**プログラミングを体系的に教えるのではなく、実際にアプリが進化する過程を教材化する。**

利用者は全段階を学ぶ必要はなく、興味のある完成テンプレートから開始できる。

## 10. 成功条件

### 利用者側

- テンプレートを起動できる
- Devinで小さな変更を依頼できる
- テスト・公開を実行できる
- 必要な場合に復旧できる
- 自分の業務に合わせて改善を続けられる

### 黒澤側

- 一度作ったテンプレートを再利用できる
- 動画教材を複数利用者に流用できる
- 個別開発を毎回ゼロから行わない
- 継続的な問い合わせに対応しなくてよい
- 初期支援の終了時点を明確化できる

**最重要KPI：引き渡し後の黒澤側の追加サポート時間。**

最終的には、完成テンプレートと動画教材によって利用者が独立運用でき、黒澤側の無期限サポートを不要にする。

## 11. 最終整理

本構想には3つの価値がある。

**① 技術的価値**

GAS＋Sheets＋Drive＋Geminiを組み合わせ、少ないインフラ構成で小規模業務アプリを成立させる。

**② 教育的価値**

日記から始め、写真・AI・ハーネス・業務応用まで段階的に発展させることで、AIアプリ開発の考え方を実践的に理解できる。

**③ 提供モデルとしての価値**

完成テンプレートとDevin Desktopによって利用者の独自改修を可能にし、黒澤側の継続サポートからの離脱を実現する。

### 基本戦略

**小さく作る → 技術要素を一つ追加する → 共通化する → 別用途へ展開する → 利用者へ移管する。**

これを「DevinとGASで始める生成AIアプリ開発」の基本ロードマップとする。
