# cast-evaluation

ガールズバー・スナック向けの独立型キャスト評価システム。既存の店舗業務・POS・会計をそのまま利用し、キャストの営業実績と評価だけを管理する。

## 仕様の正本と開発状況

[Cast Evaluation System — プロダクト方針・基本仕様・設計書 v0.3.0（Draft）](<docs/tasks/01_idea/Cast Evaluation System — 基本仕様・設計.md>) をプロダクト仕様の正本とする。配置先は `docs/tasks/` だが、通常のタスクメモとは区別し、他の文書や雛形と矛盾する場合はこの仕様を優先する。

以下は初期MVPの設計であり、実装済み機能の一覧ではない。現時点の `src/` にアプリケーション実装はなく、`Makefile` は雛形。

## プロダクト方針

**Small Core / Integration First**：責任範囲を Member → Performance → Evaluation Rule → Evaluation Result の4領域に限定する。店舗固有の評価基準を簡単な設定で吸収し、汎用ルールエンジンやワークフローエンジンは構築しない。

スマートフォン中心の利用を前提とし、日々の入力・評価確認をタッチ操作で完結できるUIを目指す。初期は手入力で検証し、負担や需要が確認された段階でCSV・API連携を検討する。GASは初期開発・検証用の選択であり、業務モデルをGAS固有の仕組みに依存させない。

## 初期MVP

| 機能 | 内容 |
|---|---|
| F01 メンバー管理 | 一覧・登録・編集・在籍状態変更。IDを自動発行し、退店時は削除せず無効化して過去実績を保持 |
| F02 営業実績管理 | 営業日とキャストを選択し、ドリンク杯数・ボトル本数・指名件数・同伴件数・個人売上（円）を登録・編集 |
| F03 評価ルール管理 | 評価項目ごとの計算単位・ポイント・有効／無効をGoogle Sheetsで直接設定 |
| F04 評価一覧 | 対象月を選び、キャスト別の5項目・総合ポイント・順位を表示。ポイント順／個人売上順の表示に対応 |

画面は「メンバー管理」「営業実績入力」「評価一覧」の3画面。評価ルールの専用画面は設けない。

### 業務・評価ルール

- メンバーの状態は `ACTIVE` / `INACTIVE`。本名などの不要な個人情報は管理しない。
- 1キャスト・1営業日につき1レコード。同一営業日・同一キャストの重複登録を禁止し、過去実績も編集できる。
- 5項目の実績は0以上の整数。件数は整数、個人売上は整数円とする。
- 個人売上の正本は店舗の既存会計・POS等。本システムには確定済みの評価用金額を記録し、売上確定、自動計算、商品明細、売上按分、自動照合は行わない。
- **評価対象期間の数量・金額をキャスト別に集計した後**、以下の式で計算する。

| 評価対象 | 計算式 |
|---|---|
| ドリンク・ボトル・指名・同伴 | ポイント = 期間数量 × ポイント単価 / 計算単位 |
| 個人売上 | 売上ポイント = floor(期間売上 / 計算単位) × ポイント |

総合ポイントは有効な評価項目の合計。個人売上ポイントは販売数量評価との重複を避けるため初期無効とし、金額自体の記録・表示は行う。その他4項目は初期有効。配点例（ドリンク1杯＝1Pなど）は設計確認用の仮設定であり、業界標準ではない。

ランキングは **総合ポイント降順 → 同点なら個人売上降順 → 両方同じなら同順位** とする。

評価結果は固定保存せず、現在のルールで都度算出する。**ルール変更時は過去期間も再計算されるため、運用開始後の変更には管理者の確認が必要。** ルール履歴管理は、過去結果の固定が必要になった段階で検討する。

## 技術構成・データ

| レイヤー | 初期技術・役割 |
|---|---|
| UI | GAS HTML Serviceによるスマートフォン対応Web UI |
| 業務処理 | Google Apps Script：入力検証、実績登録・更新、ポイント計算、月次集計 |
| データ保存 | Google Sheets：下記の3シート |
| 通信 | `google.script.run` |
| バージョン管理 | Git / clasp（設計上の採用技術） |

| シート | カラム |
|---|---|
| `members` | `member_id`, `name`, `status` |
| `daily_records` | `record_id`, `business_date`, `member_id`, `drink_count`, `bottle_count`, `nomination_count`, `accompaniment_count`, `personal_sales` |
| `evaluation_rules` | `category`, `unit`, `points`, `enabled` |

`daily_records` の `business_date` + `member_id` は一意。`category` は `DRINK` / `BOTTLE` / `NOMINATION` / `ACCOMPANIMENT` / `SALES` の固定値とし、型の詳細は正本§10に従う。評価結果の独立テーブルは設けず、この3シートから算出する。行番号を業務IDに使用しない。

UI・業務ロジック・データアクセスを分離する。ポイント計算は独立したロジックとして保持し、Sheetsの関数や画面処理へ埋め込まない。過度な抽象化や大量のService・Repositoryクラスは導入しない。

最低限の品質要件は管理者限定アクセス、サーバー側入力検証、レコードID、排他制御、重複防止、GASの実行制限を考慮した一括読み書き。公開・実行権限は運用するGoogleアカウント環境に合わせる。

## 開発・セットアップの現状

GASプロジェクトの作成・接続・公開手順と実際のビルド・検証コマンドは未整備。`make setup` / `build` / `run` / `dev` / `test` / `fmt` / `lint` はメッセージを出力する雛形であり、セットアップや品質検証の完了を意味しない。Git / claspも採用方針と実環境の設定完了を区別する。

評価ルールは `evaluation_rules` シートで管理する。開発環境用の `env/config.yaml` / `doppler.yaml` とGASとの連携方法は正本で未定義。秘密情報はコミットしない。

## MVP受入条件

正本§16に従い、機能・運用の両面で判定する。

- **機能**：キャスト登録・編集・在籍状態管理、5項目の日次実績登録・編集、重複防止、ポイント設定・計算、月次評価一覧、ポイント・個人売上でのランキング。
- **運用**：スマートフォンで主要操作が完結し、既存POS・会計の変更が不要。管理者が基本操作を理解でき、日次入力の負担が許容範囲である。

| 初期検証KPI | 仮の目標 |
|---|---|
| 日次入力所要時間 | 全キャスト分で5分以内 |
| 実績登録の継続率 | 営業日の90%以上 |
| 評価計算の整合性 | テストケース100%一致 |
| 既存業務の変更 | 原則不要 |

KPIは実店舗での運用検証を通じて調整する仮目標であり、達成済みの実績ではない。

## 責任範囲外と将来拡張

POS・注文・決済、商品・在庫、勤怠・シフト、顧客・予約、給与計算、会計・税務・経理は原則として本体に実装しない。将来も専門SaaSの利用・連携を優先する。

指名種別、共同売上按分、CSVインポート、POS API連携、ルール履歴、評価ランク、キャスト用画面、ネイティブアプリ、複数店舗対応は、正本§14の条件に応じて検討する候補。初期MVPの確定機能ではない。詳細KPI分析、高度なグラフ、複雑な評価アルゴリズム、時給査定・給与反映もMVP対象外とする。

新機能は「評価に直接必要か」「既存システムで解決できないか」「実店舗の課題として確認できたか」「評価モデルを変えず実装できるか」「未実装でも業務フローが成立するか」で判断する。未実装でも成立するものは原則後回しにする。

## 開発ステップと検証課題

1. **Phase 1：最小MVP** — GAS + Google Sheetsで評価業務が成立するか検証する。
2. **Phase 2：実運用の改善** — 実店舗で確認した入力負担・業務適合性の課題のみ改善する。UI改善・CSV取り込み等は候補。
3. **Phase 3：製品化の判断** — 店舗差分・需要を検証し、API・DB基盤やPWA / React Native + Expo / Flutterの必要性を判断する。需要の検証前にSaaS化を先行しない。

初期にネイティブアプリは開発しない。将来ネイティブ化する場合は `google.script.run` 依存UIの単純移植ではなく、独立したAPI基盤への移行を検討する。

二重入力の負担、簡単な設定で吸収できない店舗ルール、売上把握に必要となるPOS相当の機能、過大な連携・保守コスト、評価専用ツールへの需要不足は、正本§18に従って方針を再検討する条件とする。
