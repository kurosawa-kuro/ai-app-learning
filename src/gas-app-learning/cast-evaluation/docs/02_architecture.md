# 02 アーキテクチャ

根拠: [基本仕様・設計 v0.3.0（Draft）](<tasks/01_idea/Cast Evaluation System — 基本仕様・設計.md>) §2、§10〜13、§17。この文書は正本からの派生文書であり、矛盾時は正本を優先する。記載は設計・受入基準であり、実装・検証済みを意味しない。

## 初期構成

```text
スマートフォン / ブラウザ
  → GAS HTML Service（3画面）
  → google.script.run
  → 業務ロジック（検証・登録更新・集計・評価計算）
  → Sheetsデータアクセス（検索・一括読み書き）
  → Google Sheets（3シート）
```

| 構成要素 | 責務 | 実装状況 |
|---|---|---|
| UI | メンバー管理・営業実績入力・評価一覧。タッチ操作を重視 | 未実装 |
| 業務ロジック | サーバー側入力検証、メンバー・実績管理、月次集計、ポイント・順位計算 | 未実装 |
| データアクセス | Sheetsの検索・読み書き・更新を関数として分離 | 未実装 |
| 保存先 | members / daily_records / evaluation_rules | 実環境未確認 |
| バージョン管理 | Git / claspを採用予定 | 接続・公開手順未整備 |

ソース配置先は `src/`。具体的なファイル名・関数インターフェースは未決定であり、この図は実装済み構成を示さない。

## 責務と依存

- ポイント計算は独立したロジックとし、Sheets関数や画面処理に埋め込まない。
- 業務モデルではレコードIDを使い、シート行番号を業務IDにしない。
- UI・業務ロジック・データアクセスを分離するが、過度な抽象化や大量のService・Repositoryクラスは導入しない。
- 一括読み書きでGASの実行制限を考慮する。想定キャスト数・実績件数・具体的な性能基準は未決定。
- 業務評価ルールはSheetsの `evaluation_rules` に置く。開発環境の `env/config.yaml` / `doppler.yaml` と用途を混同しない。
- 既存POS・会計の変更や常時接続をMVPの成立条件にしない。個人売上は確定済み金額の手入力とする。

## 中核フローとの対応

| 要件のステップ | 通る構成要素・データ | 主な確認点 |
|---|---|---|
| 1. メンバー登録・ルール設定 | UI→業務処理→members、管理者がevaluation_rulesを直接設定 | ID・状態・設定値を読み直せる |
| 2. 実績保存 | UI→検証→排他制御を伴う検索・更新→daily_records | 同時登録でも同一営業日・キャストが重複しない |
| 3. 実績修正 | IDによる検索→検証→更新 | 既存レコードの更新と再表示 |
| 4. 月次評価 | 3シート読み取り→期間集計→計算→順位→UI | 集計後の売上切り捨て・同点判定・有効ルール |

公開権限、GAS実行、Sheetsアクセスのいずれかが機能しないとフローが成立しない。ローカルの計算検証だけで接続・公開・受入完了としない。

## 権限・同時更新

管理者限定アクセスとサーバー側入力検証は必須。GAS Webアプリの公開・実行権限は利用するGoogleアカウント環境に合わせる。具体的な管理者識別方式、Sheets共有範囲、認可方法は初回公開前に決定・検証する。

同時更新の排他制御と `business_date + member_id` の重複防止を設ける。ロック方式・待機時間・競合時の扱いは詳細設計事項。画面側の保存ボタン制御だけでサーバー側の保証を代替しない。

## 将来の移行

GASは初期開発・検証用。データアクセスを置き換えられるようにし、業務モデルを将来のAPI・DBへ持ち出せる状態にする。MVPではネイティブアプリを作らない。将来ネイティブ化する場合は `google.script.run` 依存UIの単純移植ではなく、独立API基盤を検討する。

PWA / React Native + Expo / Flutterの最終選定は実運用後。外部連携は評価業務の必要性・対応システム・需要を確認した後に判断する。
