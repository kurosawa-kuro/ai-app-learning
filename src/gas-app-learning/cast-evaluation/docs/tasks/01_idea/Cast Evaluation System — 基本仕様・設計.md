## 1. プロダクトコンセプト

### 1.1 基本理念

**既存の店舗業務を置き換えず、キャスト評価に必要な機能だけを提供する独立型評価システム。**

飲食店向けPOS、会計、決済、勤怠、在庫、顧客管理などは、既存の専門システムに委ねる。

本システムは、それらの機能を再実装せず、店舗固有のキャスト評価業務に集中する。

### 1.2 提供価値

> 今の店舗システムはそのまま。
> キャストの営業実績と評価だけを、シンプルに管理する。

### 1.3 解決する課題

一般的な飲食店向けシステムは、注文・売上・決済などの共通業務に適している。

一方、ガールズバー・スナックでは、以下のような店舗固有の評価業務が存在する。

- キャストごとのドリンク販売実績
- ボトル販売実績
- 指名・同伴の実績
- キャスト別の個人売上
- 店舗独自のポイント評価
- 月次の営業成績比較

オールインワン型システムでは、これらの評価ルールを店舗固有の業務フローに合わせて変更できない場合がある。

本システムは、こうした評価業務だけを独立させることで、既存業務への影響を最小化する。

## 2. プロダクト設計原則

### P01. オールインワンを目指さない

本システムは店舗総合管理システムではない。

他の専門SaaSで解決できる業務を原則として再実装しない。

### P02. キャスト評価だけに責任を持つ

責任範囲を以下の4領域に限定する。

1. メンバー管理
2. 営業実績管理
3. 評価ルール管理
4. 評価結果の集計・可視化

### P03. 既存の業務フローを尊重する

店舗側にPOSや会計システムの変更を要求しない。

既存の営業実績を評価システムへ取り込めることを重視する。

初期は手入力とし、将来的にCSV・API連携へ拡張する。

### P04. 店舗固有ルールを吸収する

評価対象やポイント配点など、店舗ごとに異なるルールを設定で調整できるようにする。

ただし、独自の汎用ルールエンジンやワークフローエンジンは構築しない。

**業務適合性とシステムの複雑さを混同しない。**

### P05. 機能数ではなく業務適合性を優先する

機能の追加そのものを価値としない。

実際の業務に必要であり、既存システムで代替しにくい機能だけを開発対象とする。

### P06. モバイルファースト

日々の実績入力や評価確認はスマートフォンで完結できることを目指す。

PC専用の複雑な操作画面を前提にしない。

### P07. 技術基盤をプロダクトの制約にしない

GASは初期開発・検証用の技術選択とする。

業務モデルをGAS固有の仕組みに依存させず、将来のAPI・DB・モバイルアプリへの移行余地を残す。

## 3. システムの責任範囲

### 3.1 対象領域

| ドメイン | 役割 | MVP |
|---|---|---|
| Member | キャストの基本情報 | 必須 |
| Performance | キャスト別の営業実績 | 必須 |
| Evaluation Rule | ポイント評価基準 | 必須 |
| Evaluation Result | 集計結果・ランキング | 必須 |

### 3.2 明示的な非対象領域

以下は本システムの責任範囲に含めない。

| 領域 | 方針 |
|---|---|
| POS・注文管理 | 既存POSを使用 |
| 決済・会計 | 既存システムを使用 |
| 商品・在庫管理 | 既存システムを使用 |
| 勤怠・シフト管理 | 既存SaaSを使用 |
| 顧客・予約管理 | 既存SaaSを使用 |
| 給与計算 | 既存給与システムを使用 |
| 税務・経理 | 既存会計システムを使用 |

**上記の機能を本体に取り込むことは原則として行わない。**

将来的に必要になった場合は、機能の重複開発よりも外部システムとの連携を優先する。


## 5. F01 — メンバー管理

### 5.1 目的

評価対象となるキャストを管理する。

### 5.2 機能

- メンバー一覧
- 新規登録
- メンバー編集
- 在籍状態の変更

### 5.3 管理項目

| 項目 | 説明 |
|---|---|
| member_id | 一意のメンバーID |
| name | キャスト名 |
| status | ACTIVE / INACTIVE |

### 5.4 業務ルール

- メンバーIDはシステムで自動発行する
- 退店時はレコードを削除せず無効化する
- 過去の営業実績は保持する
- 本名などの不要な個人情報は管理しない

---

## 6. F02 — 営業実績管理

### 6.1 目的

キャストごとの営業実績を日次で記録する。

### 6.2 評価対象

| 評価対象 | 入力項目 | 単位 |
|---|---|---|
| ドリンク | 販売数 | 杯 |
| ボトル | 販売数 | 本 |
| 指名 | 指名数 | 件 |
| 同伴 | 同伴数 | 件 |
| 個人売上 | 売上金額 | 円 |

### 6.3 機能

- 営業日の選択
- キャストの選択
- 5項目の実績入力
- 実績の保存
- 登録済み実績の編集

### 6.4 業務ルール

- 1キャスト・1営業日につき1レコード
- 同一日・同一キャストの重複登録を禁止する
- 実績は0以上の数値とする
- ドリンク・ボトル・指名・同伴の件数は整数とする
- 売上金額は整数円とする
- 過去の営業実績も修正できる

### 6.5 個人売上の扱い

MVPでは、店舗側で確定した日次の個人売上を入力する。

販売伝票、商品明細、売上按分などの管理は行わない。

そのため、個人売上は店舗側の既存会計・POS等を正本とし、本システムには評価用の金額を記録する。

この方式により、POS相当の機能を実装せずに個人売上評価を成立させる。

### 6.6 初期制約

- 個人売上の自動計算は行わない
- 複数キャスト間の売上按分は店舗側で処理する
- 商品別の販売明細は記録しない
- 指名種別の詳細分類は行わない
- POSや会計との自動照合は行わない

これらは初期MVPに必要ないため実装しない。

---

## 7. F03 — 評価ルール管理

### 7.1 目的

店舗固有のポイント評価基準を管理する。

### 7.2 評価項目と仮設定

| 評価項目 | 計算単位 | ポイント | 初期状態 |
|---|---|---|---|
| ドリンク | 1杯 | 1P | 有効 |
| ボトル | 1本 | 5P | 有効 |
| 指名 | 1件 | 3P | 有効 |
| 同伴 | 1件 | 5P | 有効 |
| 個人売上 | 10,000円 | 2P | 無効 |

※ 数値は設計確認用の仮設定であり、業界標準の配点ではない。

### 7.3 設定機能

- 評価項目ごとのポイント設定
- 計算単位の変更
- 評価項目ごとの有効・無効

### 7.4 計算ルール

ドリンク・ボトル・指名・同伴：

```text
ポイント = 数量 × ポイント単価 / 計算単位
```

個人売上：

```text
売上ポイント =
  floor(対象売上 / 計算単位) × ポイント
```

計算は評価対象期間の数量・金額を集計した後に行う。

個人売上ポイントは販売数量評価との重複を避けるため、初期状態では無効にする。

### 7.5 MVP制約

- ルールはGoogle Sheetsで直接設定する
- 専用の設定画面は作成しない
- ルールのバージョン管理は行わない
- 過去の評価結果を固定保存しない

**重要：ルール変更時には過去期間も新しいルールで再計算される。**

これは初期MVPの明示的な制約とする。

運用開始後のルール変更は過去の評価結果にも影響するため、管理者による確認を必要とする。過去結果の固定が必要になった段階で、ルールバージョン管理を追加する。

---

## 8. F04 — 評価一覧

### 8.1 目的

キャスト別の営業実績とポイント評価を確認する。

### 8.2 表示項目

| 項目 | 内容 |
|---|---|
| キャスト名 | メンバー名 |
| ドリンク | 月間杯数 |
| ボトル | 月間本数 |
| 指名 | 月間件数 |
| 同伴 | 月間件数 |
| 個人売上 | 月間金額 |
| 総合ポイント | 評価ポイント合計 |
| 順位 | 月間ランキング |

### 8.3 機能

- 対象月の選択
- キャスト別月次集計
- 総合ポイント順の表示
- 個人売上順の表示

### 8.4 集計ルール

対象月の営業実績をキャスト別に集計する。

総合ポイントは、有効化されている評価項目のポイント合計とする。

ランキングは以下の順序で決定する。

1. 総合ポイント降順
2. 同点の場合は個人売上降順
3. 両方同じ場合は同順位

### 8.5 対象外

- 評価ランク（S/A/B等）
- 詳細KPI分析
- 高度なグラフ
- 複雑な評価アルゴリズム
- 時給査定・給与反映

## 10. データモデル

### 10.1 基本方針

初期データストアはGoogle Sheetsとする。

1シートを1テーブルとして扱い、3シートだけで構成する。

### 10.2 members

| カラム | 型 | 説明 |
|---|---|---|
| member_id | string | PK |
| name | string | キャスト名 |
| status | string | 在籍状態 |

### 10.3 daily_records

| カラム | 型 | 説明 |
|---|---|---|
| record_id | string | PK |
| business_date | date | 営業日 |
| member_id | string | メンバーID |
| drink_count | integer | ドリンク杯数 |
| bottle_count | integer | ボトル本数 |
| nomination_count | integer | 指名件数 |
| accompaniment_count | integer | 同伴件数 |
| personal_sales | integer | 個人売上（円） |

**一意制約：**

`business_date + member_id`

### 10.4 evaluation_rules

| カラム | 型 | 説明 |
|---|---|---|
| category | string | 評価対象 |
| unit | number | 計算単位 |
| points | number | 付与ポイント |
| enabled | boolean | 有効・無効 |

categoryは次の固定値を使用する。

- DRINK
- BOTTLE
- NOMINATION
- ACCOMPANIMENT
- SALES

### 10.5 データ構造の基本原則

**評価結果は独立したテーブルとして保持しない。**

`members`、`daily_records`、`evaluation_rules` の3つから都度算出する。

データ設計は単純に保ち、GAS固有の行番号などを業務IDとして使用しない。

## 11. 初期技術アーキテクチャ

### 11.1 技術構成

| レイヤー | 技術 |
|---|---|
| UI | GAS HTML Service |
| 業務処理 | Google Apps Script |
| データ保存 | Google Sheets |
| 通信 | google.script.run |
| バージョン管理 | Git / clasp |

### 11.2 システム構成

```text
Smartphone / Browser
        ↓
  GAS HTML Service
        ↓
 Application Logic
        ↓
  Sheets Data Access
        ↓
    Google Sheets
```

### 11.3 責務分離

**UI**

- メンバー管理
- 実績入力
- 評価一覧

**業務ロジック**

- 入力検証
- 実績の登録・更新
- ポイント計算
- 月次集計

**データアクセス**

- Google Sheetsの読み書き
- レコード検索
- レコード更新

過度な抽象化や大量のService・Repositoryクラスは導入しない。

一方、ポイント計算をGoogle Sheetsの関数やGASの画面処理に直接埋め込まず、独立したロジックとして保持する。

### 11.4 最低限の品質要件

- 管理者のみアクセス可能
- サーバー側で入力値を検証
- レコードIDを使用
- 同時更新時の排他制御
- 同一営業日・同一キャストの重複登録を防止
- GASの実行制限を考慮した一括読み書き

GAS Webアプリの公開・実行権限は、運用するGoogleアカウント環境に合わせて設定する。

## 14. 開発対象外と将来拡張

### 14.1 原則として開発しない機能

- POS・注文・決済
- 商品・在庫管理
- 勤怠・シフト管理
- 給与計算
- 顧客・予約管理
- 会計・経理機能

これらは将来も既存SaaSの利用を優先する。

### 14.2 必要性を確認してから検討する機能

| 機能 | 追加を検討する条件 |
|---|---|
| 指名種別の詳細管理 | 店舗で複数種類の指名評価が必要 |
| 共同売上按分 | 店舗側での按分処理が負担 |
| CSVインポート | 手入力の負担が大きい |
| POS API連携 | 対応POSと導入需要が確認できた |
| ルール履歴管理 | 過去の評価結果を固定する必要がある |
| 評価ランク | 店舗側で実際にランク制度を使用 |
| キャスト用画面 | キャスト自身による評価確認の需要 |
| ネイティブアプリ | Webでは満たせない利用要件が発生 |
| 複数店舗対応 | 複数店舗から導入需要が発生 |

### 14.3 拡張の原則

機能追加を目的化しない。

新しい業務要件が発生しても、最初に既存サービスとの組み合わせで対応できるかを検討する。

外部連携の追加と、自社システムの機能肥大化は区別する。

## 15. 開発判断基準

新機能の実装前に、以下を確認する。

1. キャスト評価に直接必要か？
2. 既存システムで解決できないか？
3. 実店舗の業務課題として確認されているか？
4. 既存の評価モデルを変更せず実装できるか？
5. 実装しなくても現在の業務フローは成立するか？

**5番がYESなら、原則として後回しにする。**

また、POS・会計・給与など、責任範囲外の機能は、必要性があっても自社実装ではなく連携を優先する。

- [ ] スマートフォンで主要操作が完結する

| 指標 | 仮の目標 |

| 既存業務の変更 | 原則不要 |

## 17. 開発ステップ

### Phase 1 — 最小MVP

**目的：評価業務が成立することの検証**

- メンバー管理
- 日次実績入力
- ポイント設定
- 月次評価・ランキング

技術：GAS + Google Sheets

### Phase 2 — 実運用の改善

**目的：入力負担・業務適合性の改善**

実店舗で確認した課題のみを対象とする。

例：

- 入力UI改善
- 指名種別対応
- ルール管理改善
- CSV取り込み

これらは実装が確定した機能ではない。

### Phase 3 — 製品化の判断

**目的：他店舗への横展開可能性の検証**

- 店舗ごとの業務差分の分析
- 共通ルールと可変ルールの整理
- API・DB基盤の必要性判断
- PWA / React Native / Flutterの選定

店舗の需要が検証されない段階で、SaaS化を先行しない。

## 18. 競争優位性と破綻条件

### 18.1 目指す優位性

| 観点 | 目指す価値 |
|---|---|
| 導入容易性 | 既存システムを変更せず導入 |
| 業務適合性 | 店舗固有の評価基準を反映 |
| 変更容易性 | 評価ルールの変更を他業務に波及させない |
| システム独立性 | POS・会計と疎結合 |
| 運用効率 | 少ない入力で評価を確認 |
| 開発効率 | 専門領域以外を開発しない |

### 18.2 破綻条件

以下の状況では、方針の再検討が必要となる。

- 実績入力の二重管理が大きな負担になる
- 店舗固有ルールを簡単な設定で吸収できない
- 個人売上の正確な把握にPOS相当の機能が必要になる
- 外部システムとの連携・保守コストが過大になる
- 対象店舗が評価専用ツールを必要としていない

これらはMVPで検証する事業・運用上の仮説とする。

## 19. 最終設計方針

本プロジェクトは、オールインワン型店舗管理システムの代替を目指さない。

キャスト評価という専門領域を独立させ、既存SaaSとの共存によって店舗全体の業務を成立させる。

システムの中核は次の4要素に限定する。

**Member → Performance → Evaluation Rule → Evaluation Result**

技術的な複雑さや機能数の増加ではなく、現実の業務フローに対する適合性を優先する。

### プロダクトの定義

**「既存システムとの共存を前提に、店舗固有のキャスト評価業務だけを最適化する専門システム」**

### 開発の原則

**小さく作り、必要に応じて改善する。ただし、専門領域の境界はむやみに広げない。**
