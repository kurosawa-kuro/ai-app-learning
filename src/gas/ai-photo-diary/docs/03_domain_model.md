# 03 ドメインモデル

2026-10-25：日記・画像資産・AI生成の境界と業務ルールを `src/server/domain/` に分離した。現在の状態・保持期限・回復手順は [業務ルールと依存関係の設計](specs/application-domain-architecture.md)、物理データは [DB v2仕様](specs/database-v2.md) を参照。以下の旧ダミー画像を前提とした説明は初期モデルの記録。

## 用語と関連

| 用語 | 意味 |
|---|---|
| 日記（post） | タイトル・本文・作成日時を持つ記録 |
| 写真（image） | 日記に付ける画像参照。現在の file_id はダミー提供元の ID |
| キーワード（tag） | 利用者に表示する分類。内部名はタグ |
| 日記とタグの関連（post_tag） | 多対多を表す中間行 |
| 下書き（draft） | フォームに取り込むタイトル・本文。現在は固定文で、取得だけでは保存しない |
| provider | 写真・下書きの実装を差し替える提供元 |
| requestId | 1 回の保存要求を識別し、再送時の二重登録を抑える ID |

日記 1 件に写真を複数付けられる（1 対多）。日記とタグは多対多で、post_tags で関連付ける。写真の表示順は sort_order で保持する。集約は本文・写真・タグをまとめた日記としてモデルから返す。

## ライフサイクル

```text
作成フォーム → 写真・キーワード選択 → 下書き取得（任意）
            → タイトル・本文の編集 → 検証 → 保存 → 詳細・一覧
```

下書きを使わずに入力することもできる。編集・削除機能や日記のステータス列は持たない。画面の編集中状態を永続化された下書きと呼ばない。

## 不変条件

- タイトルと本文は必須。文字数やタグ数の上限は Settings から取得する。
- 写真 ID は提供元に、タグ ID はタグマスターに存在するものだけを受け付ける。選択 ID の重複は除去する。
- 写真の選択順を保存する。入力検証は書き込み前にすべて終える。
- Sheets に PK・FK・UNIQUE 制約はない。検証と書き込み順序はアプリ側で守る。
- 保存はロック内で行い、同一 requestId の完了記録をキャッシュで確認する。キャッシュの期限を越えた再送まで保証する仕組みではない。
- 初期データは新規シート作成時だけ投入する。シートの再作成は削除した日記の復元とは異なる。
