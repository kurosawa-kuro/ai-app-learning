# 04 ワークフロー

根拠: [基本仕様・設計 v0.3.0（Draft）](<tasks/01_idea/Cast Evaluation System — 基本仕様・設計.md>) §9、§11、§15〜17。正本を優先し、以下は実装・運用準備のための文書とする。実施済み・受入済みの記録ではない。

## 開発開始時

1. 正本と [索引](00_index.md) を読み、対象機能・非対象・未決事項を確認する。
2. [タスク案内](tasks/README.md) から作業を選び、Scope / Plan / Acceptance Criteriaを明示する。
3. 対象ファイルと実装状況を確認し、必要な詳細設計だけを決める。
4. [テスト戦略](07_test_strategy.md) の関連ケースで期待結果を定義する。

Codex等の準備は [AIコーディング環境](runbooks/ai-coding.md) を参照する。プロダクト要件とAI開発環境の設定を混同しない。

## セットアップ・コマンドの現状

| 項目 | 現状と次の作業 |
|---|---|
| src/ | アプリケーション未実装。構成・関数名は実装時に確定 |
| Makefile | setup / build / run / dev / test / fmt / lintはメッセージ出力のみ |
| make help | 対応ターゲットは現状存在しない |
| Git / clasp | 正本の採用技術。Git管理状態・導入済みツール・GAS接続先を実環境で確認 |
| GAS / Sheets | アカウント・共有範囲・ID・公開設定・接続手順は未整備 |
| テスト実行 | フレームワーク・実コマンドは未整備。雛形の成功終了を合格にしない |

Git管理された作業先では `git status --short` や `git diff --check` で変更を確認できる。Git未初期化の作業先で、実行できたことにしない。導入・公開の具体的コマンドは実環境で確認後、この文書へ追記する。

## 店舗の初期設定

管理者がメンバー登録 → Sheetsでポイントルール設定 → 運用開始、の順に準備する。

- メンバーIDは自動発行し、状態はACTIVE / INACTIVEで管理する。
- 設計確認用の配点例をそのまま確定配点とみなさず、店舗の設定を確認する。
- 個人売上ポイントは初期無効。他の4項目は初期有効。
- 過去期間の再計算という制約を管理者が理解した上で運用する。

## 日次運用・実績修正

1. 店舗側の既存業務で確定した実績と個人売上を用意する。
2. スマートフォンで営業日とキャストを選ぶ。
3. 5項目を0以上の整数（売上は整数円）で入力し保存する。
4. 再表示して保存内容を確認する。修正時は登録済み実績を編集し、同一日・同一キャストの重複を作らない。

個人売上の按分・確定は店舗側で処理する。本システムで販売伝票や会計を管理せず、POSとの自動照合もしない。

## 月次評価

対象月選択 → キャスト別に数量・売上を集計 → 有効項目のポイント計算 → ランキング表示。計算式・同点判定は [ドメインモデル](03_domain_model.md) に従う。ポイント順と個人売上順で確認する。

## ルール変更・退店

運用開始後のルール変更は、管理者が過去期間への影響を確認してからSheetsで行う。変更後は過去月も新しいルールで計算される。履歴固定が必要なら正本§14に従って別途検討する。

退店時はメンバーをINACTIVEにし、メンバー・過去実績を削除しない。

## 検証・作業終了

実際に行った検証、対象環境、期待値と結果、未実施と理由をタスクのVerificationに残す。ローカル検証・GAS接続・公開・実機受入・実店舗検証を分ける。手順と記録は [公開Runbook](08_release_runbook.md) と [受入書式](templates/platform-acceptance.md) を使う。

運用では全キャスト分の入力時間・営業日の登録継続率・計算整合性・既存業務の変更有無を測定し、仮KPIとの差を記録する。Phase 2の機能追加は観測した課題に基づいて判断する。
