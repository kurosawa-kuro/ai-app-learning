# GASの初期構成と外部連携の境界

根拠: [基本仕様・設計 v0.3.0（Draft）](<../tasks/01_idea/Cast Evaluation System — 基本仕様・設計.md>) §2、§11〜14、§17。プロダクト仕様は正本を優先する。

## 初期採用技術

| 領域 | 採用方針 |
|---|---|
| UI | GAS HTML Service、スマートフォンで主要操作が完結する3画面 |
| 通信 | google.script.run |
| 業務処理 | GAS。評価計算は独立したロジック |
| 保存 | Google Sheetsのmembers / daily_records / evaluation_rules |
| バージョン管理 | Git / clasp |

現時点でアプリケーション・接続・公開手順は未整備。採用方針を接続済み・公開済みという事実と混同しない。`gas/` ディレクトリや専用workflowスキルがある前提にせず、実際の構成を確認する。

Retoolは正本の初期採用技術に含まれない。生成器の汎用説明や利用可能なツールだけを理由に追加しない。

## 実装・公開時の境界

- 管理者限定アクセス、サーバー側入力検証、ID管理、排他制御、重複防止、一括読み書きを実装する。
- GAS Webアプリの公開・実行権限を運用するGoogleアカウント環境に合わせる。管理者以外からの操作を拒否できることを確認する。
- Sheetsの設定シートで評価ルールを直接管理し、専用画面を増やさない。
- 実環境のID・認証情報・店舗データを公開文書に転記しない。開発環境の設定ファイルと業務ルールの保存先を区別する。
- ローカルのモック検証、GAS接続、公開、スマートフォン実機受入、実店舗検証を分けて記録する。

具体的なアカウント設定・ツールコマンド・実行制限への対処は、実装環境で確認した内容を [リリースRunbook](../08_release_runbook.md) に反映する。

## 外部連携・移行

初期は既存会計・POS等で確定した実績を手入力する。CSVやPOS APIは実店舗の負担・対応システム・需要を確認してから検討し、POSそのものを実装しない。

`google.script.run` に依存するUIを外部アプリ向けの独立APIとみなさない。将来ネイティブ化する場合は独立API基盤への移行を検討し、PWA / React Native + Expo / Flutterの選定は実運用を踏まえる。

公開と受入の証跡は [受入書式](../templates/platform-acceptance.md) に残す。
