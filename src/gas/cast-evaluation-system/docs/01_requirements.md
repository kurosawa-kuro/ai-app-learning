# 01 要件

根拠: [基本仕様・設計 v0.3.0（Draft）](<tasks/01_idea/Cast Evaluation System — 基本仕様・設計.md>) §1〜9、§12〜19。この文書は正本からの派生文書であり、矛盾時は正本を優先する。記載は設計・受入基準であり、実装・検証済みを意味しない。

## 目的・設計原則

既存の店舗業務を置き換えず、ガールズバー・スナックのキャスト評価だけを独立して提供する。**Small Core / Integration First** を開発方針とする。

- 責任範囲は Member → Performance → Evaluation Rule → Evaluation Result の4領域。
- 店舗固有の評価基準は簡単な設定で調整し、汎用ルール／ワークフローエンジンは構築しない。
- スマートフォンで日次入力と評価確認を完結させる。
- 初期は確定済み実績の手入力。外部連携は負担・需要を確認した後に検討する。
- GASは初期開発・検証の選択であり、業務モデルをGAS固有機能に依存させない。

## ユーザー・責任範囲

MVPの利用者は管理者。キャストは評価対象であり、キャスト自身が使う画面は将来候補。個人売上の正本は既存会計・POS等とし、本システムには評価用金額を記録する。

| ID | 機能 | 成功条件 |
|---|---|---|
| F01 | メンバー管理 | 一覧・登録・編集・在籍状態変更。ID自動発行、退店時無効化、過去実績保持 |
| F02 | 営業実績管理 | 営業日・キャストを選び、5項目の実績を登録・編集。重複防止と過去実績修正 |
| F03 | 評価ルール管理 | Sheetsで計算単位・配点・有効／無効を設定。変更時は過去期間も再計算 |
| F04 | 評価一覧 | 月次の5項目・総合ポイント・順位をキャスト別に表示。ポイント順／個人売上順に対応 |

初期画面は「メンバー管理」「営業実績入力」「評価一覧」の3画面。ルール専用画面・評価結果の固定保存は設けない。業務ルールは [03_domain_model.md](03_domain_model.md)、保存形式は [05_data_model.md](05_data_model.md) を参照。

## 中核の利用フロー（Golden Path）

一次ユーザーは管理者。店舗業務を変更せず、登録した日次実績に設定ルールを適用し、月次評価と順位を確認できた状態をゴールとする。

| # | 操作 | 観測できる成功条件 |
|---|---|---|
| 1 | キャスト登録・評価ルール設定 | ID付きメンバーと設定値を読み直せる |
| 2 | 営業日・キャストを選び5項目を保存 | 再表示で実績を確認でき、同一日・同一キャストは重複しない |
| 3 | 必要に応じて登録済み実績を修正 | 同じ実績の値が更新され、月次集計に反映される |
| 4 | 対象月を選び評価を確認 | 期間集計後に計算したポイント・個人売上・順位を確認できる |

[アーキテクチャ](02_architecture.md) と [公開後の確認](08_release_runbook.md) でもこの流れを使う。

## 品質・運用の要件

管理者限定アクセス、サーバー側入力検証、ID管理、排他制御、重複防止、GASの実行制限を考慮した一括読み書きを必須とする。スマートフォンで主要操作が完結し、管理者が基本操作を理解でき、日次入力の負担が許容範囲であることを確認する。

## 非対象と将来候補

POS・注文・決済、商品・在庫、勤怠・シフト、顧客・予約、給与、会計・税務・経理は原則として本体に実装せず、将来も専門SaaSの利用・連携を優先する。

| 将来候補 | 検討する条件 |
|---|---|
| 指名種別 | 店舗に複数種類の指名評価が必要 |
| 共同売上按分 | 店舗側の按分処理が負担 |
| CSVインポート | 手入力の負担が大きい |
| POS API連携 | 対応POSと導入需要を確認 |
| ルール履歴 | 過去評価を固定する必要 |
| 評価ランク | 店舗が実際にランク制度を使用 |
| キャスト用画面 | 本人による評価確認の需要 |
| ネイティブアプリ | Webで満たせない要件 |
| 複数店舗 | 複数店舗から導入需要 |

詳細KPI分析、高度なグラフ、複雑な評価アルゴリズム、時給査定・給与反映もMVP対象外。将来候補は実装予定の確約ではない。

## 開発判断・段階

新機能は①評価に直接必要か、②既存システムで代替できないか、③実店舗の課題として確認したか、④評価モデルを変えず実装できるか、⑤未実装でも業務が成立するか、で判断する。⑤がYESなら原則後回し。

Phase 1は最小MVPで評価業務を検証。Phase 2は実店舗で確認した課題のみ改善。Phase 3で横展開の需要、API・DB基盤、PWA / React Native + Expo / Flutterを判断する。需要の検証前にSaaS化を先行しない。

二重入力の負担、設定では吸収できないルール、POS相当の機能要求、過大な連携・保守コスト、評価専用ツールへの需要不足は方針の再検討条件とする。

## 受入基準・未決事項

正本§16の機能9項目・運用4項目を [07_test_strategy.md](07_test_strategy.md) で確認する。仮KPIは全キャスト分の日次入力5分以内、営業日の登録継続率90%以上、評価計算のテストケース100%一致、既存業務の変更は原則不要。実店舗で調整する。

未定義の詳細は [索引の未決事項](00_index.md#未決事項) で追跡し、決定した仕様を正本と派生文書へ反映する。
