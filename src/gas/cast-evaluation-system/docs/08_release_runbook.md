# 08 リリースRunbook

根拠: [基本仕様・設計 v0.3.0（Draft）](<tasks/01_idea/Cast Evaluation System — 基本仕様・設計.md>) §7.5、§11〜13、§16。正本を優先し、以下は実装・運用準備のための文書とする。実施済み・受入済みの記録ではない。

## 状態と適用範囲

アプリケーション、実テスト、GAS接続・公開設定、具体的なデプロイ／復旧コマンドは未整備。以下は初回公開前に具体化・検証する手順であり、公開完了報告ではない。

設計上はGit / claspで管理するが、スクリプトID・スプレッドシートID・公開URL・利用アカウント・既存デプロイを推測しない。

## 初回公開の前提

- [中核フロー](01_requirements.md) と [テスト戦略](07_test_strategy.md) に対応する実装・実行可能な検証を用意する。
- [未決事項](00_index.md#未決事項) のうち、認証・日付・集計表示・ルール検証など当該公開に必要なものを決定する。
- 管理者限定となる公開・実行権限とSheets共有範囲を利用アカウント環境に合わせ、対象外ユーザーからのアクセスを確認する。
- 実環境の接続先・対象版・反映差分・直前の動作版・復旧手順を明確にする。
- データの退避・復旧方法を決定し、検証用データで確認する。アプリの自動バックアップ機能を新たなMVP要件として追加しない。
- 実績・ルール変更がある場合は影響範囲を示す。運用開始後のルール変更では過去期間の再計算を管理者が確認する。

本番反映や実データ変更は対象と影響を明確にした依頼の範囲で実施する。文書更新やローカルテストだけで本番操作の実施を意味しない。

## 公開の進め方（具体手順は実装時に確定）

1. Git管理状態・対象ソース・検証結果を確認する。雛形Makefileの成功表示を根拠にしない。
2. 検証用のGAS / Sheetsに対象版を反映し、接続・権限・3シート構成を確認する。
3. スマートフォンで中核フローと重要な異常系を実施する。
4. 反映先・実行ユーザー・公開範囲・復旧方法を確認し、対象の公開版へ反映する。
5. 公開後の確認結果を [受入書式](templates/platform-acceptance.md) に残す。

ツールのバージョン、認証方法、具体コマンドと結果は実際に確認した後で記録する。push・公開・実機受入・実店舗検証を別の状態として扱う。

## 公開後の確認（Golden Path）

実績を汚さない検証環境または合意した検証データを使用する。使用した環境・データ・版を記録し、検証データの本番混入を避ける。

| # | 操作 | 期待する観測結果 |
|---|---|---|
| 1 | 管理者で開き、メンバー登録・ルール設定 | ID付きメンバーと設定値が読み直せる |
| 2 | 営業日・キャスト・5項目を保存 | 同一日・同一キャストにつき1レコード。再表示で値が一致 |
| 3 | 実績を修正 | 既存レコードの値が更新される |
| 4 | 対象月の評価を表示 | 期間集計後の計算値、個人売上、同点判定を含む順位が期待値と一致 |

追加で、非管理者の拒否、同時登録の重複防止、スマートフォン操作を確認する。ローカルテストやビルドだけで公開後の確認を代替しない。

## 障害時の復旧計画

権限逸脱、データ欠損・重複、誤集計、中核フローの不成立があれば運用継続可否を判断し、影響する更新を止めて状態を確認する。

- コードの問題：確認済みの直前版へ戻す方法を初回公開前に用意し、復旧後に中核フローを再確認する。
- データの問題：影響範囲・現在値・退避データを照合し、復旧内容を確認してから対応する。無条件な全体上書きを復旧手順にしない。
- ルールの問題：コードを戻してもSheetsの設定値は戻らない。変更前の値と影響期間を確認し、管理者確認の上で戻し、過去月を再計算する。
- 通信障害：書き込みの成否を照合してから再操作する。重複登録を避ける。

具体的な戻し方・退避先・担当者は未決定。これらを実環境で確認するまでは「復旧可能」と記載しない。

## 公開後の運用検証

管理者の操作理解、入力負担、既存POS・会計を変更せず運用できることを確認する。正本§16の仮KPI（全員分5分以内、営業日90%以上、計算100%一致、既存業務変更は原則不要）を測定する。

技術的な公開成功とMVP受入・実店舗での有効性を区別する。未解決事項はタスクへ記録し、確定した手順のみこの文書へ反映する。
