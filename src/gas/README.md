# GAS アプリ集：プロジェクト案内・学習テーマ・内製化支援

身近な遊び・写真日記・英語学習・店舗業務を入口に、AI・プログラミング・データモデリングを学ぶためのディレクトリ。Google Apps Script（GAS）を中心とした小規模アプリを教材とし、本人が理解している世界を、データと処理の仕組みへつなげる。

この README は、共通の教育方針、対象者別の学習体験、各プロジェクトへの入口、横断的な機能案、内製化支援の商品構想を整理する。教育の到達目標と個別アプリの実装範囲を分け、現行仕様や開発手順は各 README とそこから参照する正本に従う。

## 現在の優先順位

**事業化は後回し。題材は既存5プロジェクトに固定し、新しい教材テンプレートを増やさない。**

まず5教材の責任領域と学習成果を明確にし、既存アプリの検証と、再利用できる仕様・受入条件・解説を整える。同じ題材にGAS版とNext.js＋Supabase＋Vercel版の模範実装を用意する方針とし、利用実績や教育効果を確認できたものから段階的に進める。5教材すべての2基盤化を一度に行わない。

当面の成果は、販売件数ではなく「本人が理解して変更・検証できる教材」と「比較に使える検証済みの模範実装」。価格・収益試算・有料検証は、将来事業化を検討するときの仮説として保持する。今回の方針更新だけでNext.js版の実装、ディレクトリ移動、募集・販売を開始したことにはしない。

## 身近な世界をプログラミングへ翻訳する教育モデル

**「相手が既に理解している世界を入口に、AI・プログラミング・データモデリングを学ぶ。」**

本人が関心を持つ遊び・記録・学習・仕事の課題から始める。まずアプリを体験し、身近な対象の関係を言葉にして、設定や小さな変更を試す。その過程でデータ設計・処理・AI活用・検証を学ぶことを、このアプリ集の共通の教育方針とする。

出発点は、企画者が実際に受けている相談や、身近な人との接点である。保護者からの「子供に将来プログラマーになってほしいが、どうしたらよいか」という相談、海外で働きたい英会話学習者との会話、ナイトワークの女性にとって身近な写真日記や店舗業務を、教材の入口へ変換する。

これらは企画者の接点から得た対象者の仮説であり、女性・職業・学習者全体の傾向を示す市場調査ではない。本人の興味、学びたい範囲、困っていることを確認して題材を選ぶ。

### 対象者・題材・提供価値

| 教材 | 想定する対象者・相談 | 身近な入口 | 提供したい価値 |
|---|---|---|---|
| [skill-janken](skill-janken/README.md) | プログラミングに関心のある子供と、将来の学び方を相談する保護者 | じゃんけん・仲間・スキル・ポイント | 遊びを通じた論理的思考と、自分でルールを変える楽しさ |
| [ai-english-trainer](ai-english-trainer/README.md) | 海外で働くことに関心がある英会話学習者。企画者が接する女性学習者を含む | 自分の英語学習・AI会話・振り返り | 英語とITスキルの接点を作り、自分の学習を改善する経験 |
| [ai-photo-diary](ai-photo-diary/README.md) | 写真日記を身近に感じるナイトワークの女性など | 写真・日記・思い出・タグ | 身近な情報をデータとして整理し、関係を設計する能力 |
| [cast-evaluation-system](cast-evaluation-system/README.md) | 独立を計画し、複数キャストを雇う予定のキャスト・店長 | ドリンク・指名・売上・評価 | 自分の店舗業務を自分で改善する能力 |

保護者の希望だけで進路を決めず、子供本人が遊んで興味を持ち、試したいと思える体験を入口にする。成人向けは知識量だけでなく、本人の課題を解決できたかを重視する。

4教材は共通概念へ到達する異なる入口であり、全員が順番に修了するコースではない。ECは引き続き取引・明細・確定時点の保存を学ぶ題材とし、今回のFBから新たな対象者像を決めつけない。

### 日常の言葉からデータの関係へ

| 教材 | 最初に話すこと | つなげる基礎概念 |
|---|---|---|
| じゃんけん | 「どの仲間がどのスキルを使える？」「この条件なら何点？」 | 条件分岐、状態管理、1対多・多対多、IDと対応表 |
| 写真日記 | 「日記に何枚の写真を載せる？」「同じタグを別の日記でも使う？」 | データ構造、添付、分類、関連付け、一覧・絞り込み |
| 英語訓練 | 「どの問題にどう答えた？」「AIは何を返した？」 | API、AI連携、問題・回答・評価の分離、履歴・版管理 |
| キャスト評価 | 「誰の、いつの実績？」「配点を変えたらどうなる？」 | 業務分析、ルールと実績の分離、期間集計、業務システム設計 |

写真日記なら、「1つの日記に複数のタグを付け、同じタグを別の日記でも使う」という話から多対多を説明し、日記とタグを結ぶ記録を考える。最初に専門用語を覚えさせるより、本人が理解している関係を言葉・図・表にしてから、IDや中間テーブルへつなげる。

現行の写真日記ではタグは日記に関連付く。写真への直接のタグ付け機能があるようには説明しない。また、保存済み日記の編集・削除は対象外。CRUDの概念を紹介する場合も、現在使える登録・参照と、別途設計が必要な更新・削除を区別する。「改修できる」は将来の学習到達目標であり、すべてが設定画面で変更できるという意味ではない。

### 英語学習とITスキルを結びつける

海外で働きたい学習者に、「英語を勉強するためのアプリを、自分でAIを使って改善する」という体験を提供する。英語学習そのものと、その学習を支える仕組みづくりを結びつける。

学習活動の候補は次のとおり。

- GitHubで自分のコードと変更履歴を管理する。
- GASでWebアプリを動かし、データの保存先と画面の関係を理解する。
- GeminiなどのAI APIへの入力・応答を確認する。
- 問題・回答・評価・学習履歴を読み、自分の振り返りに使う。
- 必要な英語の技術ドキュメントを読み、調べた内容を変更へつなげる。
- Devin等へ要望と期待する結果を伝え、差分と動作を確認する。

成果物はアプリだけでなく、本人が説明できる変更内容、検証記録、英語学習の記録を組み合わせる。公開用の作品紹介を作る場合は、秘密情報や私的な会話履歴を含めず、本人が担当した部分を示す。

これは技術職やITを活用する仕事への入口を目指す教育案であり、1つのGASアプリの制作で海外就職できるという約束ではない。英語力や就業能力の向上は、アプリ完成とは別に確かめる。

### 教材に共通する6工程

| 工程 | 学習者の行動 | 共通化する指導・教材 |
|---|---|---|
| ① 体験 | 動作確認済みのアプリを使い、自分が変えたい点を見つける | 操作案内、体験時の問いかけ |
| ② 理解 | 身近な対象・関係・処理を、自分の言葉や図で説明する | データの関係を整理するワーク |
| ③ 設定 | 対応している設定を変え、結果を予想する | 変更前の記録、設定範囲の確認、期待値の書き方 |
| ④ 改修 | 必要な小さな変更をDevin等へ依頼し、差分を読む | 要望・対象範囲・期待結果を伝える型 |
| ⑤ 検証 | 予想と実際を比べ、修正・再実行・復旧を試す | テストと確認記録、戻し方 |
| ⑥ 自立 | 次の改善を自分で選び、必要な支援を判断する | 振り返り、次の課題、相談材料 |

設定可能な範囲やデータモデルはアプリごとに異なる。共通化するのは教え方と変更・検証の進め方であり、各アプリを同じ仕様へ作り変えることではない。

子供向けのAI操作や契約・アカウント準備は、大人が伴走する形で設計する。現行skill-jankenは提供者の管理端末・本人限定公開を前提とし、子供本人のDevin契約や自由なプロンプト入力を受講条件にしない。アプリごとの利用形態を教材にも反映する。

### 記事・動画と対面30分×3回

**記事・動画で繰り返し確認できる知識を提供し、対面では本人の理解と操作を支援する。** 対面30分×3回を初期の指導構成案とし、すべての導入・開発・公開を90分で完了する保証にはしない。

| 回 | 対面で扱うこと | 本人が示す成果 |
|---|---|---|
| 1回目・30分 | アプリを体験し、題材のデータ関係を一緒に整理する | 「何を保存し、何とつながるか」を言葉や図で説明する |
| 2回目・30分 | 小さな設定変更、または準備した改修課題を試す | 変更前に結果を予想し、自分で操作する |
| 3回目・30分 | 変更を検証し、つまずき・戻し方・次の改善を振り返る | 何を変え、どう確かめたかを説明・再現する |

記事は概念・操作手順・確認事項、動画は操作の実演、対面は理解の確認と個別のつまずきに充てる。環境準備と事前視聴の範囲を先に示し、各回の間にできる小さな課題を用意する。子供の場合は保護者にも、本人が理解できたことと次の関心を共有する。

共通コンテンツはアカウント・データ・AIへの依頼・差分確認・テスト・復旧。題材別コンテンツはゲームの条件、写真とタグ、問題と回答、実績と配点に分ける。受講者のつまずきを教材の版とともに記録し、説明・例題・動画を改善する。講師が毎回最初から説明する負担を減らし、教材が増えても指導ノウハウを蓄積できる形を目指す。

### 対象者ごとの成功条件と見直す兆候

| 対象 | 成功条件 | 見直す兆候 |
|---|---|---|
| 子供 | 小さなルール変更を自分で試し、結果と理由を説明できる | AIや講師が完成させ、本人は変更内容を理解していない |
| 海外志向の英語学習者 | 英語とITを使った成果物が残り、自分の変更を説明できる | アプリ完成だけで海外就職できるという期待が先行する |
| 写真日記の利用者 | 日記・写真・タグの関係を説明し、小さな変更と検証ができる | 私的な写真・顧客情報が教材や公開例に混入する |
| 独立予定のキャスト・店長 | 店の評価方法を設定し、結果を確認して運用できる | 技術学習が開業準備の負担になり、評価業務の必要性も低い |

完成画面だけでなく、本人の説明、操作の再現、変更前の予想と確認結果を記録する。子供向けは楽しさと理解、成人向けは具体的な課題解決を重視する。写真日記の教材は架空データや利用許可を確認した画像で作り、本人専用の公開範囲・AIへ送る内容を理解することも学習に含める。

### 教材提供前の検証と教育モデルの検証

プロジェクト一覧の実装状況と、教材として提供できる状態は分けて管理する。

| 段階 | 確認すること |
|---|---|
| ローカル | 配布対象の最新版でテストと画面確認を行う |
| 実環境 | 実GAS・Sheetsと、採用しているDrive・AIサービスで主要操作を確認する |
| コピー・引き渡し | 新規環境で初期設定・権限・保存先を確認し、元のデータや秘密情報が混入しないことを確かめる |
| 教材との一致 | 配布版と記事・動画の手順を揃え、学習者または保護者・講師が再現できるか確認する |
| 少人数の指導 | 各対象者の成功条件、必要な介助、所要時間、次も改善したいかを観測する |

提供者管理端末で使う子供向けと、本人の環境へ導入する成人向けでは、引き渡し・準備の条件を分ける。公開環境が既にあるアプリでも、最新版の受入やコピー先での動作を省略しない。キャスト評価は設計段階から検証用MVPを用意する必要がある。

検証結果は、アプリが動いたこと、本人が理解して変更できたこと、指導時間・支援負担、支払い意思を分けて記録する。教育効果や販売需要を、既存の相談があることだけで実証済みにはしない。

## 5教材の役割分担と全体最適化

**5つの専門ドメイン × 2つの技術基盤 × 1つの共通教育メソッド**を目指す。題材を増やす代わりに、重複する業務機能を必要最小限にし、各教材の特徴と学習成果を強める。

以下を教材全体の役割分担の方針とする。個別アプリの現行仕様を一括変更する指示や、実装済み機能を直ちに削除する計画ではない。機能の整理は、個別の正本・利用実績・受入条件に照らして判断する。

### 各教材の中心ドメイン

| プロジェクト | 中心ドメイン | 強化する専門性 | 意図して広げない・薄くする機能 |
|---|---|---|---|
| skill-janken | ゲーム | 条件分岐、状態遷移、ゲームルール、行動と結果の関係 | 汎用ポイント基盤、複雑なユーザー管理 |
| ai-english-trainer | 教育・学習 | AI採点・会話、学習評価、回答・評価・振り返りの関係 | 汎用日記、写真管理 |
| ai-photo-diary | コンテンツ管理 | 写真・日記・タグ、AI下書き、情報の保存と検索 | 学習評価、複雑なAIエージェント |
| cast-evaluation-system | 業務評価 | 営業実績、変更可能な評価ルール、月次計算・ランキング | POS、会計、給与 |
| ec-shop | 商取引 | 商品、カート、注文、明細、確定時点の情報と整合性 | 汎用顧客管理、会計、キャスト評価 |

専門性の強化は機能数の増加に限定しない。データ設計の理由、境界条件、失敗時の挙動、検証例を分かりやすくすることも強化に含める。

写真日記の保存後の編集・削除、英語訓練の新たな習熟度分析などは、中心ドメインに近くても現行の提供機能と同一視しない。追加が必要なら、学習目標と個別仕様を先に確認する。

### 重複しやすい3組の境界

| 組み合わせ | 重なって見える要素 | 分ける業務上の意味 |
|---|---|---|
| skill-janken × cast-evaluation-system | ポイント、結果の表示 | ゲーム内の行動・状態に応じた得点と、営業実績に評価ルールを適用した結果 |
| ai-english-trainer × ai-photo-diary | LLM、履歴、テキスト生成 | 学習者への評価・対話・振り返りと、個人の記録を支援する下書き |
| ec-shop × cast-evaluation-system | 金額、人にひも付く記録 | 注文者と注文・明細の成立と、キャストに帰属する営業実績の評価 |

同じ名称の「ポイント」でも、ゲームの得点と営業評価では意味・計算・保持方法が異なる。名前だけで巨大な共通ポイント管理へまとめない。現行skill-jankenではランキングは対象外であり、キャスト評価との比較のために追加しない。

英語訓練と写真日記はAIへの要求や応答を扱うが、採点基準・回答履歴・教材の版と、日記本文・画像・タグの関係は別に設計する。LLMを使うことだけを理由に、両者を汎用AIアプリへ統合しない。

ECが扱うのは注文・明細と注文時点の金額であり、現行初期範囲では決済・会計上の売上確定を扱わない。キャスト評価は既存POS・会計等で店舗が確定した評価用金額を入力する。ECの注文者とキャストも同一の役割ではない。将来連携を検討しても、データの正本・金額の意味・帰属方法を先に決め、1つのアプリへ統合する前提にしない。

認証の説明は共通化できても、本人専用、提供者の管理端末、管理者限定、架空ユーザーを選ぶ学習用という利用形態は同じではない。共通ライブラリや共通画面を先に作り、個別の仕様をそれに合わせる順序にはしない。

### Portfolio Architecture Review

まず上記の責任領域を基準として持ち、比較できる実装・検証結果が揃った段階で、**Portfolio Architecture Review（ポートフォリオ横断のアーキテクチャレビュー）**を行う。

現状は5つすべての実装が揃っておらず、Next.js版も今後用意する模範実装。全10実装を急いで完成させるのではなく、1題材の両版が揃うごとに確認し、各教材の比較材料が揃った時点で全体を再整理する。

レビューでは次を確認する。

1. 各教材の中心ドメインと、本人が得る学習成果が明確か。
2. 同じ業務機能を別の教材でも厚く作り、役割が重複していないか。
3. 同じ技術を使うだけの類似と、意味まで一致する共通部分を区別できているか。
4. 機能や説明を薄くしても、中核の操作・受入条件・学習目標が成立するか。
5. 共通の記事・動画・検証手順として再利用できるものは何か。
6. 同じ教材のGAS版とNext.js版が、共通の業務要件・受入条件を満たすか。
7. 両版の保守と教材の更新に必要な工数が、教育効果に見合うか。

| レビュー記録 | 残す内容 |
|---|---|
| 対象と根拠 | 教材・機能・仕様版・実装版・利用や検証の記録 |
| 意味と学習目標 | 何のための機能か、学習者が何を理解できるか |
| 判断 | 固有のまま強化／維持／薄くする／共通教材へ整理／共通コード候補／保留 |
| 影響 | データ・利用者・公開範囲・受入条件・両実装・記事動画への影響 |
| 次の作業 | 個別正本へ反映する変更、検証方法、移行・復旧の必要性 |

重複が見つかっただけで削除・統合しない。独立した教材を理解するために必要な説明や基本操作は残す。データ保持・権限・整合性の保証も、差別化のために薄くする対象にしない。承認された個別変更だけを各プロジェクトの正本・実装・テストへ反映する。

この整理で蓄積するのは、特定のAIツールの操作手順だけでなく、身近な世界をデータとルールに分け、AIを使って実現し、自分で検証するための知識と手順である。

## 題材を固定し技術レベルを広げる

### 同じ題材に2つの模範実装

既存の5教材に対し、**GAS版**と**Next.js＋Supabase＋Vercel版**を模範実装として用意する。模範実装は単一のコード上の正解ではなく、同じ仕様・受入条件を満たす検証済みの比較対象とする。発展版は今後の準備対象であり、現行GAS版も検証状況はプロジェクト一覧に従う。

| 学習の入口・発展 | 技術・道具 | 学ぶこと |
|---|---|---|
| Level 1：GAS | Google Apps Script＋Google Sheets | データの関係、登録・参照、業務ルール、AIへの開発指示。更新・削除は各アプリの仕様に応じて扱う |
| Level 2：Web開発 | Next.js＋Supabase＋Vercel | SQL、リレーショナルDB、認証・認可、RLS、API、デプロイ、テスト、運用 |
| Level 3：AIによる改善 | Devin等＋仕様・テスト・模範実装 | 独自要件を整理し、AIの変更案を検証・比較して改善する |

GASを修了しなければ発展版へ進めない、という制約は設けない。経験・関心・目的に応じて入口を選ぶ。Level 3のAI活用は両基盤で行え、本人の理解・判断・検証を伴う改善を目指す。

| 既存教材 | GAS版を通じて学ぶこと | 発展版で深める観点 |
|---|---|---|
| skill-janken | 条件分岐・状態管理・仲間とスキルの関係 | ゲームロジックとDB設計、更新の整合性 |
| ai-english-trainer | AI API・問題と回答・評価・学習履歴 | 認証・AI連携・学習データの管理 |
| ai-photo-diary | 写真・日記の登録と参照・タグ | Storage、リレーショナルDB、画像と記録の権限 |
| cast-evaluation-system | 実績・評価ルール・期間集計 | 認可・RLS、複数利用者を扱う場合のデータ分離 |
| ec-shop | 商品・注文・明細・確定時点の保存 | 注文整合性、DBトランザクション |

発展の観点を、現在のGAS版の追加要件にしない。特にキャスト用画面・複数店舗・複数利用者への拡張は、既存の管理者限定MVPとは別に範囲と受入条件を決める。認証機構が異なっても、同じ基本課題では元の利用者・公開範囲を尊重する。

### 正解は共通の受入条件で判断する

学習サイクルは **AIに開発・改修を依頼 → 自分で検証 → 模範実装と比較 → 理由を説明して改善** とする。比較前に期待する結果を言葉にし、実際の動作とデータで確かめる。

同じ教材のGAS版、Next.js版、学習者の実装で共通にするのは業務要件・入力例・期待結果・守るべき制約。異なる5教材の業務ルールまで同一化するものではない。見た目やコード構造が違っても、合意した仕様と受入条件を満たせば正解とする。模範コードの丸写しを合格条件にしない。

| 共通化するもの | 基盤ごとに用意するもの |
|---|---|
| 機能仕様、非対象、利用者と公開範囲 | GAS／SheetsまたはNext.js／Supabaseの具体構成 |
| データの意味、業務ルール、入力と期待値 | 物理スキーマ、通信、認証・認可の実装 |
| 中核の操作シナリオ・受入テスト仕様 | 各環境で動かすテストコード・テストデータの投入方法 |
| 学習目標、問いかけ、変更課題 | 導入・公開・復旧手順、画面操作の動画 |
| 仕様版と受入条件の対応 | 実装版・検証結果・既知の差分 |

同じテストコードを無理に共用するのではなく、同じ受入テスト仕様を各基盤で実行できる形にする。DBや認証の違いによる検証は、共通の業務テストに加えて行う。

たとえばキャスト評価では、期間合計後のポイント計算、同点順位、重複防止、退店後の実績保持を共通条件にできる。一方、ルール履歴やキャスト用画面を追加する課題は拡張仕様として分け、元の正解を暗黙に変更しない。

### 教材の管理構成案

```text
skill-janken/
├── spec/       # 共通の機能仕様・非対象
├── gas/        # GAS模範実装
├── nextjs/     # Next.js＋Supabase＋Vercel模範実装
├── tests/      # 共通の受入テスト仕様・入力例・期待値
└── lessons/    # 記事・動画・AI演習
```

これは将来の整理案であり、現在のファイル配置ではない。既存のsrc/・docs/等から直ちに移動せず、発展版を作る題材を選んだ時点で移行方法と参照を設計する。同じ役割を既存の構成で満たせるなら、名前を揃えるためだけに移動しない。

模範解答にはコードに加え、仕様、データ設計の理由、テスト、導入・運用・復旧手順、学習者が比較する観点を含める。記事・動画と両実装がどの仕様版に対応するかを記録する。

### 10実装を抱え込まない進め方

最初に選ぶのは1題材。利用実績・教育効果・現行版の安定性・発展版で学ぶ価値を見て選び、GAS版と発展版を共通条件で検証してから、他の題材へ進む。

5教材×2基盤の保守負担を前提に、共通仕様と実装差分を分け、変更時には両版への影響を確認する。未対応の版は未対応と明記し、仕様も挙動も揃っていない状態を同等の模範実装として配布しない。

Next.js版はGASコードの単純変換で完成としない。認証、RLS、許可されていないデータへのアクセス拒否、Storageの公開範囲、秘密情報、AIの外部送信、注文等の更新整合性を、その環境で検証する。具体的な構成・コマンド・サービス条件は実装時に公式情報と照合する。

対面30分×3回は初期導入・理解・AI活用の伴走の構成案。90分で全基盤を習得させるものではなく、その後も記事・動画・模範実装を使って同じ題材を深められるようにする。

### 拡張課題を作る場合の書式案

採用を検討する課題ごとに、対象プロジェクト、学習目的、前提知識、追加機能、データモデルへの影響、変更してはいけない既存機能、AIへの依頼例、受入条件、模範実装と比較する観点を整理する方法が考えられる。現時点で全課題の作成や模範実装を必須にはしない。

参考例として「skill-jankenのAI攻略アドバイザー」を検討するなら、次のような確認観点がある。

- AIに渡す状態・履歴と、返してよい提案の範囲を定義する。
- 提案と理由を表示し、勝敗判定・既存のゲーム状態を変更させない。
- 提案失敗や不正な行動の提案でもゲームを継続できることを確認する。
- 追加したアドバイザーを無効にしても、元のゲームが成立することを確認する。
- APIキーを公開せず、呼出回数や費用の扱いを決める。
- 現行CPUの仕組みに照らし、根拠のない必勝策や優位性を説明しない。

これも課題の採用決定や実装要件ではない。子供向けの利用形態、大人の伴走、現在の自由入力・公開範囲の制約も含め、採用する場合に具体化する。

必要性や学習効果を確認した候補だけを、ポートフォリオの役割分担・現行仕様・保守負担と照合する。その後、個別プロジェクトで範囲・受入条件・仕様変更を決定する。ここに記載しただけでタスク化・開発着手・販売案内へ進めない。

すべての候補に模範実装を用意する必要はなく、採用した代表課題だけを例示し、他は学習者が考える余地として残す方法もある。採用しない、簡素化する、後で見直す選択を残す。

### 本業の専門能力を再利用できる教材へ

事業化は後回しとし、以下は将来の判断材料として残す。AIプラットフォームエンジニアのフリーランス活動を収入・専門能力の基盤と位置付け、教材ではその一部を、一般の人が理解し使えるコード・動画・記事・導入手順へ変換して蓄積する。

| 収益 | 案件・専門性・稼働に応じた対価 | 教材の再利用と範囲を決めた支援への対価 |

| 成立条件 | 案件に必要な成果を出せる | 教材だけで進める範囲が増え、支援負担を把握できる |

収入額の優劣を目標にせず、専門能力と教材資産が相互に育つ構造を目指す。教材の再利用で稼働依存を下げられる可能性はあるが、制作・更新・支援の時間がなくなるわけではない。

保護者からの相談、海外志向の英語学習者、ナイトワークや独立予定者との接点は、課題を聞いて試してもらう入口として活かす。接点があること自体を、購入需要や教育効果の証明とはしない。

### 仮価格による売上シミュレーション

将来の価格仮説は教材単体19,800円、対面30分×3回（計90分）の伴走付き59,800円。伴走の提供範囲をこの検証用の仮案に合わせる。確定価格ではなく、支援範囲・対象教材・提供条件を決めてから検証する。

| 商品案 | 仮単価 | 仮の月間件数 | 月間販売額 |
|---|---:|---:|---:|
| 教材単体 | 19,800円 | 5件 | 99,000円 |
| 教材＋対面90分の伴走 | 59,800円 | 3件 | 179,400円 |
| 合計 | — | 8件 | 278,400円 |

- 月商の単純試算：278,400円。
- 同じ販売数が12か月続くと仮定した年間売上：3,340,800円。
- 対面枠のみの時間：90分×3人＝270分＝4.5時間／月。

件数・価格は仮説であり、予測や達成目標ではない。教材制作・更新、事前準備、移動、集客、質問対応、個別改修、決済手数料、税金等を差し引く前の売上。4.5時間は総労働時間ではない。利益や本業との比較には、実際の総工数と費用を別途記録する。

### 事業化を検討する段階での初期検証

将来の有料検証の目安は、**自分の知人以外の3人が購入し、90分の伴走後に合意した小さな変更を自分で行い、検証・説明できること**。紹介経由でも本人とは面識がない購入者等を対象にし、既存の知人の好意による評価と分けて記録する。

現時点で有料募集や売上目標を設定するものではない。先に教材の再現性と対象者別の学習成果を確認する。子供向けでは購入者の保護者と学習する本人を区別し、本人の理解を評価する。

記録するのは、購入条件、開始時の経験、本人が行った変更、伴走前後の到達、追加支援時間。3人の成立だけで継続的な収益性まで証明したとは扱わない。

次の状態では商品・教材・支援範囲を見直す。

- 個別サポートが毎回何時間も必要になる。
- Devinの操作や変更判断を代行し続け、提供者が実質的に開発を請け負う。
- 動画と手順で導入・確認を再現できない。
- 関心は示されるが、示した条件で購入する人がいない。
- 2つの技術基盤の保守が、得られる学習価値や提供余力に見合わない。

安価な受託開発へ変質させず、支援外の個別開発は別途扱う。学習者が自立するほど、教材・伴走の目的を達成できたと判断する。

### 資産が蓄積する循環

既存テンプレートを整備 → 記事・動画・対面で自立を支援 → 利用者の質問・改善を観測 → 共通教材と模範実装を改善 → 次の学習者へ再利用する。

当初は講師の能力に依存する部分を、説明・例題・受入テスト・導入手順へ移していく。本業で培うAI活用・業務分析・データモデリング・自動化・プロダクト設計も、教材化を通じて説明可能な知識へ整理する。これを小規模な教育・ソフトウェア事業へ発展させられるかは、将来あらためて検証する。

## 独立開業者向けの内製化支援キット

事業化を検討する段階での提供案。当面は既存教材・模範実装・教育手順の整備を優先する。

### 提供する価値

**「自分のお店の仕組みを、自分で作り、変えられるようになる。」**

共通の教育モデルを独立開業者向けに具体化する。キャスト評価アプリを入口に、独立後も店舗の業務を自分で改善し続ける能力を提供する。プログラミングやGASの習得自体を目的にせず、オーナーが店舗のルールを理解し、設定変更や必要な改修を判断できるようになることを重視する。

商品名の仮案は **Cast Evaluation Starter Kit — 独立開業者向け・AIで育てる店舗評価システム**。完成アプリ・ソースコード・Devinを使う改修環境の案内・導入運用動画を組み合わせた、小規模店舗向けの内製化支援を目指す。

これは商品構想であり、現在の販売商品ではない。キャスト評価アプリは設計段階で、完成アプリ、配布用コード一式、Devin環境、教材動画、導入・復旧手順の検証はこれから準備する。需要、学習効果、支払い意思も未検証。

### 対象者と訴求

主な対象は、**ガールズバー・スナックでの独立を計画し、将来キャストを複数人雇う予定がある人**。キャスト経験を持ち、自分の店の評価ルールを考えたい人を想定する。

独立希望者全般を一律の対象にしない。一人で運営する予定ならキャスト評価が不要な場合があり、物件・開業資金・集客より優先順位が低い可能性もある。評価業務への具体的な必要性を先に確認する。

案内の中心は「このアプリを作れるようになりませんか？」から、次へ置き換える。

> 独立したとき、自分のお店のルールに合わせた管理アプリを、自分で作って変更できるようになりませんか？

### 商品構成の案

| 提供物 | 内容 | 購入者が目指す状態 |
|---|---|---|
| GASアプリ＋MVPソースコード | メンバー管理、5項目の日次実績、ポイント設定、月次評価・ランキング | 自分のGoogleアカウントで導入・運用できる |
| Devin活用環境・教材 | GitHubリポジトリ、設計書、テスト、環境設定の案内、改修依頼用プロンプト | 店舗の要望を整理し、AIに変更案を依頼できる |
| 導入・運用の学習動画 | アカウント準備、GAS導入、日々の操作、設定変更、検証、公開、復旧 | 動画を見ながら必要な操作を再現できる |
| 検証・変更・復旧の一式 | 検証データ、テストコード、変更確認の手順、更新前の退避・戻し方 | 改修の影響を確認し、問題時に戻せる |
| 任意の個別支援 | 初回導入、店舗設定、必要な改修の相談 | 自力で難しい部分だけ支援を受けられる |

購入者が自分のGoogle・GitHubアカウントでコードとデータを管理し、特定の開発会社に頼り切らずに運用できる形を目指す。ソースの利用・改変・再配布の範囲は販売前に利用条件として定める。「ソース提供」と「著作権の譲渡」は同一視しない。

DevinはAI改修のための道具として位置付ける。Devinの契約・利用料は商品価格と分け、利用を希望する購入者が自身のアカウントで契約する想定。AI改修を希望しない人も、完成アプリの導入・日常運用・設定変更まで行える商品設計にする。

### 習得ステップ

| 段階 | 体験 | 到達の確認 |
|---|---|---|
| 1. 使える | 動画を見ながら導入し、キャストと実績を登録する | スマートフォンで登録・編集・月次評価を確認できる |
| 2. 設定を変えられる | 配点・計算単位・有効／無効を自分の店に合わせる | 変更後の期待値を説明し、結果が一致することを確認できる |
| 3. AIで作り変えられる | Devinに要望・対象範囲・期待する結果を伝える | 変更案と差分を確認し、検証環境で試せる |
| 4. 継続して改善できる | 必要な改修だけを反映し、問題時は戻す | テスト・反映・復旧を含む変更手順を再現できる |

最初からコードを書くことや、段階3への到達を全員に求めない。「まず動くアプリを使う → 必要な設定を変える → 必要になったら改修を学ぶ」の順序で、独立準備中の負担を抑える。

### 動画教材の構成案

1. 店舗の評価業務を整理する：対象者、5項目の実績、既存POS・会計との役割分担。
2. 自分の環境へ導入する：Googleアカウント、Sheets、GAS、管理者の権限とスマートフォンでの確認。
3. 日々の運用を行う：メンバー登録、実績入力・訂正、退店時の無効化、月次評価。
4. 店舗の設定を変える：配点・単位・有効／無効、計算例、過去期間への影響。
5. Devinで改修案を作る：GitHub、設計書とテスト、要望の書き方、変更差分の読み方。
6. 検証して反映する：検証用環境、期待値との比較、対象版と公開範囲の確認。
7. トラブルから復旧する：保存成否の照合、コード・データ・ルールそれぞれの戻し方、支援が必要な場合の連絡材料。

動画は配布するコードの版に対応させる。第三者サービスの画面や条件が変わった際の教材更新範囲も販売前に定める。

### 共通部分と店舗ごとの変更を分ける

| 区分 | 方針 |
|---|---|
| 共通テンプレート | 標準コード・設計書・テスト・教材を版とともに管理する |
| 店舗設定 | 配点・計算単位・有効／無効など、標準機能の設定で変えられる部分を明示する |
| 店舗固有の改修 | 設定では足りない変更だけを別の差分として管理し、検証範囲と支援条件を決める |

「同伴を週末だけ2倍にする」といった要望は、現在の固定カテゴリ・単純配点を超える**将来の改修例**であり、標準MVPで設定可能と案内しない。まず必要性・仕様への影響・既存業務での代替可否を検討する。

現在のMVPでは、評価ルール変更時に過去期間も再計算される。設定変更の教材にもこの制約と管理者確認を含める。AIがコードを変更できたことを、本番で問題なく運用できる証拠にしない。テスト環境で確認してから反映し、コードだけでなくデータ・設定の復旧も扱う。

任意のコード改変まで一律に無制限サポートする設計にはしない。標準版の不具合、導入支援、設定相談、店舗固有改修を区別し、対象版・期間・回数・対応範囲を明示する。共通テンプレートへ取り込む改善は、実店舗の必要性と検証結果を基に選ぶ。

### 提供・収益モデルの仮説

| モデル | 提供するもの | 収益の考え方 |
|---|---|---|
| アプリ販売・利用提供 | 完成した評価アプリの利用 | 月額等の利用料 |
| 制作教材 | コード、動画、変更手順、AI活用教材 | 教材・講座の代金 |
| 伴走型 | 店舗への導入と、変更できるようになるまでの支援 | 初期支援＋任意の継続支援 |

**将来事業化を検討する際は、少人数の伴走型で、購入者がどこまで自力で進められるかを検証する。** 共通のつまずきをコード・動画・手順へ反映し、その後に自習用キットの提供を検討する。継続支援を必須にして依存を残すより、設定変更や運用を自分で行える範囲が広がったことを成果として評価する。

| 商品案 | 検証用の仮価格 |
|---|---:|
| GASソース＋導入・運用動画＋Devin活用教材 | 19,800円 |
| 上記＋対面30分×3回（計90分）の伴走 | 59,800円 |
| 店舗独自の改修・相談 | 個別見積もり |

これらは提示されたFBに基づく価格仮説であり、販売価格・支払い意思を検証済みという意味ではない。税込／税別、利用条件、提供期間、更新・支援範囲は販売前に決める。

売上の仮試算と有料検証の目安は [将来の事業化仮説](#将来の事業化仮説) を参照。コードと動画を再利用できても、購入者ごとの支援負担を含めて判断する。

Devin・Google・GitHub等の第三者サービスは、料金・利用条件・必要なプランを販売時点の公式情報で確認する。本書では具体的なDevinのプラン価格や「すべて無料」を確約しない。教材代、任意の支援費、外部サービス利用料を分けて案内する。

### 将来の需要検証

事業化を検討する段階で実施する案。現段階の教材づくりでは、理解・操作・検証の再現性を先に確認する。

最初から大規模な有料講座を作らず、対象に合う5〜10人へ評価アプリのデモを見せて確認する。現状は設計段階なので、実際に触れる検証用MVPを用意してから操作を伴う検証を行う。

| 確認すること | 記録する反応・行動 |
|---|---|
| 評価業務の必要性 | 採用予定人数、開業時期、現在または予定している評価方法、他の開業課題に対する優先度 |
| アプリへの需要 | 既存の評価方法を自分の店でも使いたいか、日次入力の負担を許容できるか |
| 自分で変更する価値 | ポイントを自分で変えたいか、何を変えたいか |
| 学習への需要 | アプリだけ欲しいか、設定変更まで学びたいか、AI改修も学びたいか |
| 支払い意思 | 教材・導入支援・個別改修のどれに、どの条件なら支払うか |
| 実際の到達 | テンプレートで配点を変更し、期待した結果を自分で確認できたか |
| 支援負担 | 自力で完了した範囲、かかった時間、質問数、介助が必要な箇所 |

口頭の興味、操作できた事実、支払い意思、実際の購入を別々に記録する。動画だけで進めた場合と伴走した場合の違いも確認する。

結果に応じて次を判断する。

- アプリは必要だが制作学習の需要が弱いなら、利用・設定中心の商品にする。
- 学習意欲があり設定変更を再現できるなら、教材化を進める。
- 導入のつまずきが多いなら、動画・標準コード・初回支援を改善して再検証する。
- 評価自体の優先度が低い、対象店舗の需要がない、支援負担が大きすぎる場合は、対象者・商品構成・価格を見直す。

開業教育の市場があることと、キャスト評価アプリの制作学習に需要があることは別の仮説として扱う。外部の開業支援事例を使って告知する場合は、出典・開催時期・内容を確認し、未確認の紹介文を市場検証の証拠にしない。

### 個別アプリとの関係

この構想は「アプリを教材にした内製化支援」という提供方法を追加するもので、Cast Evaluation Systemをオールインワン店舗管理へ広げるものではない。プロダクトは引き続き **Small Core / Integration First** に従う。

教材の題材を別の店舗業務へ広げる場合も、キャスト評価アプリにPOS・会計・給与等を取り込まず、既存サービスとの組み合わせや独立した題材として扱う。Devinは開発・学習用の道具であり、評価アプリ本体へAI機能やDevin連携を追加することをMVP要件にしない。

## アプリから学ぶ基本の型

基本 4 アプリ（日記・英語訓練・EC・じゃんけん）に、実績集計・評価ルールを扱うキャスト評価を加えて整理する。

| プロジェクト | 学ぶ構造・処理 | 応用先の例 |
|---|---|---|
| ai-photo-diary | 記録の登録・一覧・絞り込み、画像添付、タグ、AI 下書き | 作業日報、点検記録、問い合わせ受付、記事管理 |
| ai-english-trainer | 出題・回答・評価、対話、履歴、教材の版管理 | 社内研修、面接練習、理解度確認、文章添削 |
| ec-shop | マスターと取引、注文と明細、確定時点の情報保存 | 受発注、見積、経費申請、貸出管理 |
| skill-janken | 選択と条件判定、行動履歴、状態復元、更新競合の検出 | 申請・承認、進捗管理、ポイント管理、操作履歴 |
| cast-evaluation-system | 日次実績、設定による計算、月次集計、順位 | 営業実績、活動実績、ルールに基づく評価一覧 |

共通して学ぶのは、対象の登録・表示、1 対多と多対多、入力検証、状態変更、履歴保存、ファイルや外部サービスとの関連付け。アプリ全体を合体するより、必要な処理とデータ構造を取り出して応用する。

| 組み合わせ例 | 応用する型 | 別途設計すること |
|---|---|---|
| 点検システム | 写真日記の画像付き記録＋英語訓練の評価 | 点検基準、判定、訂正のルール |
| 経費精算 | EC の申請・明細＋じゃんけんの状態変更・履歴＋写真日記の添付 | 承認経路、権限、締め処理 |
| 実績ダッシュボード | キャスト評価の期間集計＋日記の記録・絞り込み | 指標定義、対象期間、集計結果の公開範囲 |

日記・英語訓練・じゃんけんの README には、再送制御・途中失敗への対処・更新競合や AI 重複実行への対処が記載されている。再利用する際は対象の仕様・コード・検証記録を確認する。設計案や過去の試験結果を、そのまま現在の動作保証にはしない。

業務アプリへ広げる場合は、認証・認可、訂正・削除・承認、決済・通知・外部同期、データ量・同時更新への対応を用途ごとに追加する。たとえば写真日記は保存後の編集・削除が対象外であり、汎用的な更新機能まで備えるわけではない。

## 共通の追加機能案：AI 利用金額

AI を利用する各アプリで、利用ごとの金額・今月の合計・累計を確認できるようにする構想。元のメモを横断的な追加機能案として整理したもので、各アプリへの実装済み要件ではない。

| 項目 | 表示・記録する内容の案 |
|---|---|
| 利用ごとの金額 | 1 回の AI 要求に対応する利用量と推定金額 |
| 今月の使用金額 | 定義した月の範囲に含まれる要求の推定金額合計 |
| 累計の使用金額 | 記録開始以降の推定金額合計 |
| 根拠 | 実行日時、アプリ、要求 ID、モデル、入力・出力等の利用量、適用単価と通貨 |
| 成否・不明状態 | 成功・失敗・結果不明と、利用量を取得できたかどうか |

初期設計で揃えること：

- 月の区切りは Asia/Tokyo を候補とし、集計対象の利用者・アプリ・記録開始日を定義する。
- 推定金額とプロバイダーの請求額を区別する。単価・モデル・料金の適用時点を記録し、実装時に公式の料金情報を確認する。
- 同じ要求 ID の結果再取得を新たな AI 利用として二重計上しない。実際に追加の API 呼び出しが発生した場合は、その実行を区別して記録する。
- 結果不明や利用量未取得を 0 円とみなさない。未集計件数などで不完全な集計だと分かるようにする。
- 表示機能と、利用上限・警告・課金停止は別機能として扱う。

現時点の対象候補は写真日記・英語訓練・じゃんけんの管理画面での AI 利用。EC とキャスト評価の初期仕様には AI 機能がないため、金額表示のためだけに AI 機能を追加しない。

## 追加するとカバー範囲が広がる型

この節と続く銀行・転職・人材・メンバー評価の説明は、既存アプリの応用範囲を考えるための参照資料として残す。新規教材を追加する計画ではない。題材は既存5つに固定し、当面は同じ題材の理解・改修・技術基盤の違いを深める。

ここで扱うのはシステム設計の型。各業界の法令・制度・認証要件を網羅したものではない。また、型を学習用に再現できることと、本番サービスとして必要な性能・可用性・安全性を満たすことは別に評価する。

| 追加の型 | 代表的なシステム | 基本4アプリから追加で必要になる中心概念 |
|---|---|---|
| 台帳・残高・照合 | 銀行、ウォレット、会計、ポイント口座 | 複式の記録、整合する入出金、取消仕訳、利用可能残高、外部記録との照合 |
| マッチング・選考 | 転職、人材紹介、業務委託、取引先紹介 | 双方の条件、候補の順位付け、応募・推薦、段階別の進行、情報開示の範囲 |
| 目標・評価・育成 | メンバー評価、人事評価、360度評価、スキル管理 | 評価期間、基準の版、評価者の割当、根拠、評価調整、確定・公開、育成目標 |
| 予約・在庫・資源割当 | 宿泊、診療予約、座席、設備貸出、倉庫 | 有限の枠や数量、時間帯の重複、仮押さえ、期限切れ、取消による解放 |
| 組織・権限・承認 | 社内申請、グループウェア、企業向けSaaS | 組織階層、役割、企業別データ分離、代理承認、差戻し、承認ルート |
| 定期契約・利用量 | サブスクリプション、会員サービス、従量課金 | 契約期間、プラン変更、利用権、利用量集計、更新・解約、料金の適用期間 |
| 多人数のリアルタイム共有 | チャット、共同編集、対戦、ライブ状況表示 | イベント配信、接続・再接続、順序、同時編集の競合、在席状態 |
| 検索・推薦・公開配信 | 求人検索、商品検索、ナレッジ、SNS | 検索索引、関連度、推薦、公開範囲、投稿審査、フィード、検索エンジン向け公開ページ |
| 非同期処理・外部連携 | 一括取込、動画変換、メール配信、データ同期 | ジョブ、キュー、再試行、進捗、定期実行、Webhook、外部との不整合の検出と回復 |
| 集計・分析 | 売上分析、経営指標、利用分析 | 時系列集計、指標定義、集計用データ、遅れて届くデータ、過去値の再計算 |
| 地理・経路・現場連携 | 配送、配車、訪問業務、設備監視 | 位置と範囲、経路、移動時間、端末からの継続データ、圏外時の保存・再同期 |

特に大きく抜けているのは、**「量を矛盾なく移す」「有限資源を取り合う」「条件の合う相手を探す」「複数人・組織で権限を分けて進める」**という4つ。既存アプリにも履歴や競合対策はあるが、これらの業務ルールまで備わっているわけではない。

## 銀行系で加わるもの

銀行のWeb画面にある一覧・詳細・入力・履歴は、基本アプリの型を応用できる。追加の学習価値が大きいのは、口座間の価値の移動と、その記録の整合性。

- **台帳と残高**：残高だけを書き換えず、何によって増減したかを記録する。複式の台帳では、1取引内の借方・貸方を一致させる。
- **一体として成立する振替**：A口座の減額だけが保存され、B口座の増額が失われる状態を防ぐ。同じ送金要求を再送しても二重に移動させない。
- **取消・訂正**：確定済みの記録を消して帳尻を合わせず、元の取引を参照する取消・訂正の記録を追加する。
- **確定と保留の区別**：帳簿上の残高、保留中の金額、実際に利用可能な金額を区別する。
- **照合**：内部台帳と外部から得た取引記録を突き合わせ、不一致を検出して調査・修正する。

`skill-janken`の行動履歴と二重実行防止、`ec-shop`の取引・明細構造は出発点になる。ただし、ゲームの得点加算だけで複数口座の資金移動の整合性を満たせるわけではない。

学習用には「架空の口座間でポイントを振り替えるミニ台帳」が適している。実際の銀行システム全体には、このほか本人確認、不正検知、外部決済接続、運用統制など別の設計領域がある。

## 転職・人材系で加わるもの

転職・人材系は、**基本4アプリを組み合わせる効果が大きく、マッチングと複数当事者の業務を追加で学べる題材**。

| 機能 | 既存の型を応用できる部分 | 追加で設計する部分 |
|---|---|---|
| 求職者・求人の登録 | 日記の登録・一覧・絞り込み、タグや多対多の関係 | 求職者・企業・求人・スキル・希望条件のモデル |
| 履歴書・職務経歴書 | 日記の添付管理の考え方 | PDF等の取扱い、差替え・版、企業別の閲覧権限、開示の同意 |
| 求人への応募・企業への推薦 | ECの取引構造、じゃんけんの状態変更と履歴 | 応募・推薦の違い、重複応募、辞退、選考段階、担当者 |
| 条件のマッチング | タグによる絞り込み、英語訓練の評価構造 | 双方の必須条件と希望条件、順位付け、判定理由 |
| 面接練習・文章支援 | 英語訓練の対話・フィードバック、日記のAI下書き | 職種別のシナリオ、職務経歴書の改善支援、人による確認 |
| 面接日程 | 既存の一覧・入力画面 | 候補日時、複数参加者の空き、確定・変更、通知 |
| 人材紹介会社の案件管理 | 履歴、管理画面、取引情報 | 求職者・企業・担当者の三者関係、紹介経路、成約の記録 |

基本モデルの例は、`求職者`、`企業`、`求人`、`スキル`、`求職者スキル`、`求人スキル`、`応募`、`選考履歴`、`面接予定`。人材紹介に広げる場合は、`紹介会社`、`担当者`、`推薦`などを追加する。

「求職者と求人が多対多」だけでは不足する。両者を結ぶ応募には、応募日時、経路、現在の段階、辞退などの独自情報があるため、応募自体を業務上の対象として扱う。選考段階の履歴も別に残す。

マッチングは、まず勤務地・雇用形態・必須スキル等の明示的な条件で実装できる。推薦順位やAIによる補助はその後に追加する。AIの文章評価機能をそのまま採否判定に転用する設計にはせず、支援機能と採用判断の責務を分ける。

## メンバー評価管理で加わるもの

既存の [cast-evaluation-system](cast-evaluation-system/README.md) は、日次実績と現在の評価ルールによる月次集計に絞った設計。以下の自己評価・上司評価・承認・基準の版管理は、そこから広げる場合の別テーマであり、同アプリの初期 MVP に含めない。

メンバー評価管理は、**「目標・評価・育成」の型を学ぶ有力な題材**。社員・チームメンバーの目標、活動の根拠、自己評価、上司等による評価、面談、次期の育成目標を管理する想定。英語訓練の評価・履歴を応用できるが、人と組織をまたぐ評価の運用を追加する必要がある。

| 機能 | 既存の型を応用できる部分 | 追加で設計する部分 |
|---|---|---|
| 目標・活動実績 | 日記の記録・添付・タグ | 評価期間、個人目標、達成指標、活動と目標の関連 |
| 評価項目・基準 | 英語訓練の教材・評価・版管理 | 職種・役割別の基準、段階ごとの説明、必要なら配点・重み |
| 自己評価・上司評価 | 回答と評価結果の分離 | 評価者・対象者の割当、評価者の立場、複数人の独立した回答 |
| 根拠・フィードバック | 記録、添付、対話履歴 | 評価項目ごとの根拠、本人に公開するコメント、面談記録 |
| 提出・調整・確定 | 状態変更、履歴、二重送信防止 | 締切、差戻し、評価者間の調整、承認、公開時期、異議申立て |
| 育成と振り返り | 英語訓練の学習記録・振り返り | 次期目標、支援内容、フォロー面談、期間をまたぐ変化 |

この題材の特徴は、**「対象者 × 評価期間 × 評価項目 × 評価者」**の組合せを管理すること。単にメンバー表へ評価点の列を追加すると、過去の評価、複数評価者、基準変更を扱いにくくなる。

基本モデルの例：

- `メンバー`・`組織所属履歴`：誰が、いつ、どこに所属していたか。
- `評価期間`・`評価基準版`・`評価項目`：いつの評価で、どの基準を使うか。
- `目標`・`活動記録`：何を目指し、どんな実績・根拠があるか。
- `評価者割当`：対象者、評価者、期間、自己・上司・同僚などの役割。
- `評価回答`・`項目別評価`：割当ごとの提出単位と、各項目の評価・コメント。
- `確定評価`・`変更履歴`：調整後の決定と、変更理由・承認者・日時。

評価回答と確定評価を分ければ、上司間の調整で元の回答を上書きせず、判断の経緯を残せる。評価に用いた基準の版や割当も保持し、異動や基準の更新で過去の意味が変わらないようにする。

設計上、次の点が基本4アプリからの大きな追加になる。

1. **評価の状態と公開状態を分ける**：下書き→提出→確認・調整→確定と進め、本人への公開は別に管理する。確定後の訂正は理由と履歴を残す。
2. **権限を対象・期間・役割で判定する**：本人、割り当てられた評価者、人事、承認者が、それぞれ何を読めて変更できるかをサーバー側で判定する。異動後の閲覧範囲も決める。
3. **未評価と低評価を区別する**：未入力・評価不能・対象外を0点として集計しない。総合点を計算する場合は、対象外項目や重みの扱いを明示する。
4. **基準変更と比較可能性を扱う**：評価尺度や職種が変わった場合に、過去の点数をそのまま横並びにしない。
5. **360度評価は追加設計にする**：匿名性の範囲、少人数集計、自由記述からの評価者の特定を考慮し、氏名を隠しただけで匿名と扱わない。

最初の小規模版は「1組織・1評価期間・自己評価と上司評価・固定の評価基準・提出と差戻し・確定と本人公開」に絞ると、中心の仕組みを学びやすい。通知、360度評価、組織横断の評価調整、給与・昇格との連動は後から分けて追加する。

AIを加えるなら、活動記録の要約、根拠の整理、コメントの下書き、入力漏れの確認が候補。評価点・順位・昇格を自動決定する前提にはせず、根拠を確認した評価者が判断する。AIを使わなくても評価の全工程を完了できる構成にする。

転職・人材系が「人と仕事の出会い・選考」を扱うのに対し、メンバー評価は「参加後の目標・貢献・育成」を扱う。両方を題材にすると、人材領域の異なる業務構造を経験できる。

## 今後の進め方

当面は事業化と新規題材の追加を行わず、既存5教材を深める。[役割分担と全体最適化](#5教材の役割分担と全体最適化) を先に判断基準とし、機能の重複を薄くすることと、必要な基本機能を削ることを混同しない。

1. **現在のGAS版を検証する。** 最新の変更、実GAS環境での主要操作、コピー・引き渡し・復旧を確認する。設計段階のEC・キャスト評価は小さなMVPを具体化する。
2. **共通仕様と受入条件を整える。** 個別アプリの正本から業務要件・非対象・利用者・入力例・期待値を整理し、学習者の実装にも使える確認方法を用意する。
3. **最初の1題材を選ぶ。** 実際の利用・学習体験、現行版の安定性、発展版で学ぶ価値を基に選ぶ。全5教材を一括で移植しない。
4. **発展版の模範実装を用意する。** Next.js＋Supabase＋Vercelで同じ基本要件を満たし、共通の受入条件と基盤固有の権限・保存・運用を検証する。
5. **説明と演習へ落とし込む。** 記事・動画・AIへの改修依頼・比較観点を揃え、共通6工程と対面30分×3回の指導案で、本人が変更・検証・説明できるか確認する。
6. **教材資産として蓄積する。** つまずきと支援工数を記録し、共通手順へ戻す。他の題材の発展版は教育効果と保守余力を確認して追加する。
7. **横断レビューで再整理する。** 各題材の両版が揃うごとに確認し、比較材料が揃った時点でPortfolio Architecture Reviewを行う。専門性の強化、重複機能の簡素化、共通教材への整理を判断し、個別仕様と検証へ反映する。

将来事業化を検討するときに、需要・支払い意思・価格・有料伴走後の自立を検証する。現在の準備と有料募集を混同しない。銀行・転職等の応用例やAI利用金額の案は参照として保持し、実装範囲へ自動的に追加しない。

GAS版と発展版は基盤が違っても同じ業務要件を満たす比較対象とする。仕様を満たす方法は一つに限定せず、AIで作った結果を自分で確かめ、理由を説明できることを到達目標とする。
